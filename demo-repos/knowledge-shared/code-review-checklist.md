# 代码评审清单

> 适用范围：全部服务的合并请求评审，与具体业务领域无关。各服务的专属约定见各自仓库 `docs/` 下的文档。

评审时按组逐项自问。任何一项答不上来，都应先问清楚再决定是否通过。

## 1. 正确性

- 边界条件是否覆盖：空集合、极值、首尾元素、并发同时到达？
- 失败路径是否与成功路径一样被处理，还是只写了顺利情况？
- 涉及多次写入时，中途失败会留下什么状态，是否可恢复？
- 重复执行同一请求会不会产生第二次副作用？
- 改动是否附带了能复现原问题的测试，而不只是补一个通过的用例？

## 2. 安全

- 这次改动是否新增了未经权限校验的入口？
- 拼进语句、命令或路径的值有没有一个来自外部输入？
- 身份与权限是取自认证上下文，还是取自请求里传来的字段？
- 响应、日志与异常信息里有没有本不该出现的敏感字段？
- 新引入的配置项里有没有直接写死的密钥或口令？

## 3. 性能

- 循环体内是否发起了数据库或远程调用？
- 查询能否命中索引，还是依赖全表扫描碰运气？
- 返回集合有没有上限，数据量增长后会怎样？
- 新增的远程调用是否设置了超时与失败处理？
- 加锁范围是否超出了必要，会不会把并发压到串行？

## 4. 可观测性

- 出问题时，凭现有日志能否还原这次调用的完整路径？
- 请求标识是否贯穿全链路，异步分支有没有断掉？
- 值得告警的失败有没有对应的指标或日志级别？
- 日志量是否与调用量成正比到不可承受的程度？

## 5. 可维护性

- 这段逻辑的位置是否合理，还是塞在了顺手的地方？
- 有没有重复实现仓库里已存在的能力？
- 命名是否需要读注释才能理解？
- 新增依赖是否必要，引入的维护成本是否说得清？
- 若半年后由他人接手，最容易误解的是哪一处，是否已用注释说明原因？
