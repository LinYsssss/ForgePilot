按产品权限表，Finding 的处理链需要三种角色分工，而**你现在三个项目上都只有 LEADER 一个角色**：

| 动作 | LEADER | DEVELOPER | REVIEWER |

> 每个项目**恰有一个 LEADER**，补 DEVELOPER/REVIEWER 不影响这一点。

## 1. 全流程总览

```
① 上传项目知识  ──┐
                  ├──→ ③ 提 PR ──→ ④ webhook 自动同步 ──→ ⑤ Review 自动跑
② 建需求 + AC  ──┘                      ↓                        ↓
                                   PR↔需求关联              产出 Finding
                                                                 ↓
                              ⑥ Finding 处理闭环 ←──────────────┘
                                        ↓
                              ⑦ Review 终局 Decision
                                        ↓
                              ⑧ LEADER 确认需求 DONE
```

**顺序不能乱**：项目知识必须在触发 Review **之前**就位，否则审查拿不到它，Finding 的质量会明显下降。你自己的评测数据是最好的说明——知识进上下文让缺陷检出从 21.62% 提到 32.26%。

### 记下需求 id —— 这是整条链路最容易出错的地方

需求创建后，**页面上的需求 id 是全局递增的，不是项目内编号**。

系统从 PR 标题和分支名里解析的是 `REQ-<全局 id>`，正则是 `(?<![A-Za-z0-9])REQ-(\d{1,18})`。

清库前的数据就栽在这里：项目 1 的需求 id 恰好是 1–5，它的 5 个 PR 标题写 `REQ-1..REQ-5` 全部关联成功；项目 2、3 的需求 id 是 6–10 和 11–15，标题却也写着 `REQ-1..REQ-5`，于是 **10 个 PR 一个都没关联上**。

按本文档顺序建需求的话，id 会是这样：

| 仓库 | 需求 | 全局 id |
|---|---|---|
| mall-order-service | 发货校验与幂等 / 强制发货鉴权 / 搜索注入 | 1 / 2 / 3 |
| tenant-user-center | 认证授权与租户来源 / SQL 注入与 bcrypt / 前端安全整改 | 4 / 5 / 6 |
| payment-settlement | 整数分与配置费率 / 幂等与鉴权 / 回调验签 | 7 / 8 / 9 |

### DRAFT → READY 之前把内容改对

- **DRAFT 阶段**：正文与 AC 可以原地编辑。
- **READY 之后**：正文与 AC **锁定**。再改必须由 LEADER 创建一个新的不可变 Revision 并填写变更原因，旧 AC 永久保留。

所以：**粘贴完先通读一遍，确认无误再置 READY。**

`READY → IN_DEVELOPMENT` 与**首次指派**是同一个事务——把需求指派给自己，状态会自动推进，不需要单独操作。后续换负责人不再改变状态。

### 可选：跑一次需求质量检查

界面上可以对需求跑质量检查。**它的结果是建议，不是工作流状态**，不会阻塞也不会自动置 READY。答辩时这是个不错的展示点。

### 可选：生成一次性 AI 实现建议

需求详情页可以生成实现建议（LEADER，或被指派的 DEVELOPER）。**每条需求只能生成一次**，想展示就在动手写代码前做。

## 4. 第三步：写代码、提 PR

在对应仓库上开分支实现。**PR 标题必须带上全局需求 id**：

```
REQ-7 发货接口补齐前置校验并保证幂等
```

分支名也可以承载，两者取其一即可：

```
feature/req-7-ship-validation
```

**正则细节**：`(?<![A-Za-z0-9])REQ-(\d{1,18})`——`REQ-` 前面不能紧挨字母或数字。`[ForgePilot Demo] REQ-7 ...` 可以，`XREQ-7` 不行。

推荐的 PR 描述模板：

```markdown
## 需求
REQ-7 发货接口补齐前置校验并保证幂等

## 改动
- OrderService.shipOrder 补齐四项前置校验
- updateStatus 改为条件更新，返回影响行数
- 新增 shippedAt 与操作人写入

## 自测
- 未支付订单被拒绝
- 连续调用两次只发货一次
```

推上去、开 PR 之后，webhook 会自动投递。**不需要在 ForgePilot 里手动创建 PR。**

### 关联不上怎么办

解析失败**不会阻断入库**——PR 照样进系统，只是标记「未关联需求」。两条补救路径：

1. **界面改**：代码审查页面找到该 PR，用需求下拉框选中，可改可清除。
2. **改 PR 标题**：在 GitHub 上把标题改对，再推一个新 commit 触发同步。

权限：LEADER 始终可改；DEVELOPER 只能改本人的 PR，且**当前 head 尚无任何人工终局 Decision** 时才可改。

对应接口是 `PUT /api/projects/{projectId}/pull-requests/{pullRequestId}/requirement`。

> 一个需求可以有多个 PR；一个 PR 至多关联一个需求。

## 5. 第四步：确认 PR 已同步、Review 已触发

webhook 到达后，系统做三件事：校验签名 → 回读 Provider 权威数据 → 在同一事务里落 PR 并创建 **PENDING** 的 Review，提交后才启动执行器。

界面：**代码审查**（`/reviews`）。也可以直接查库：

```bash
docker exec fp-demo-postgres-1 psql -U forgepilot -d forgepilot -c \
  "select pr.id, pr.project_id, pr.external_number, pr.title, pr.requirement_id,
          left(pr.head_sha,8) as head, rv.status, rv.decision
   from pull_request pr left join review rv on rv.pull_request_id = pr.id
   order by pr.id desc limit 10;"
```

看 `requirement_id` 是否非空，以及 Review 是否从 `PENDING` 走到 `RUNNING` → `COMPLETED`。

关联是不是**真的由 webhook 自动完成**的，看这张表：

```bash
docker exec fp-demo-postgres-1 psql -U forgepilot -d forgepilot -c \
  "select * from pull_request_requirement_event order by id desc limit 5;"
```

`actor_type = SYSTEM` 且 reason 形如 `Linked from REQ-7 in the pull request title` —— **只有真实 webhook 摄入路径会写出这一行**，手工塞数据写不出来。答辩时这是「真投递」最硬的证据。

## 6. 第五步：处理 Finding

**导航：代码审查 → 点进具体 Review**。

每条 Finding 带着证据：命中的 AC、代码位置、引用的项目知识片段。

### 三个正交的概念，界面上分开呈现，不要混为一谈

| 概念 | 取值 | 含义 |
|---|---|---|
| **Finding 状态** | OPEN / CONFIRMED / IN_PROGRESS / FIXED / VERIFIED / CLOSED / REJECTED | 人工处理到哪一步 |
| **continuity** | NEW / PERSISTING / SUPPRESSED | 这条问题跨轮次的来源 |
| **模型置信度** | HIGH / MEDIUM / LOW | 模型自报把握，**未经校准** |

置信度**不参与任何自动门禁或状态流转**。答辩被问到时要如实说：它是模型自报的，不是质量保证。

### 状态流转

```
主链：OPEN → CONFIRMED → IN_PROGRESS → FIXED → VERIFIED → CLOSED
旁路：OPEN → REJECTED，CONFIRMED → REJECTED
打回：FIXED → IN_PROGRESS（复验不通过）
重开：REJECTED → OPEN（仅 continuity = SUPPRESSED 的继承驳回项）
终态：CLOSED；REJECTED（普通驳回不可逆）
```

一条 Finding 的完整走法，对应你补齐角色后的三顶帽子：

1. **确认**（LEADER/REVIEWER）：`OPEN → CONFIRMED`，或判定误报 `OPEN → REJECTED`
2. **认领**（DEVELOPER）：`CONFIRMED → IN_PROGRESS`
3. **修复后标记**（DEVELOPER）：`IN_PROGRESS → FIXED`
4. **复验**（LEADER/REVIEWER）：通过 `FIXED → VERIFIED`，不通过打回 `FIXED → IN_PROGRESS`
5. **关闭**：`VERIFIED → CLOSED`

**普通驳回不可逆**，想清楚再点 REJECTED。

## 7. 第六步：改完代码推新 head，触发复审

修完推新 commit 到同一个 PR。

Review 的身份是 **(PR, head SHA, Diff fingerprint, 需求版本)** 四元组。新 head 一到，上一次 Review 立刻变成**历史**，需要新的一轮。

**这一步答辩时一定要演**——清库前的库里只有 1 个 PR、1 次 Review，「推新 head 让前一次 Review 变历史」是唯一没被真实数据覆盖过的环节。

上一轮已驳回、且源码证据与判定依据都没变的 Finding，本轮**自动抑制**，不要求你重复驳回一遍（`continuity = SUPPRESSED`）。

> **已知限制，答辩要如实说**：`finding_key` 里含 patch 新侧行号，无关插入造成行号整体移动时，同一条证据可能被判成 `NEW` 而继承不到上一轮的 `SUPPRESSED`。

**需求版本变了不会自动重审**——关联 PR 会显示「审查已过期」，由人工触发。

## 8. 第七步：Review 终局决策

**权限**：LEADER 或 REVIEWER。

`PENDING → APPROVE` 或 `PENDING → REQUEST_CHANGES`，**只能写入一次**。写入条件：

- 目标 Review 已 COMPLETED；
- head、Diff fingerprint、需求版本三者都等于 PR 当前值。

**闸门**：同一个 head 上出现过 REQUEST_CHANGES 后，**必须有新的 head SHA 才能再 APPROVE**。改 Base、改需求关联、改需求版本、重新同步 Diff 都解不开这个闸门。

需求列表上的「评审活动」是**只读派生量**，不落表，按当前 head + fingerprint + 需求版本实时算：

| 情况 | Activity |
|---|---|
| 没有关联 PR | `NO_PR` |
| 没有匹配当前输入的 Review | `REVIEW_REQUIRED` |
| 执行失败 | `FAILED` |
| Decision 为 REQUEST_CHANGES | `CHANGES_REQUESTED` |
| RUNNING，或 COMPLETED 但等人工决策 | `REVIEWING` |
| PENDING | `PENDING` |
| Decision 为 APPROVE | `APPROVED` |

多 PR 聚合：`FAILED`、`CHANGES_REQUESTED` 依次占优；全部相同返回该状态；全 `APPROVED` 才 `APPROVED`；其余返回 `MIXED` 并展示各状态计数。

**需求状态与评审活动并列展示，不合并。**

---

## 9. 第八步：需求收尾

单个 PR 的 APPROVE **只结束当前 Review**，不代表需求完成。

需求状态 `IN_DEVELOPMENT → DONE` 必须由 **LEADER** 在确认全部关联工作完成后手动执行。

**AI、Webhook、PR、Review 一律不得推进需求状态**——这是产品的硬边界，答辩时值得主动讲，它区分了「AI 给建议」和「AI 替人做决定」。

## 10. 一次完整演练的推荐路线

想最快跑通全链路，建议用 **Mall Order Service Demo 的 REQ「订单搜索消除 SQL 注入」**：改动面小、缺陷类型明确（SQL 注入）、项目知识里有 BUG-004 的历史事故可被引用为证据。

```
补三个角色
  → 修 mall 的 webhook secret（§0 硬阻塞二，不修的话 PR 根本进不来）
  → 上传 3 份项目知识，等 READY
  → 建 mall 的 3 条需求，记下 id，置 READY 并指派给自己
  → 在 mall 仓开分支，故意「只修 searchByKeyword、留着 selectBySql」
  → 提 PR，标题带 REQ-<id>
  → 看 Review 是否命中 AC-4（预期会）
  → 确认 Finding → 认领 → 补修 selectBySql → 推新 head
  → 看上一轮 Review 变历史、新一轮不再报这条
  → REQUEST_CHANGES → 新 head → APPROVE
  → LEADER 置需求 DONE
```

这条路线一次覆盖：知识引用、AC 命中、Finding 全生命周期、跨轮抑制、新 head 使 Review 变历史、Decision 闸门、需求状态由人控制。**故意留一个漏项**，是为了让审查有东西可报——第一轮全对反而演示不出效果。

### webhook 没触发

```bash

gh api repos/LinYsssss/reposage-demo-mall-order-service/hooks/669791570/deliveries \
  --jq '.[0:5][] | "\(.delivered_at) \(.event) -> \(.status_code) \(.status)"'
```

| 响应码 | 含义 | 处理 |
|---|---|---|
| 2xx | 正常 | 查 `pull_request` 表 |
| 401 / 403 | 签名校验失败 | ForgePilot 里的 webhook secret 与 GitHub hook 上的不一致。**mall 仓当前就是这个状态**，修法见 §0 |
| 422 | 被拒绝 | changed-file 数量超限。**这种情况不留痕**，运维看不到，是已知限制 |
| 5xx | 后端异常 | `docker logs fp-demo-backend-1 --tail 200` |

hook id：mall `669791570`；campus-backend `672382214`、campus-frontend `672382220`（毕设仓）。tenant 与 payment 建好 webhook 后把新 id 记在这里。

### PR 进来了但没关联需求

```bash
docker exec fp-demo-postgres-1 psql -U forgepilot -d forgepilot -c \
  "select id, project_id, external_number, title, requirement_id from pull_request order by id desc limit 5;"
```

`requirement_id` 为空，九成是标题里的编号不是**全局 id**。按第 4 节两条路径补救。

### Review 一直 PENDING 或 FAILED

```bash
docker exec fp-demo-postgres-1 psql -U forgepilot -d forgepilot -c \
  "select id, status, decision, execution_attempt, engine, model from review order by id desc limit 5;"

docker exec fp-demo-postgres-1 psql -U forgepilot -d forgepilot -c \
  "select id, review_id, use_case, model, status, latency_ms, error, created_at
   from ai_call_log order by id desc limit 10;"
```

- 长时间 `PENDING`：执行器没启动或已停滞，reconciliation 会兜底恢复；**reconciliation 不会补建缺失的 Review**。
- `FAILED`：看 `ai_call_log`。AI 返回结构非法时 Review 判定失败，**系统绝不会生成「成功的空报告」**——这是有意为之。
- FAILED 重试复用同一行；COMPLETED 永不覆盖。

## 12. 答辩时要主动说清的几件事

这些是产品的真实边界，被问到再解释不如主动讲：

1. **语义检索没有向量索引**，走顺序扫描的精确余弦序。冻结的 Embedding Profile 是 4096 维，超过 pgvector 0.8.6 全部精确索引形态的维度上限，可建的两种都是有损预筛。这是决策不是遗漏。
2. **评测的第三臂喂的是案例的全部知识文件原文**，由 runner 从磁盘读入渲染进 prompt，不做 embedding、不做 TopK、不碰运行中的应用。所以 21.62% → 32.26% 证明的是「项目知识进上下文有用」，**不是「ForgePilot 的 pgvector 检索管线有效」**。检索是有独立测试的产品能力，但不是这组数字评的东西。
3. **holdout 只有 12 例**，且缺陷是人工构造的演示缺陷，不是真实企业缺陷。结论必须给置信区间。
4. **模型置信度未经校准**，不参与任何门禁。
5. **需求状态转换不单独留痕**，`DRAFT→READY`、指派、`DONE` 的转换本身不写审计行。这是明确接受的取舍。
6. **一个项目一个仓库**是 MVP 约束；仓库产生 PR 后不可原地更换。
