# Campus Frontend Demo — 需求清单

> 目标项目：ForgePilot「Campus Frontend Demo」（项目 2）
> 目标仓库：`LinYsssss/campus-platform-frontend`
>
> **使用方式**：每条需求的「标题 / 背景 / 描述」直接粘进 ForgePilot 需求表单，「验收条件」逐条录入。
> 分隔线以下的「改动范围」「预期发现」**不要粘贴**。

三条需求都对应仓库里当前真实存在的缺口。

> **注意**：本仓 `package.json` 中没有测试框架（`scripts` 只有 `dev` / `build` / `preview`），因此所有验收条件都不要求补单元测试，验证方式是 `npm run build` 通过加人工走查。这一点已写进项目知识，审查会据此判定「要求补测试」的说法不成立。

## 需求一：登录态过期处理修复

**标题**

```
登录态过期后保留来源路由并消除重复跳转
```

**背景**

```
src/api/request.js 的响应拦截器在两处处理 401：业务层分支（response.data.code === 401）和传输层分支（error.response.status === 401）。两处的处理都是「ElMessage 提示 → authStore.logoutAction() → router.push('/login')」。

这段处理有三个问题：

1. 没有保留用户当前所在路由。重新登录后一律落到角色默认首页，用户丢失上下文。
2. logoutAction() 内部自己已经调用了 router.push('/login')，拦截器随后又调一次，同一次过期触发两次导航。
3. logoutAction() 会先调用 logout() 这个后端接口。但在 401 场景下 token 已经失效，这个请求本身会再次返回 401，重新进入响应拦截器，再走一遍整套处理 —— 提示重复弹出，且形成自我触发的循环。

页面并发发起多个请求时，上述过程会按失败请求数量重复，用户会看到叠加的多条「登录已过期」提示。
```

**描述**

```
把登录态过期的处理收敛成一次性的、可恢复的流程：记住用户原本要去的地方，只跳转一次，只提示一次，并且不因清理动作本身再次触发过期处理。

登录成功后回到过期前的页面。用户原本就在登录页、或来源是登录页时，回到角色默认首页。
```

**验收条件**

```
AC-1  会话过期跳转登录页时，通过路由查询参数携带过期前的完整路径（含查询参数）。
AC-2  登录成功后跳回该路径；未携带该参数、或该参数指向登录页时，回到 ROLE_DEFAULT_PATH 对应的角色默认首页。
AC-3  该参数只接受站内路径，以协议或双斜杠开头的外部地址一律忽略并回落到默认首页。
AC-4  一次会话过期只发生一次路由跳转，logoutAction 与拦截器不重复导航。
AC-5  并发请求同时返回 401 时，只弹出一条提示、只跳转一次。
AC-6  清理登录态的过程不再触发新的 401 处理，不出现自我循环。
AC-7  业务层（响应体 code）与传输层（HTTP status）两处 401 分支行为一致，不得只改其中一处。
AC-8  已在登录页时收到 401 不再跳转，也不弹提示。
AC-9  清理登录态时 token、userInfo、permissions、roles 与已过滤路由全部清空，与现有 resetState 行为一致。
AC-10 npm run build 通过，403 / 400 / 500 等其他错误码的现有行为不变。
```

---
**改动范围（不要粘贴）**

- `src/api/request.js`
- `src/stores/auth.js`
- `src/views/login/index.vue`
- 可能涉及 `src/router/index.js`

**预期 ForgePilot 会报出的问题**

只改一处 401 分支应命中 AC-7。直接把 `redirect` 参数拿去 `router.push` 而不校验来源应命中 AC-3（开放重定向）。用模块级布尔量做去重却不复位，会导致第二次过期不再提示，审查应指出这个状态泄漏。

## 需求二：路由权限过滤修复

**标题**

```
修复权限过滤后残留空目录父路由
```

**背景**

```
src/utils/permission.js 的 filterRoutes 函数注释声明「父路由的 children 全部被过滤后，父路由也移除」，但实现链尾的这条过滤：

  .filter(route => !route.children?.length || route.children.length > 0)

条件恒为 true —— children 为空数组时第一个子句成立，非空时第二个子句成立。该过滤是死代码，声明的行为从未生效。

后果是：一个自身没有 meta.roles 限制、但子路由全部被角色过滤掉的父节点，仍然留在侧边栏菜单中，用户点进去是一个空目录。
```

**描述**

```
让 filterRoutes 的实现与其声明一致：递归过滤后，凡是原本有子路由、但子路由全部被过滤掉的父节点，一并移除。

叶子路由本身没有子路由，不受此规则影响，必须保留。
```

**验收条件**

```
AC-1  原本有子路由、过滤后子路由为空的父节点被移除。
AC-2  原本就没有子路由的叶子路由被保留，不因 children 为空数组而误删。
AC-3  多层嵌套下逐层生效：孙节点全被过滤 → 子节点被移除 → 若父节点因此没有子节点，父节点也被移除。
AC-4  自身命中 meta.roles 限制的路由，行为与现在一致（在第一层过滤中即被移除）。
AC-5  未设置 meta.roles 的路由仍然放行，hasPermission 的语义不变。
AC-6  函数保持纯函数，不修改传入的 routes 数组。
AC-7  三个角色（admin / teacher / student）登录后侧边栏均无空目录，且各自原有的可见菜单一项不少。
AC-8  npm run build 通过。
```

---
**改动范围（不要粘贴）**

- `src/utils/permission.js`

**预期 ForgePilot 会报出的问题**

把条件写成 `route.children.length > 0` 会连叶子路由一起删掉（`.map` 里给叶子赋了 `children: []`），应命中 AC-2 —— 这是这条需求最容易踩的坑。用 `delete route.children` 或就地修改入参应命中 AC-6。

## 需求三：请求失败提示收敛

**标题**

```
请求失败提示去重与可恢复动作
```

**背景**

```
src/api/request.js 的响应拦截器在每个错误分支都无条件调用 ElMessage.error。页面首屏通常并发发起多个请求，后端一旦故障，用户会同时看到多条内容完全相同的错误提示堆叠在屏幕上。

同时，除 401 之外的错误码只有一句文案，没有任何可恢复动作 —— 用户看到「服务器内部错误」后无事可做，只能手动刷新整页。
```

**描述**

```
让同一类错误在短时间内只提示一次，并为可重试的失败提供明确的恢复入口。

提示去重按错误内容归并，不同错误仍要分别提示，不能因为去重而吞掉真实信息。
```

**验收条件**

```
AC-1  同一文案的错误提示在短时间窗口内只显示一条，窗口结束后再次发生同类错误仍能正常提示。
AC-2  不同文案的错误分别提示，去重不跨错误类型合并。
AC-3  网络不可达（无 response）与后端返回 5xx 分别给出可区分的文案。
AC-4  可重试的失败（网络不可达、5xx、超时）在提示中提供重试入口或明确告知可重试；400、403 这类不可重试的失败不提供重试入口。
AC-5  401 的处理路径不受本需求改动影响，行为与需求一交付后保持一致。
AC-6  去重状态不泄漏到页面切换之后，路由跳转不会让后续同类错误被静默吞掉。
AC-7  请求成功路径零改动，normalizeResponseData 的行为不变。
AC-8  npm run build 通过。
```

---
**改动范围（不要粘贴）**

- `src/api/request.js`
- 可能新增 `src/utils/` 下的提示工具

**预期 ForgePilot 会报出的问题**

用一个模块级 `Set` 记录已提示文案却从不清理，会让同一错误此后永远静默，应命中 AC-1 与 AC-6。把去重实现进 `normalizeResponseData` 或成功分支应命中 AC-7。
