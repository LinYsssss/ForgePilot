## 1. 用户确认的范围

1. 改善审查质量，但不增加系统复杂度。
2. **不新增调用次数限制、预算、注册限制或计费功能**；只展示已有模型使用记录。现有基础保护保持原样。
3. 保留已有“通过并合并／退回修改”；“拒绝并关闭”放在最后，作为可独立暂缓的步骤。
4. 最小化实现、复用原代码、不引入冗余抽象，不为测试数量或覆盖率扩张测试。

总边界：一条 Review Engine；不加 Agent、Redis、MQ、缓存层、编排器、一级导航、新业务表、图表库或第二审查管线。不做全仓索引、Rerank、自动训练、自动修复或大范围重构。冻结评测文件、holdout、原始输出和历史报告均不改写、不重跑。

## 2. 复核结论与本次修订

已对照现有提示词、校验器、决定流程、统计查询和最新前端变化检查方案。方向可行，补齐以下边界后，不需要扩大为新架构：

- UNKNOWN 仅表达内容证据不足，不能把非法 JSON、缺失必需数组或 Provider 失败变成成功报告。
- 新结论同步生产 schema、读模型和前端映射；历史三值报告原样兼容，不迁移实验数据。
- 调用面板复用既有能力，次数定义为累计已记录请求尝试，不冒充审查轮数或供应商账单。
- 关闭重试须区分远端已关闭但本地未记、远端已合并、版本已变化，不能被关闭闸门挡死，也不能伪造成功。
- REJECT 是新增的一次性人工决定，不能覆盖既有决定；同 head 的拒绝不得通过改 Base、关联或需求修订绕过通过闸门。
- C 比 A/B 范围大，保持独立、最后做，不把它包装成只增加一个按钮。

## 3. 步骤 A：改善审查质量

### A1 补全候选问题的交接

现状：ReviewPrompts.appendCandidates 只输出类型、文件/行号、AC 和代码引用，未交接 FindingCandidate 已有的类别、问题解释和修复建议。

- 直接在原方法附带 category、explanation、suggestion，仍作为不可信模型内容处理；不新建候选表、转换器或提示词注册中心。
- 保留原代码证据和 AC 关联。当前 Candidate 没有保存原始 sourceIds，本步骤不另建引用模型或从 hash 反推引用。
- 不以模型自报 confidence 作为正确性证明或自动门禁。综合阶段核对并合并问题理由，不仅凭孤立引用重猜问题。
- 沿用已有散文长度上限及完整 Prompt 预算检查。不截断代码证据、不静默丢候选；超限显式失败，不另造压缩器或增加调用轮次。用现有代表性 fixture 检查增加散文后的预算影响。

### A2 区分信息不足和确定结论

- 将已有且经过批次校验的 acEvidence 交给最终校验逻辑，不新增校验服务或另一套规则运行器。
- 生产 AC 报告增加 UNKNOWN（信息不足／待人工核实）。它不是需求状态、Review 执行状态或人工决定。
- 对合法结构的回答：漏答某条 AC、该 AC 声称 COVERED 却无对应有效证据，或本轮零文件实际受审时，将相应 AC 记为 UNKNOWN 并保留 warning。
- Provider 失败、非法 JSON、缺失必需数组仍走原有有限修复和 FAILED 路径，不能被 UNKNOWN 兜底吞掉。
- 有有效引用只是 COVERED 的必要条件，不证明逻辑正确。部分文件未审或已截断时仍展示覆盖清单；NOT_FOUND 仅说明在本轮已审变更中未找到，不表示整个仓库没实现。
- 无关联需求时仍返回空 AC 列表，不生成虚构的 UNKNOWN 条目。
- 问题解释聚焦触发条件、实际影响、证据和修改建议；对缺少实现／测试的断言要求克制，不增加判官调用或评分模型。

兼容与范围：

- 同步生产 Prompt/schema、AcVerdict、现有覆盖度读模型及前端类型/标签；不用新增表、数据库列或迁移。
- 旧报告仍读取原有三个值，不把历史 NOT_FOUND 改成 UNKNOWN，新旧历史可同时展示。
- 生产 ReviewPrompts.VERSION 递增；不改 Finding key/双 hash 规则及 FindingKeys.RULE_VERSION；不修改冻结的离线 schema、runner、scorer。
- 改动集中于 ReviewPrompts、ReviewOutputValidator、ReviewPipeline 及直接消费这些字段的原代码，不新造中间层。

验收：候选理由进入综合；无对应证据不能显示已覆盖；格式失败仍失败；旧报告可读；模型调用阶段数量不增加。

## 4. 步骤 B：完善已有 AI 使用面板

现有 ai_call_log 已记录 model、use_case、状态、Token、耗时和时间；现有 GET /api/projects/{projectId}/ai-usage 与工作台折叠台账已展示统计，直接扩展原查询和表格。

1. 聚合从按用途改为按 **model + use_case**，响应增加 model，原表格补模型列。
2. 保留原成功／未成功、耗时分位、已记录 Token 和最近调用，不新增图表。
3. 标注本项目累计已记录调用尝试：重试各算一次，失败/超时计入；运行中或未成功写入日志的请求不冒充已经统计，次数不等于审查轮数或账单。
4. 模型名来自请求记录，不声称验证了服务商内部模型。行 key 使用用途与模型的唯一组合；用途种类不能继续使用 rows.length。
5. 没有记录时显示暂无调用；读取失败仅显示局部错误，不影响工作台，也不显示成零。
6. Token 使用已记录合计口径，说明未上报部分不计入；全缺失显示未记录，不伪造为零。不估算金额，不把调用成功率叫作审查准确率。

范围：ReviewInsightRepository、现有响应/映射、前端 review/api.ts、WorkspacePage.vue。复用原项目鉴权、接口、布局和 CSS，不撤销最新主线的界面密度调整。

不做：额度、熔断、注册开关、充值、计费、日期筛选、导出、自动刷新、推送、新页面、新表或新端点。

验收：不同模型分开、累计次数与记录一致、项目隔离不变、空数据/错误/缺失 Token 表述真实。

## 5. 步骤 C：可选的最小终局操作

### 保留已有两种动作

| 人工动作 | 行为 |
|---|---|
| 通过并合并 | 保留现有权限、当前版本、一次性决定与被审 SHA 核验，远端确认后提交本地决定 |
| 退回修改 | 必填理由，保留 PR 和分支，开发者新提交后进入新轮次 |

### 只补拒绝并关闭

- 审查详情增加次要危险操作，要求理由和二次确认，默认不删除源分支。
- 复用原决定入口、SCM 门面、GitHub/GitLab 客户端和 Review 的 actor/time/comment 记录。增加 REJECT 决定，不建独立关闭服务、审计表或通用命令模块。
- 权限沿用指定审查人／LEADER，沿用 Review 已完成、尚未终局及当前版本检查。用户明确拒绝整个 PR，系统才执行远端关闭。
- 远端明确关闭后才提交本地拒绝决定；已合并 PR 不能当成关闭成功。关闭针对 PR 本身，不承诺像 SHA 合并那样具有远端原子版本条件，执行前仍核验版本。
- 超时或结果不明时仅做一次只读核验；仍不明确就不记录成功，提示人工核查。不做无限写重试或后台补偿队列。

最小重试与一次性语义：

- 同一 Review 已有终局决定时不覆盖、不重复通知；重复请求保持原决定，不再次触发远端写入。
- 若本地仍 PENDING、远端已关闭，且原有权限/版本条件仍满足，允许同一个关闭动作只读核验后补记本地决定，不能被统一的已关闭不可操作规则挡住。界面保留必要的核验补记入口，可复用原关闭操作，不另建恢复页面。
- 若远端已合并或版本已变化，拒绝补记并提示核查，不强行修成一致；跨系统原子性仍不保证。
- 已终局的退回修改不能在同一 Review 上改判成关闭；随后放弃该 PR 可在托管平台关闭，由原同步路径读取事实。本版不增加撤销决定流程。
- 同 head 的 REQUEST_CHANGES 或 REJECT 都不能通过改 Base、关联或需求修订绕过通过闸门。外部重开不撤销旧决定，后续按新提交进入新轮次。

### 必要的最小状态同步

- pull_request 增加远端状态字段 OPEN/CLOSED/MERGED；历史未核验可为空并显示未同步，不能在迁移时猜测为 OPEN。
- 复用已有权威快照/Webhook读取远端状态；该状态不进入 Diff 指纹，不制造新 Review 身份。GitHub 关闭与合并须按实际 merged 标志区分，不能只看 closed。
- 本系统合并/关闭确认成功时也回写状态，不依赖 Webhook 恰好及时到达；已关闭/合并不再进入待审队列或启动新审查。
- 已经运行的审查可按原流程结束并保留历史，不新增取消执行器；终局操作仍受当前远端状态约束。
- 外部合并不伪造本系统人工 APPROVE；关闭不自动取消需求，合并不自动 DONE。
- 不做历史批量联网补齐、仓库定时轮询或新增重开按钮。历史未同步记录在真正操作前读取远端确认。
- 沿用原通知，只补拒绝关闭文案，不新增通知渠道。

预计一份追加 Flyway 迁移，使用下一可用序号：扩展现有决定 CHECK 并增加 PR 远端状态列，不修改旧迁移、不加表。同步迁移计数/版本断言及必要规范，这是兼容性工作，不是扩大测试范围。

改动落在 review、scm、现有通知和相应前端状态展示；C 的跨层范围大于 A/B。若实现需要额外恢复系统、状态编排或突破以上范围，先停下说明，由用户决定是否暂缓 C，不自行扩张。

官方接口核对依据：GitHub REST Pull requests（Update / Merge），GitLab Merge requests API（Update / Merge）。关闭确认是 Provider 状态核验，不是另建 Git 工作区。

## 6. 最少且必要的验证

不为 DTO/getter、每个文案、颜色或覆盖率数字增加测试，复用原 fixture、Provider 桩和测试类。

- A：候选理由交接；证据不足与格式失败分流；旧报告兼容。相近输入合并参数化场景，顺带检查代表性 Prompt 预算。
- B：模型分组、项目隔离、缺失数据语义及原面板的一次必要渲染检查。
- C：确认关闭才提交、失败/不明不记成功、已关闭未落本地时可核验补记、已合并/旧版本/无权限不能误关，以及新状态队列语义与非空历史数据迁移兼容。通过原入口集中验证，不建新测试框架。
- 每步跑相关定向检查；全部代码完成后沿用现有完整回归/构建一次。只有失败且发生修复时，才重跑受影响门禁，不因改文案重复全量。
- 本机不具备的运行条件明确记录未执行，不降低 Java/数据库版本制造通过。
- 人工只走查改动面板和关闭确认。真实模型调用、真实 PR 合并/关闭另需明确授权，不作为自动测试默认动作。
- 不重跑旧 holdout、不新建大规模评测、不反复采样。代码检查通过不等于模型质量提升已被证明。

**本次仅发布计划**：只做文档复核、源码路径核对、差异检查、提交范围和远端提交核验，不执行上述未来功能测试。

预期交付：原审查不再丢失重要理由、证据不足时更诚实；原工作台显示模型与调用；原通过/退回保留，关闭仅在最小范围内补齐。不是新平台。
