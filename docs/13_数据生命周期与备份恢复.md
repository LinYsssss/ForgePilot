# 数据生命周期与备份恢复

> 口径日期:2026-08-14,与 `deploy/docker-compose.yml` 卷实况及 backend 代码逐条核对。
> 本文回答三件事:哪些数据是持久真相、每个卷/表的清理边界在哪、备份与恢复怎么做。

## 1. 数据分层总览

| 层 | 载体 | 生命周期 | 是否需要备份 |
| --- | --- | --- | --- |
| 业务真相 | PostgreSQL(`postgres_data` 卷) | 永久,唯一需备份的数据 | **是** |
| 消息 | RabbitMQ 队列 | 瞬态,消费即焚;彻底失败进死信队列等人工处理 | 否 |
| 工作区/缓存 | `backend_work` / `sandbox_work` / `sandbox_dependency_cache` 卷 | 可重建 | 否 |
| 工作区归档 | `sandbox_archives` 卷 | 短命,由 `WorkspaceArchiveService` 管理(见 §3) | 否 |
| 容器日志 | Docker json-file | 滚动覆盖,每服务 3×10m 封顶,整栈约 330m | 否 |
| 观测数据 | Prometheus / Alertmanager / Grafana | 刻意不持久化,容器重建即清零(看板由 provisioning 重建) | 否 |

关键前提:**只有 dump 恢复不出可用系统**。数据库里的 SCM 凭据 / webhook 密钥是用 `deploy/.env` 的 `TOKEN_ENCRYPT_KEY` 加密的,`.env` 必须走单独安全渠道保管(不入库、不放备份目录,纪律见 `deploy/backup.sh` 头注)。

## 2. Compose 卷清单与清理边界

五个具名卷(`deploy/docker-compose.yml` 底部声明),逐一说明:

| 卷 | 挂载点 | 职责 | 能否删 / 清理机制 |
| --- | --- | --- | --- |
| `postgres_data` | postgres `/var/lib/postgresql/data` | 全部业务数据(含 pgvector 向量) | **不能随手删**,删即丢库;重建前必须有可恢复的 dump |
| `backend_work` | backend `/app/.work` | backend 的仓库克隆/检出工作区 | 可删,下次任务自动重建;仅在磁盘吃紧时 `docker compose down` 后清 |
| `sandbox_work` | sandbox-runner `/app/.work` | 沙箱作业的临时工作区 | 可删,作业级临时数据,重建零成本 |
| `sandbox_dependency_cache` | sandbox-runner `/app/.cache/dependencies` | 沙箱构建的依赖缓存(Maven 等) | 可删,唯一代价是下次构建回冷、首跑变慢 |
| `sandbox_archives` | backend `/app/archives`(读写)、sandbox-runner 只读 | 工作区归档交接(backend 唯一生产者,runner 消费) | **不要手工清**,归档有自动生命周期,见 §3;手工删除正在交接的归档会让沙箱作业解析不到文件 |

清理边界的一条硬规则:**除 `postgres_data` 外全部可重建**;而 `postgres_data` 的重建路径只有一条——从备份恢复(§4)。

## 3. 工作区归档:WorkspaceArchiveService 的既有职责

`sandbox_archives` 卷不靠人工维护,backend 的 `WorkspaceArchiveService` 是它的唯一生产者与生命周期管理者(职责已在类头注释成文):

- **产出**:派发沙箱作业前落盘归档(Agent 取证归档 = head 树 + 预置 base→head diff;补丁验证归档 = head 树 + 候选补丁),命名含 runId+sha,天然幂等可重试。
- **就地清理**:正常完成的 Run 在发布步骤即清掉自己的归档。
- **保留例外**:FAILED / TIMED_OUT 的 Run 保留归档,给运维 `reopenForRetry` 续跑用。
- **TTL 兜底**:`@Scheduled` 每 15 分钟清扫一轮,删除超龄文件(TTL 配置 `app.sandbox.archive-ttl`,默认 6 小时),兜住崩溃残留与清理失败,防共享卷膨胀。清扫随 `app.agent.scheduling.enabled` 开关生效(与 Outbox 排空、恢复 watchdog 同一开关)。

运维含义:磁盘上看到 `sandbox_archives` 里有文件是正常态(最多滞留约 6 小时),持续膨胀才是异常(先查调度开关是否打开、backend 日志里的清扫告警)。

## 4. PostgreSQL 备份与恢复

### 4.1 日常备份

用既有脚本(逻辑备份,pg_dump 走容器,客户端与服务端版本天然一致):

```bash
deploy/backup.sh                  # 备份到 deploy/backups/,自定义格式(-Fc)
BACKUP_KEEP=30 deploy/backup.sh   # 保留最近 30 份(缺省 14 份,滚动删除)
```

脚本自带完整性初检(校验 PGDMP 魔数,空文件/错误输出立即失败删除)。`deploy/backups/` 已被 gitignore,备份产物是业务数据,不得入库。

### 4.2 恢复

```bash
# 先确认备份可读(列出内容清单)
docker compose exec -T postgres pg_restore --list < deploy/backups/code_review-<时间戳>.dump

# 恢复到运行中的 postgres(--clean 先删已存在对象,--if-exists 容忍空库)
docker compose exec -T postgres pg_restore -U code_review -d code_review \
    --clean --if-exists < deploy/backups/code_review-<时间戳>.dump

# 恢复后重启 backend,让连接池与缓存回到干净状态
docker compose restart backend
```

恢复的前提仍是 §1 的关键前提:同一份 `TOKEN_ENCRYPT_KEY`。换了密钥,库里加密的 SCM 凭据全部作废,需要重新录入。

完整服务器操作语境(含手工一次性 pg_dump 纯 SQL 备份)见 `docs/12_服务器部署与演示手册.md` 「11. 备份与恢复」。

## 5. ai_call_log 留存口径

`ai_call_log` 表是 AI 调用的逐条审计账(请求类型、provider、模型、prompt/响应字符数、token 三项、时延、状态、截断后的错误信息)。两点写实说明:

1. **只存元数据,不存内容**:prompt 与模型响应正文不落这张表,单行只有几百字节,不含代码内容,敏感面低。
2. **当前没有时间型清理任务**(未实施,如实标注):留存策略是"跟随宿主实体"——删项目时由 `ProjectCleanupService` 以 `deleteByProjectId` 级联清掉,删单个审查任务时由 `ReviewService.deleteTask` 以 `deleteByTaskId` 清掉;不删项目/任务则日志一直留存。

量级核算:一次完整审查/Agent Run 产生几十行,演示与答辩周期累计万行级,对 PostgreSQL 是零负担——这是"不做 TTL"的依据,不是疏漏。若未来进入长期多项目运行形态,加一个按 `createdAt` 的定期清理任务即可(与 §3 的 TTL 清扫同款模式),届时再实施。

聚合视图走 Micrometer(`reposage.ai.review` / `reposage.ai.tokens`,Grafana 看板已接),明细核账才查这张表,两者分工见 `AiMetrics` 类头注释。

## 6. 消息与死信

RabbitMQ 队列不备份:正常消息消费即焚;耗尽重试的消息进死信队列(`code.review.dead.queue` / `agent.dead.queue` / `sandbox.dead.queue`)等人工处理,死信非零会触发告警(`deploy/observability/alerts.yml` 的 `DeadLetterQueueNotEmpty`)。死信的语义、排查与重放流程见 `docs/04_MQ与异步任务设计.md`。

## 7. 容器日志与观测数据

- **容器日志**:无采集侧车,json-file 就地留存,每服务 3 个 10m 分片封顶(compose 顶部 `x-logging` 锚点),整栈(11 个服务)上限约 330m,滚动覆盖、无需人工清理。要留证据(如演示实跑记录)需主动 `docker compose logs <svc> > 文件` 导出。
- **观测数据**:Prometheus 指标历史、Alertmanager 静默/通知账、Grafana 的 UI 态改动都不挂持久卷,容器重建即清零。看板与数据源由 provisioning 文件重建,这是刻意取舍(演示栈要的是"当下可见",不是历史留存);需要长期指标时再给 prometheus 挂 TSDB 卷,见 `deploy/observability/README.md`。
