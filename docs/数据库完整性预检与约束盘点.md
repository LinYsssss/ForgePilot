## 一、为什么先出这份文档而不是直接写迁移

整改方案 Phase 4.2 明确要求：

> 迁移前为每一条候选约束执行孤儿数据和交叉归属查询，并把查询结果保存为验收证据；发现脏数据先备份、修复，再添加约束，**不能直接让 Flyway 在答辩环境启动失败**。

当前工作机**没有任何方式可以执行 Flyway 迁移**：

- 没有 Docker（`docker` 命令不存在），Testcontainers 全部 skipped；
- 没有本地 PostgreSQL；
- `V1__baseline_schema.sql` 第 1 行是 `create extension if not exists vector`，**H2 无法运行**，所以整条迁移链在 H2 上也跑不起来。

由此产生一个必须记录在案的事实：

> **V19、V20、V21 三个迁移至今从未被任何数据库真正执行过。**
> 后端测试通过是因为 dev/test 用 H2 + `spring.jpa.hibernate.ddl-auto=create-drop` 从实体建表，`spring.flyway.enabled=false`，**完全绕过 Flyway**。唯一会执行迁移的 `LegacySchemaMigrationIntegrationTest` 标注了 `@Testcontainers(disabledWithoutDocker = true)`，属于那 3 个 skipped 测试之一。

因此这三个迁移目前只有"语法上看着对"的把握，没有执行证据。在此基础上再盲写三个**加约束**的迁移，风险等级完全不同：加列失败最多是启动报错，加约束失败会在有数据的库上直接卡住 Flyway。

**结论：V22~V24 推迟到能执行迁移之后再写。** 本文件先交付不依赖数据库的部分——盘点表、预检脚本、唯一约束业务规则复核。

## 三、候选约束表（V22 目标）

删除语义按整改方案的规则确定：**聚合根默认 RESTRICT；明确从属且允许随父清理的用 CASCADE；审计与证据链优先 RESTRICT 或 SET NULL，禁止无意识级联删除**。

| # | 约束 | 现状 | 目标删除语义 | 理由 |
|---|---|---|---|---|
| 1 | project.owner_id → user_account.id | 缺失 | RESTRICT | 用户是聚合根，删用户不应静默带走项目 |
| 2 | code_repository.project_id → project.id | 缺失 | CASCADE | 仓库绑定明确从属于项目 |
| 3 | pull_request.project_id → project.id | 缺失 | CASCADE | 同上 |
| 4 | pull_request.repository_id → code_repository.id | 缺失 | CASCADE | 同上 |
| 5 | knowledge_document.project_id → project.id | 缺失 | CASCADE | 知识库随项目消亡 |
| 6 | knowledge_document.uploader_id → user_account.id | 缺失 | **SET NULL** | 上传者是审计信息，删用户不应删文档 |
| 7 | knowledge_chunk.project_id → project.id | 缺失 | CASCADE | document_id 已有 FK |
| 8 | review_task.project_id → project.id | 缺失 | CASCADE | |
| 9 | review_task.repository_id → code_repository.id | 缺失 | CASCADE | |
| 10 | review_task.trigger_user_id → user_account.id | 缺失 | **SET NULL** | 触发人是审计信息 |
| 11 | review_task.pull_request_id → pull_request.id | 缺失 | SET NULL | PR 可能被清理，任务记录应保留 |
| 12 | review_report.task_id → review_task.id | 缺失 | CASCADE | |
| 13 | review_issue.report_id → review_report.id | 缺失 | CASCADE | |
| 14 | feedback.issue_id → review_issue.id | 缺失 | CASCADE | |
| 15 | feedback.user_id → user_account.id | 缺失 | **RESTRICT** | 反馈是用户产出的证据 |
| 16 | mq_task_log.task_id → review_task.id | 缺失 | **RESTRICT** | 审计日志，禁止随任务级联消失 |
| 17 | ai_call_log.project_id → project.id | 缺失 | **RESTRICT** | 同上，含成本与调用证据 |
| 18 | ai_call_log.task_id → review_task.id | 缺失 | **SET NULL** | 同上 |
| 19 | approval_request.user_id → user_account.id | 缺失 | **RESTRICT** | 审批是责任链证据 |
| 20 | agent_run.project_id / repository_id / review_task_id | 待核 | 逐项确认 | V3 可能已建部分 |

**范围边界**：`scm_installation`、`scm_webhook_delivery` 两张表的约束**不在 V22 内**，归 Track B 的 V25 —— B 的 Webhook 原子幂等依赖那里的唯一键，必须与 B 的代码同批提交。（另注：`UQ_SCM_DELIVERY_PROVIDER_DELIVERY` 唯一索引**已经存在**，B 大概率不需要新建。）

**交叉归属风险**：只加外键**防不住**"task 属于 A 项目、repository 属于 B 项目"这类错误。第 8/9、3/4、17/18 条都存在这个问题，需要在 Service 层校验或用复合唯一键 + 复合外键。这一项单独列入 V22 的设计决策，不能靠 FK 蒙混过去。

## 五、唯一约束业务规则复核（不成立就不加）

整改方案要求"唯一约束必须以业务规则为前提再添加……规则不成立时不得为看起来规范而盲目加唯一键"。逐条结论：

| 候选唯一键 | 结论 | 依据 |
|---|---|---|
| code_repository (project_id) | **需确认** | `CodeRepositoryJpaRepository.findByProjectId` 返回 `Optional`，暗示一项目一仓库；但要确认产品是否允许多仓库，否则加了就锁死演进 |
| pull_request (repository_id, external_number) | 倾向成立 | 外部 PR 号在单仓库内唯一是平台语义 |
| scm_webhook_delivery (provider, delivery_id) | **已存在** | `UQ_SCM_DELIVERY_PROVIDER_DELIVERY`；归 Track B |
| scm_installation (provider, external_installation_id) | **已存在** | `UQ_SCM_INSTALLATION_PROVIDER_EXTERNAL`；归 Track B |
| agent_step (agent_run_id, sequence_no) | **已存在** | 实体上 `uq_agent_step_sequence` |
| agent_outbox_event (event_key) | **已存在** | `uq_agent_outbox_event_key` |
| review_task (project_id, repository_id, commit_id, base_commit_id_normalized, branch_name) | **已存在** | 实体上已有 |

净新增候选只有前两条，且第一条必须先问清产品语义。

## 六、CHECK 约束候选（V23 目标）

优先覆盖：`role`、`status`、`provider`、`severity`、`confidence` 落在 0~1、`retry_count >= 0`、`line_start`/`line_end` 为正数且有序。

注意：这些列当前多为 `varchar`，加 CHECK 前必须先跑一遍**实际取值分布**（`select distinct status, count(*) from ... group by 1`），否则历史数据里的意外取值会让迁移失败。这条同样属于预检范围。

## 七、放行条件

V22~V24 必须在同时满足以下条件后才编写并提交：

1. 有可执行 Flyway 的 PostgreSQL 环境（Docker Desktop 或本地 PG + pgvector）；

4. 第六节取值分布已跑过；
5. V19~V21 已在真实 PostgreSQL 上成功执行一次，证明现有迁移链本身是好的；
6. 迁移在副本上演练，记录耗时与锁影响，并准备好备份与前向修复预案。

在此之前，本项在验收材料中一律记为**未验证**，不得写成通过。
