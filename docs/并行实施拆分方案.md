## 一、切割轴与拆分原则

原方案是按"风险类型"分阶段（可靠性 → 安全 → 数据 → 前端 → 交付），阶段之间存在文件交叉。并行化必须换一条轴：**按代码所有权切**，而不是按阶段切。

最终切割轴：

| | Track A | Track B |
|---|---|---|
| 名称 | 内核可靠性与业务数据线 | 安全边界与交付线 |
| 边界 | 后端**业务层**：Agent 执行闭环、事务、数据库、分页、对象级授权应用 | 后端**安全基础设施与外部边界** + Model Service + 前端 + 部署/CI |
| 心智模型 | "请求进来之后，系统内部做对了吗" | "谁能进来、能出去到哪、怎么交付出去" |
| 对应原方案 | Phase 1、Phase 2、Phase 4（含 4.1/4.2/4.3/4.4）、P0-05、P0-09(A侧) | Phase 3、Phase 5、Phase 6、P0-06/07/08/10 |
| 预估工期 | 4.5～6 天 | 4～6 天 |

三条硬规则：

1. **文件所有权唯一**：每个文件只有一条线可以修改。表格未列出的文件默认冻结，需要改就走跨线协商。
2. **Flyway 版本号预分配**：A 用 V19～V24，B 用 V25～V29。跨段使用视为违规。
3. **契约先冻结再并行**：Phase 0 产出的 4 份契约提交后即冻结，双方只消费不修改。

## 二、Phase 0：共同前置（必须串行完成，约 2～3 小时）

**这一步不能并行，必须一个人做完并推送后，两条线才能开工。** 它的唯一目的是把所有共享文件一次性改完、冻结，之后两条线永不相遇。

### 0.2 拆分 application.yml（消除最大冲突源）

现状：`backend/src/main/resources/application.yml` 154 行，`app:` 子树（第 57～154 行）包含 12 个块，两条线都要改。

动作：用 `spring.config.import` 拆成两个独占文件。

~~~yaml
# application.yml 保留：spring / server / logging / management / resilience4j
spring:
  config:
    import:
      - optional:classpath:config/app-agent.yml
      - optional:classpath:config/app-boundary.yml
~~~

| 新文件 | 迁入的 app 子键 | 所有者 |
|---|---|---|
| `resources/config/app-agent.yml` | `agent`、`review`、`rag`、`ai`、`notify` | **A 独占** |
| `resources/config/app-boundary.yml` | `git`、`ratelimit`、`security`、`http`、`sandbox`、`scm`、`model-service` | **B 独占** |

`application-dev.yml` / `application-prod.yml`（36 / 33 行）暂不拆，**Phase 0 阶段一次性把两条线预计要用的 profile 键位加成占位值**，之后冻结；若必须改，走协商。

验收：拆完后 `mvn -s .mvn/settings.xml verify` 仍为 304 tests 通过、3 skipped。**配置拆分不允许附带任何行为变更。**

### 0.3 预分配 Flyway 版本段

| 段 | 归属 | 计划用途 |
|---|---|---|
| V19 ～ V24 | **A** | V19 outbox 投递护栏、V20 step 执行租约、V21 引用完整性、V22 CHECK 约束、V23 查询索引、V24 备用 |

### 0.4 冻结四份跨线契约

Phase 0 必须把下面 4 个文件建好并提交，**内容此后冻结**：

**契约 1 — 统一分页响应**（`common/api/PageResponse.java`，新增）

~~~java
public record PageResponse<T>(List<T> items, int page, int size,
                              long totalElements, int totalPages) {}
~~~

默认 size=20，最大 100，排序字段白名单。A 负责后端所有分页接口改造，B 负责前端按此形状适配。**B 不需要等 A 完成**——契约已定，可直接写前端。

**契约 2 — 统一错误响应 + 完整错误码枚举**（`common/exception/`）

~~~json
{ "code": "AGENT_OUTBOX_PUBLISH_FAILED", "message": "任务暂时无法调度，请稍后重试",
  "traceId": "...", "data": null }
~~~

Phase 0 必须**一次性把 A、B 双方所需的错误码全部定义完**（含 A 的 `*_NOT_FOUND`/`*_CONFLICT`/`AGENT_*`，B 的 `AUTH_*`/`CSRF_*`/`RATE_LIMITED`/`OUTBOUND_URL_REJECTED`/`WEBHOOK_SIGNATURE_INVALID` 等）。之后 `GlobalExceptionHandler.java` 归 **A 独占**，B 只消费不改；B 若临时需要新错误码，口头协商后由 A 追加。

**契约 3 — 对象级授权门面**（`common/security/ProjectAuthorization.java`，新增接口 + 实现）

~~~java
void requireRead(Long projectId, Long userId);   // 无权 → 403
void requireWrite(Long projectId, Long userId);
~~~

Phase 0 建好后归 **B 所有**（属安全基础设施），但 **A 负责把它应用到自己的每个 controller**。B 承诺：方法签名冻结，不做破坏性变更。

**契约 4 — CSRF 开关位**（`app-boundary.yml`）

~~~yaml
app.security.csrf.enabled: false   # Phase 0 占位，开发期两线均保持 false
~~~

**这是防止两条线互相打断的关键**。B 的 SPA CSRF 一旦生效，A 所有 MockMvc 非 GET 测试会立即 403。约定：B 在自己分支内可置 true 做测试，但**合入集成分支时必须回落 false**，由合流阶段统一打开并跑全量回归。

### 0.5 一次性补齐 pom.xml 依赖

`pom.xml` 由 **B 独占**，但 Phase 0 阶段就把两条线预计要用的依赖全部加齐并提交：Caffeine（B 的 ReplayGuard TTL 缓存）、OWASP dependency-check-maven（B 的供应链门禁）、Testcontainers 相关（A 的集成测试）。避免 A 中途要加依赖时被迫改 B 的文件。

### 0.6 Phase 0 退出条件

- `git status --short --branch` 干净，四组未跟踪 Demo 文件完好；
- `mvn -s .mvn/settings.xml verify` = 304 tests / 0 fail / 3 skipped（与基线一致）；
- 4 份契约文件已提交，两条 track 分支已从同一提交点切出。

### 5.1 Phase 0 之后仍存在的接触面（共 4 处，全部已定契约）

### 5.2 跨线协商流程

任何一方发现必须修改对方文件时：**不要直接改**。在 `docs/跨线协商.md` 追加一条（时间、需求方、目标文件、原因、期望改动），由所有者在自己分支实现并推送，需求方 rebase 后继续。这比事后解冲突便宜得多。

### 5.3 每日同步动作（两条线各自执行）

~~~powershell
git fetch origin
git rebase origin/fix/defense-hardening   # 或对应集成分支
mvn -s .mvn/settings.xml verify           # 确认自己这条线仍绿
~~~

Track A 与 Track B **互不 rebase 对方分支**，只以集成分支为共同基准。

### 5.4 已知的"看起来冲突但实际不冲突"

- `config/` 目录两条线都会进入，但 A 只碰 `RabbitMqConfig.java`，B 碰其余 5 个文件 —— 目录相同、文件不同，git 不冲突；
- `db/migration/` 目录共享，但版本段预分配，文件名不重叠；
- `backend/src/test/.../support/IntegrationTestContainers.java` 是**共享测试基础设施**，Phase 0 后冻结。若 A 的 Testcontainers 集成测试需要扩展它，走 5.2 协商（B 是所有者）。

## 六、合流与集成阶段（双线完成后，1～2 天）

**顺序不可颠倒**：

1. **A 先合入集成分支**（内核可靠性是地基，且 A 拥有 `GlobalExceptionHandler`），跑全量 `mvn verify`；
2. **B 再合入**，跑全量 `mvn verify` + `sandbox-runner mvn test` + 前端 `npm ci && npm test && npm run build`；
3. **打开 CSRF 开关** `app.security.csrf.enabled=true`，跑全量回归。此时会暴露 A 遗留的未带 CSRF 的 MockMvc 写测试 —— 这是**预期内的一次性集中修复**，由合流负责人统一处理，不是返工；
4. 跑一次完整授权反向测试矩阵，确认 A、B 双方的 ID 型资源都被覆盖；
5. 进入原方案 **Phase 7**：Docker 动态验收、Testcontainers 三个 skipped 转实跑、Compose smoke、镜像扫描、备份恢复演练、文档同步。

**Phase 7 不拆分并行**——它是全局验收，必须在统一的集成分支上一次性完成。

## 十、风险提示

1. **Phase 0 偷懒的代价最大**。如果跳过 `application.yml` 拆分或不预分配 Flyway 版本段，两条线大约在第 2 天就会开始持续解冲突，并行收益会被抵消掉。
2. **CSRF 开关必须遵守**。B 在自己分支置 true 后忘记回落，会导致 A 合入后大面积 403，误判为 A 的 bug。
3. **A 的工期风险高于 B**。A1+A2 是整个项目最难的两块（分布式租约 + 事务重构），若超期，可把 A5（DB 完整性）降级到合流后处理，不影响 P0 闭环。
4. **两条线的 JaCoCo 阈值**。原方案要求 line ≥ 70%、branch ≥ 50%，但这是**全局指标**，单条分支上可能因新增未测代码而暂时下探。约定：各线自查不低于基线（71.2% / 51.9%），最终以集成分支为准。
