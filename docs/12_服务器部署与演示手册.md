# 服务器部署与演示操作手册

## 1. 部署目标

本手册用于把 ForgePilot 部署到一台云服务器上，形成可访问、可演示、可排障的完整环境。

最终对外入口：

- 前端页面：`http://服务器IP/`
- 后端健康检查：`http://服务器IP/actuator/health`
- RabbitMQ 管理台：`http://服务器IP:15672`

部署后的服务组成：

```mermaid
flowchart TB
    User["浏览器"] --> Nginx["Nginx :80"]
    Nginx --> Frontend["Vue 静态页面"]
    Nginx --> Backend["Spring Boot :8080"]
    Backend --> Postgres["PostgreSQL + pgvector"]
    Backend --> Rabbit["RabbitMQ"]
    Backend -.可选.-> LLM["OpenAI-compatible 大模型 API"]
    Backend --> Git["Git 仓库或演示仓库目录"]
    Rabbit --> TaskQ["code.review.task.queue"]
    Rabbit --> DeadQ["code.review.dead.queue"]
```

## 2. 推荐服务器配置

| 项目 | 建议 |
| --- | --- |
| 系统 | Ubuntu 22.04 / 24.04 LTS |
| CPU | 2 核及以上 |
| 内存 | 4 GB 及以上 |
| 磁盘 | 40 GB 及以上 |
| 开放端口 | `80` 必需，`15672` 可选 |
| 网络 | 能拉取 Docker 镜像，能访问 Git 仓库 |

学生展示建议选择 4 GB 内存。2 GB 服务器也能尝试，但建议使用 `AI_PROVIDER=mock`，并在演示前提前构建镜像。

## 3. 代码侧已补强点

这次部署前已针对审查发现的问题做了加固：

- 生产环境启动时执行 `backend/src/main/resources/db/schema-postgres.sql`，自动创建业务表和 pgvector 表。
- 生产环境仍使用 `spring.jpa.hibernate.ddl-auto=validate`，避免 Hibernate 随意改表。
- MQ/AI 失败时任务状态独立提交，方便在服务器排障。
- 删除 RAG 文档时同步清理 pgvector 向量表。
- 同一 commit 支持按不同 `baseCommitId` 和分支重新审查。
- HTTPS 私有仓库 token 已用于 Git clone/fetch/pull 的认证头。
- 前端演示仓库路径改为可通过 `VITE_DEMO_REPO_PATH` 配置。

## 4. 首次部署

### 4.1 安装 Docker

在 Ubuntu 上可按下面步骤准备运行环境：

```bash
sudo apt update
sudo apt install -y ca-certificates curl git
curl -fsSL https://get.docker.com | sudo sh
sudo usermod -aG docker $USER
```

重新登录 SSH 后检查：

```bash
docker --version
docker compose version
git --version
```

### 4.2 获取项目代码

推荐通过 Git 获取：

```bash
git clone https://github.com/LinYsssss/reposage.git
cd reposage
```

如果仓库是私有的，clone 时需要认证。用 GitHub Personal Access Token（PAT）：

```bash
git clone https://<你的GitHub用户名>:<你的PAT>@github.com/LinYsssss/reposage.git
cd reposage
```

> PAT 在 GitHub「Settings → Developer settings → Personal access tokens」生成，至少勾选 `repo` 读取权限。

确认目录中存在：

```bash
ls backend frontend deploy demo-repos
```

初始化内置演示仓库：

```bash
bash scripts/init-demo-repos.sh --verify
```

说明：GitHub 不会把嵌套目录里的 `.git` 目录当普通文件上传。这个脚本会在服务器上把
`demo-repos/` 下的**三个**演示仓库（`mall-order-service`、`payment-settlement-service`、
`tenant-user-center`）分别初始化成可被后端 clone 的本地 Git 仓库，并各自重建一条 PR 分支
（`feature/promotion-batch-ship`、`feature/instant-settlement`、`feature/ops-console`）。
脚本是幂等的，已初始化时会自动跳过。

`--verify` 会把重建出的 6 个 ref（3 个 `main` + 3 个 PR 分支）与 `scripts/demo-repos-expected-sha.txt`
里钉死的 SHA 逐条比对，六条全中才退出 0 —— 这是确认服务器上的素材没被改动过的最快方式。
PowerShell 环境用 `pwsh -File scripts/init-demo-repos.ps1 -Verify`。若上一次运行中途失败留下
半成品仓库，脚本只看 `.git` 在不在、会直接跳过，需要先 `rm -rf demo-repos/*/.git` 再重跑。

> **重要**：服务器拉到的是 GitHub 上的代码。请确保本地改动（文档、`RagService`、`application.yml`、`deploy/.env.example` 等）已 `git push` 到 GitHub，否则服务器跑的仍是旧版本。

### 4.3 配置环境变量

进入部署目录并复制配置：

```bash
cd deploy
cp .env.example .env
nano .env
```

最低可演示配置如下：

```env
APP_ENV=prod
SERVER_PORT=8080

DB_URL=jdbc:postgresql://postgres:5432/code_review
DB_USERNAME=code_review
DB_PASSWORD=change-me-to-a-strong-db-password

RABBITMQ_HOST=rabbitmq
RABBITMQ_PORT=5672
RABBITMQ_USERNAME=reposage
RABBITMQ_PASSWORD=change-me-to-a-strong-rabbit-password

JWT_SECRET=change-me-to-a-long-random-string
TOKEN_ENCRYPT_KEY=change-me-to-another-long-random-string

REVIEW_INLINE=false
RAG_MODE=memory
RAG_FULL_CONTEXT=true

VITE_DEMO_REPO_PATH=/app/demo-repos/mall-order-service

AI_PROVIDER=openai-compatible
LLM_BASE_URL=https://token-plan-cn.xiaomimimo.com/v1
LLM_API_KEY=replace-with-your-mimo-key
LLM_CHAT_MODEL=mimo-v2.5-pro
EMBEDDING_PROVIDER=mock
```

说明：

- `AI_PROVIDER=openai-compatible`：调用真实大模型，需要设置 `LLM_BASE_URL`、`LLM_API_KEY`、`LLM_CHAT_MODEL`。本例使用小米 MiMo。
- `AI_PROVIDER=mock`：不依赖外部大模型，用规则引擎模拟审查，适合无 Key 时演示。
- `RAG_FULL_CONTEXT=true`：启用全量注入，把项目全部知识库文档喂给大模型，**不需要 embedding**。MiMo 等只提供聊天接口的服务正适用。
- `EMBEDDING_PROVIDER=mock`：上传文档时向量用本地占位，不参与审查决策（全量注入模式下向量不参与检索）。
- 仅当改用向量检索（`RAG_FULL_CONTEXT=false` + `RAG_MODE=pgvector`）且需真实语义检索时，才设 `EMBEDDING_PROVIDER=openai-compatible` 并配置 `EMBEDDING_BASE_URL`、`EMBEDDING_API_KEY`、`LLM_EMBEDDING_MODEL`。
- `REVIEW_INLINE=false`：走 RabbitMQ 异步审查，更能体现消息队列。
- `VITE_DEMO_REPO_PATH=/app/demo-repos/mall-order-service`：前端“填入演示仓库”按钮会填这个容器内路径。

**上线前必须改掉的项**（不要用模板默认值）：

- `DB_PASSWORD`、`RABBITMQ_PASSWORD`：数据库和 MQ 密码。
- `JWT_SECRET`、`TOKEN_ENCRYPT_KEY`：登录签名密钥和 Git token 加密密钥。
- `LLM_API_KEY`：填你**重新生成的** MiMo Key（旧 Key 若曾泄露请先在 MiMo 后台吊销）。

生成强随机字符串：

```bash
openssl rand -hex 32
```

### 4.4 放行端口

云服务器需要在**安全组 / 防火墙**放行：

- `80`：必需，前端和 API 入口。
- `15672`：可选，RabbitMQ 管理台（仅演示时临时开放，结束后建议关闭）。

> 阿里云/腾讯云等在控制台「安全组」配置；若服务器自身开了 ufw，执行 `sudo ufw allow 80`。

在 `deploy` 目录执行：


```bash
docker compose ps
```

预期看到这些服务为 `running` 或 `healthy`：

- `postgres`
- `rabbitmq`
- `backend`
- `frontend`
- `nginx`

## 6. 演示操作流程

```mermaid
flowchart LR
    A["打开 http://服务器IP/"] --> B["注册/登录"]
    B --> C["创建项目"]
    C --> D["进入仓库页"]
    D --> E["点击填入演示仓库"]
    E --> F["绑定仓库并加载 Commit"]
    F --> G["进入知识库页上传 12 份知识文档"]
    G --> H["测试 RAG 检索"]
    H --> I["填入 PR 分支 HEAD 并触发审查"]
    I --> J["RabbitMQ 消费任务"]
    J --> L["RAG 上下文 + AI 审查"]
    L --> M["查看报告/AI日志/MQ日志"]
    M --> N["提交人工反馈"]
```

具体步骤：

1. 打开 `http://服务器IP/`。
2. 注册账号，例如 `developer / 123456`。
3. 创建项目：`mall-order-service`，默认分支 `main`。
4. 进入“仓库”，点击“填入演示仓库”，再点击“绑定仓库”。
5. 点击“加载 Commit”，能看到 `main` 上的两个提交。**审查目标不要选最新的那个** —— 缺陷全部在 PR 分支上，`main` 的 HEAD（mall 是 `6977028`）只是知识文档提交，审它得到的是没有代码变更的 diff，报告自然没有风险。而 `listCommits` 只列绑定分支的提交，PR 分支的提交不会出现在这个列表里。正确做法二选一：
   - **直接填 SHA**（演示最省事）：第 8 步的「Commit ID」填 PR 分支 HEAD，mall 是 `e205e0e`；Base Commit 留空即可 —— 它的父提交正是 `main` 的 HEAD，diff 就是完整的 PR 内容。
   - **走 PR 导入**（对应测试方案 M4）：`POST /api/projects/{id}/pull-requests` 建 PR（base=`main`，head=PR 分支 HEAD），再 `POST .../pull-requests/{id}/review-task`，审查范围是 `base..head`。
6. 进入“知识库”，上传该项目的 12 份 `.md`：`demo-repos/mall-order-service/docs/` 下 4 份 + `demo-repos/knowledge-shared/` 5 份（通用规范）+ `demo-repos/knowledge-noise/` 3 份（干扰文档，用于检验检索排序）。等状态全部变为 `INDEXED` 再往下走。只做冒烟可先传 `docs/security-policy.md` 一份，但那样跑不出 `docs/演示素材与缺陷对照表.md` 第五节的三档对照。
7. 输入问题，例如 `admin endpoint authorization and paid order shipping rule`，点击测试检索。
8. 进入“审查”，按第 5 步填好 Commit ID，勾选刚上传的知识文档，触发审查任务。
9. 刷新报告，查看 `AUTH_RISK`、业务规则风险等问题。**这是 `AI_PROVIDER=openai-compatible`（4.3 节 `.env` 的默认值）下的预期。** 若因 2 GB 内存或现场网络/余额不稳而切回 `AI_PROVIDER=mock`，规则引擎对这份 diff 只会产出 **1 条 `SQL_INJECTION`**（对应对照表 M5，且证据字段不引用知识库）—— 那是 mock 的正常表现，不是链路故障，机理见 `docs/11_本地开发与联调手册.md` 第 9 节的说明。
10. 查看 AI 日志，应能看到 `CHAT_REVIEW` 等记录（文档上传时还会有 `EMBEDDING_INDEX`；向量检索模式下审查会有 `EMBEDDING_SEARCH`）。
11. 查看 MQ 日志，生产模式下应能看到 `PUBLISHED`、`CONSUMED` 等记录。
12. 对 issue 提交“真实问题/误报/需要讨论”反馈。

## 7. 真实大模型切换

只接入聊天模型（如小米 MiMo，无 embedding 接口），用全量注入，将 `.env` 改为：

```env
AI_PROVIDER=openai-compatible
LLM_BASE_URL=https://token-plan-cn.xiaomimimo.com/v1
LLM_API_KEY=你的key
LLM_CHAT_MODEL=mimo-v2.5-pro
EMBEDDING_PROVIDER=mock
RAG_FULL_CONTEXT=true
```

如果你的服务同时支持 OpenAI 兼容 embedding，且想用向量检索（适合知识库很大时），可改为：

```env
AI_PROVIDER=openai-compatible
LLM_BASE_URL=https://你的聊天模型服务/v1
LLM_API_KEY=你的聊天key
LLM_CHAT_MODEL=你的chat模型
RAG_FULL_CONTEXT=false
RAG_MODE=pgvector
EMBEDDING_PROVIDER=openai-compatible
EMBEDDING_BASE_URL=https://你的embedding服务/v1
EMBEDDING_API_KEY=你的embedding-key
LLM_EMBEDDING_MODEL=你的embedding模型
```

重启后端：

```bash
docker compose up -d --build backend
docker compose logs -f backend
```

注意：

- 真实 embedding 维度和已入库 mock embedding 不一致时，建议清空旧知识库后重新上传文档。
- 答辩现场如果网络或余额不稳定，切回 `AI_PROVIDER=mock` 即可继续演示。

## 8. 私有仓库绑定

支持 HTTPS 仓库 token：

1. 在前端仓库页填写 HTTPS 仓库地址。
2. `Provider` 可填 `GITHUB`、`GITLAB`、`GITEE` 或 `OTHER`。
3. `accessToken` 填个人访问令牌。
4. 后端会 AES-GCM 加密存储 token，接口不返回明文。
5. clone/fetch/pull 时会自动通过 Git HTTP Header 带上 token。

建议答辩前优先使用公开仓库或内置演示仓库，私有仓库作为增强能力说明。

## 11. 备份与恢复

日常备份用脚本(逻辑备份 + 保留最近 14 份,`BACKUP_KEEP` 可调):

```bash
deploy/backup.sh                 # 产物在 deploy/backups/code_review-<时间戳>.dump
BACKUP_KEEP=30 deploy/backup.sh  # 保留 30 份
```

建议放进 crontab(每天凌晨 3 点):

```bash
0 3 * * * cd /root/reposage && deploy/backup.sh >> /var/log/reposage-backup.log 2>&1
```

三件事必须知道:

1. **dump 不含密钥。** 数据库里的 SCM 凭据、webhook 密钥是用 `deploy/.env` 的
   `TOKEN_ENCRYPT_KEY` 加密的;只有 dump、没有 `.env` 恢复不出可用系统。
   `.env` 走单独安全渠道保管(不在仓库、不放备份目录)。
2. **备份目录已被 gitignore**(`deploy/backups/`),里面是业务数据,不得入库。
3. 需要备份的**只有 PostgreSQL**:RabbitMQ 队列是瞬态的,sandbox 工作卷可重建。

恢复(空库或新卷上):

```bash
# 先确认备份可读(列出内容清单)
docker compose exec -T postgres pg_restore --list < deploy/backups/code_review-<时间戳>.dump

# 恢复到运行中的 postgres(--clean 先删已存在对象,--if-exists 容忍空库)
docker compose exec -T postgres pg_restore -U code_review -d code_review \
  --clean --if-exists --no-owner < deploy/backups/code_review-<时间戳>.dump

# 恢复后重启 backend,让连接池与缓存回到干净状态
docker compose restart backend
```

手工一次性备份仍可用 `pg_dump`(纯 SQL 格式,便于肉眼检查):

```bash
docker compose exec postgres pg_dump -U code_review code_review > reposage_backup.sql
```

## 12. 常见问题

| 问题 | 可能原因 | 处理方式 |
| --- | --- | --- |
| 前端打不开 | Nginx 未启动或安全组未开放 80 | `docker compose logs nginx`，检查云服务器安全组 |
| 后端 health 不是 UP | 数据库、RabbitMQ、配置错误 | `docker compose logs backend --tail=200` |
| 后端启动时报缺表 | schema 初始化未执行或 DB 权限不足 | 检查 `APP_ENV=prod`、`DB_USERNAME` 是否有建表权限 |
| 审查任务一直 PENDING | RabbitMQ 未消费或 backend 未连接 MQ | 看 RabbitMQ UI 和 `mq_task_log` |
| 审查任务 FAILED | Git、RAG 或 AI 调用失败 | 前端查看任务错误、AI 日志、后端日志 |
| 知识库检索为空 | 未上传文档、embedding 不一致 | 重新上传文档，真实模型模式下避免混用旧 mock 向量 |
| 私有仓库 clone 失败 | Token 权限不足或仓库地址不对 | 先用服务器 `git clone` 验证 token 权限 |
| 服务器内存不足 | 构建或多个服务占用过高 | 增加 swap，或先在本地构建镜像再部署 |

## 14. P8 双路径演示与离线彩排

ForgePilot 的答辩演示保留两条路径，二者都走真实 webhook 验签；离线模式只替换依赖，不关闭安全边界。

### 14.1 在线 webhook 路径

在已部署并完成 SCM installation 绑定的环境中，使用真实 installation secret 注入固定的 pull request payload：

```powershell
$env:SCM_WEBHOOK_SECRET = '<out-of-band-secret>'
pwsh -File scripts/rehearse-webhook.ps1 `
  -BaseUrl 'https://<server>' `
  -WebhookSecret $env:SCM_WEBHOOK_SECRET `
  -AdminUser '<seed-admin>' `
  -AdminPassword '<password>' `
  -EvidencePath '.trellis/tasks/08-17-p8-experiment-defense/rehearsal-online-2026-08-18.md'
```

### 14.3 证据与限制

- 证据文件只保留 payload SHA-256、delivery id、HTTP 状态、run 状态、gate verdict、步骤状态和 commit SHA，不保留 secret。
- 在线结果与离线结果分开记录；离线结果不得进入 38 例真实模型实验矩阵。
- 演示素材中的缺陷是刻意植入的验证素材，能力表述必须引用已落档的评测或彩排证据，不承诺 AI 全部命中。
