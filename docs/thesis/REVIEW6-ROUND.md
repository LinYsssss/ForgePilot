# review-6 线上一轮：38 个开放 PR 的重审、逐条判定与人工闭环

本文记录 2026-11-15/16 在生产部署（提交 `811b7e7`，提示词版本 `review-6`）上对全部 38 个开放 PR 重审一轮的结果，以及随后的逐条判定、终局决定和一次完整的修复闭环。这是 `review-6` 第一次有线上样本。全部数值可由 `verify-review6-round.py` 从两份紧凑数据集复算；数据集不含 Prompt、模型正文、Diff、知识原文或凭据。

> 这组数据衡量的是**运行行为**与**已报告 Finding 的确认率**。它不含漏报，不能当作召回率；模型质量的精确率、召回率与需求违规召回率仍只引用 `evaluation/` 下的不可变证据，各组证据不得合并分母。

## 一、设计

被审对象与 2026-09-25 稳定性复测相同：三个演示仓的 14 个开放 PR（每个按事故台账反向构造了缺陷），以及 Halo fork 上重放的 24 个上游真实 PR（当时因超时被跳过的 #23 这次一并纳入）。给每个 PR 分支推一个空提交——diff 不变、head 变化——由 webhook 触发新审查。

与上一轮（09-25，`review-4`）相比，三样东西同时不同，因此下文的差异**只能描述、不能归因**到其中任何一项：

| | 09-25 | 本轮 |
|---|---|---|
| 提示词 | `review-4`（类型由是否引用验收条件推导） | `review-6`（模型显式给出类型，矛盾时保留为代码质量类；综合阶段拿到候选的类别、说明与建议；`COVERED` 须有已校验的证据，否则记 `UNKNOWN`） |
| 聊天模型 | `gpt-5.6-luna` | `gpt-6-luna`，温度 0 |
| 向量服务 | 原服务 | 另一家服务上的同一模型 `Qwen/Qwen3-Embedding-8B` |

更换向量服务后没有重建知识库：抽取 11 个已入库切片重新向量化，与库内向量的余弦相似度为 0.99986–0.99993，维度同为 4096。这是抽样核对，不是全量验证。

一处运行偏差：mall 仓保存的仓库令牌已被 GitHub 拒绝，它的 4 次投递在权威读取处以 502 失败；次日用负责人账号更换令牌后重投同一批投递，head 未变。

**判定与决定的执行人。** 每条 Finding 都对照被审 head 的源码核实后记为确认或驳回，理由写在该条的审计备注里。这项工作、随后的终局决定以及第五节的修复提交，都由作者授权的 AI 编程助手代为执行：判定与决定用指定审查人的测试账号，修复用开发负责人的测试账号，更换令牌与确认需求完成用作者提供的负责人账号。作者尚未逐条复核；引用本文数字前应抽查，首先是第三节列出的、与此前判定相左的三条。

## 三、判定结果

| 范围 | 确认 / 已判定 | 确认率 | 95% Wilson 区间 |
|---|---:|---:|---:|
| 全部 | 44 / 54 | 81.5% | 69.2–89.6% |
| 演示仓 | 41 / 42 | 97.6% | 87.7–99.6% |
| Halo | 3 / 12 | 25.0% | 8.9–53.2% |
| 置信度 HIGH | 37 / 42 | 88.1% | 75.0–94.8% |
| 置信度 MEDIUM | 7 / 12 | 58.3% | 32.0–80.7% |
| 需求类 | 36 / 43 | 83.7% | 70.0–91.9% |
| 代码质量类 | 8 / 11 | 72.7% | 43.4–90.3% |

同一 PR 内的 Finding 彼此相关，判定人只有一个，区间只作描述，不是对生产准确率的置信保证。

两组数据的方向截然不同。演示仓的每个 PR 只有 2–14 行刻意违反验收条件的代码，几乎每条 Finding 都成立；Halo 的 PR 是维护者审过并合并的修复，12 条里只确认 3 条。

### Halo 的 12 条

| fork PR | 类型 · 置信度 | 内容 | 判定 | 依据 |
|---|---|---|---|---|
| #3 | 需求 · HIGH | 回归测试只断言 `expectNextCount(1)`，未证明带回复的评论列表内容不变 | 确认 | 测试确实只计数 |
| #8 | 需求 · MEDIUM | 附件删除请求在重试时可能重复发起 | 驳回 | `client.delete` 同步写入删除时间戳，下一次协调被 `!isDeleted` 过滤 |
| #13 | 代码质量 · HIGH | 测试用带标志的旧键，没有覆盖「纯校验和」这一升级前格式 | 确认 | 测试类里没有以旧格式注解为前置的用例 |
| #16 | 代码质量 · HIGH | `reasonSubject` 为空时空指针 | 驳回 | 该字段在资源定义中必填，修改前的代码同样直接解引用 |
| #16 | 代码质量 · HIGH | 两次查询结果拼接会出现重复订阅 | 驳回 | 下游按订阅者名称去重，不产生重复收件人 |
| #17 | 需求 · MEDIUM | 类加载器不是 `URLClassLoader` 时回退到可能委派的查找 | 驳回 | 插件类加载器继承自 `URLClassLoader`，该分支在插件场景不可达 |

| #23 | 需求 · MEDIUM | 分类的变更检测按存储的父字段判断，修正后的父节点可能不写回 | 驳回 | 同一文件里先给全部兄弟节点写入有效父节点，再与原值比较 |
| #23 | 需求 · MEDIUM | 菜单项同上 | 驳回 | 同一实现 |

10 条驳回（含演示仓的 1 条）可以分成三类：

- **被 diff 之外的事实排除（5 条：#8、#16 两条、#17、#18）。** 模型只看到变更片段，无法确认字段是否必填、对象是否已标记删除、下游是否去重、分支是否可达，于是把「可能」报成了问题。审查上下文只含变更片段，是这类误报的直接来源。
- **与代码或运行事实不符（3 条：#20、#23 两条）。** 其中 #23 的反证就在被审文件里。
- **问题在需求而不在代码（2 条：#24 与演示仓的 1 条）。** #24 按验收条件的字面是成立的，是需求写得不准；演示仓那条指的是一段根本没有排序的代码「无法确认排序走白名单」，未实现已由该条验收条件的 `NOT_FOUND` 表达。

09-22 的判定用的是「真 / 可辩 / 假」三档，本轮按产品里的二值动作记录。第一类驳回按当时的口径更接近「可辩」而不是「假」，两轮的比例因此不能直接相比。

### 与此前判定是否一致

54 条里有 40 条能在同一 PR 的此前轮次找到同一问题的人工判定（口径同第四节）。其中 35 条与本轮一致。不一致的 5 条：

- **Halo 的 3 条需要作者裁定。** #8 与 #20 对应的问题在 2026-10-18 被判为确认，本轮驳回；#17 在此前轮次里两次确认、一次驳回，本轮驳回。若这三条按此前的判定计，Halo 的确认率是 6 / 12 而不是 3 / 12，全部是 47 / 54（87.0%）。Halo 的 25% 因此应读作 25%–50% 之间、取决于判定口径的一个数。
- **演示仓的 2 条**（payment PR #1 的金额类型、PR #2 的权限校验）此前各有一次驳回，本轮确认。其中至少一次是 09-22 为观察跨轮抑制而特意做的驳回，不代表当时认为问题不成立。

判定人不同、时间不同，同一问题就可能得到不同结论——这正是只有一个判定人时最主要的效度威胁。

### 与 09-22 已知真问题的重合

09-22 判定为真的 7 条分布在 fork PR #3、#5、#7、#12、#16、#19、#22。本轮再次报告的只有 #3 与 #22 两条（人工比对内容得出）；#5、#7、#12、#19 四个 PR 本轮没有任何 Finding，#16 报的是另外两个问题。09-25 的两轮各复现其中 5 条。这是一次观察，不是召回率估计，但它与上表的 25% 指向同一件事：这一轮在第三方真实代码上既报得不准，也漏掉了此前报出过的真问题。

## 四、与上一轮相比

以每个 PR 的首次审查与它紧邻的上一条已完成审查比较（演示仓上一轮 55 条、Halo 17 条）：

| | 演示仓 | Halo | 合计 |
|---|---:|---:|---:|
| 本轮 Finding | 42 | 12 | 54 |
| 与上一轮是同一问题 | 34 | 4 | 38 |
| `finding_key` 相同（落为 PERSISTING） | 3 | 1 | 4 |
| 继承抑制（SUPPRESSED） | 0 | 0 | 0 |

「同一问题」沿用稳定性复测的粗口径：需求类比较文件与验收条件，代码质量类比较文件与行号。

1. **问题延续了，身份没有延续。** 54 条里 38 条指向上一轮报过的同一问题，key 相同的只有 4 条。`finding_key` 含行号与模型给出的类别，换模型、换提示词后两者都在漂移，血缘几乎全部断开。没有一条 Finding 被继承抑制：tenant PR #2 的排序条目与 Halo #17 的问题此前都被驳回过，这次以新身份再次出现，只能重新驳回。这是 PRD §7「Finding 身份连续性」限制到目前为止最直接的样本。
2. **演示仓的密度略降，Halo 持平。** 演示仓每个 PR 平均 3.0 条（09-22 为 3.8），Halo 0.5 条（09-22 为 0.48），24 个 PR 里 14 个零 Finding。
3. **AC 裁定更保守。** Halo 上 `COVERED` 占 49.0%（09-22 为 77.6%），另有 22.1% 落在本版本新增的 `UNKNOWN`。`review-6` 要求 `COVERED` 必须有通过校验的证据，证据被丢弃或缺席时不再默认覆盖。

## 五、人工闭环

16 条审查作了**退回修改**（至少有一条确认的 Finding），均附理由；Halo 其余 21 条与一条被取代的中间审查保持未决定。Halo 的 PR 没有合并也没有关闭。

**拒绝并关闭。** payment PR #3 的四条验收条件全部未满足——实现对任何非空正文直接返回 200——经本系统拒绝后，GitHub 上的 PR 已关闭，源分支保留，需求状态不变。这是本系统第一次发起真实关闭。

**修复、复审、通过合并、需求完成。** tenant PR #1 走完了产品定义的整条链路：

1. 首轮审查报出 1 条需求类 Finding（仅判断请求头存在就放行），确认后退回修改。
2. 开发账号认领，在原分支推了两个修复提交：复用仓库既有的令牌校验并区分 401 / 403，再把它挂到全部运营路由上。提交前在一次性容器里验证了 14 种请求。
3. 两次复审都没有新 Finding。Finding 依次标记已修复、验证通过、关闭，审计事件五步齐全。
4. 审查人通过，GitHub 合并了被审查的 SHA；负责人随后把需求置为完成——这是线上第一条走到完成的需求。

复审把四条验收条件全部判为 `AT_RISK` 而不是 `COVERED`，通过的依据是第 2 步在系统之外做的验证。裁定是建议而不是门禁，这里按设计由人决定；它同时说明当前的裁定不足以单独支撑「已满足」的结论。

**SCM 身份与「本人 PR」。** 开发账号验证了提交全部 PR 的 GitHub 身份并绑定到四个项目，39 个 PR 的作者随即映射到该成员。以它请求审查自己的 PR 时通过授权（因该审查已完成而得到 409），另一名未绑定的开发成员得到 403。

## 六、有效性威胁

- 判定、决定与修复均由 AI 编程助手代为执行，判定人只有一个，作者尚未复核；每条理由留在审计备注里，可逐条重查。
- 演示仓的缺陷是构造的，且变更只有寥寥数行，97.6% 的确认率不能外推到真实代码。
- Halo 只有 12 条 Finding，比例对单条变化很敏感。
- 提示词、聊天模型与向量服务同时变化，只有一轮；模型服务在温度 0 下也不确定性作答（见 [LIVE-EXERCISES.md](./LIVE-EXERCISES.md) 第五节），差异不能归因。
- 只判定了报出来的 Finding，没有真值，测不了漏报。
- 向量服务更换后只做了 11 个切片的抽样核对。
- 修复闭环只有一例，证明的是流程接通，不是开发效率。

## 数据与复算

- `review6-round-20261116.csv`：40 行，每行一条审查，含上一条已完成审查、调用与 token、Finding 的类型 / 置信度 / 连续性分布、与上一轮同一问题数、警告分类、AC 裁定、判定数与决定。
- `review6-findings-20261116.csv`：54 行，每行一条 Finding，含类型、类别、置信度、连续性、文件路径、首次判定、同一问题在此前轮次被确认与驳回的次数，以及导出时的状态。
- 复算：`python3 docs/thesis/verify-review6-round.py`，只用标准库，先校验两份 CSV 的 SHA-256 并核对逐条明细与汇总一致。
