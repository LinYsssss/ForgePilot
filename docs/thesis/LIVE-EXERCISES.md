# 线上演练结果：演示仓重跑与 Halo 真实 PR 重放

本文把 2026-09-22 在生产部署（提交 `6162166`，含证据锚定校验器）上完成的两次演练整理为可直接引用的小节。全部数值可由 `verify-live-exercises.py` 从两份紧凑数据集复算；数据集不含 Prompt、模型正文、Diff、知识原文或凭据。

> 这两组数据衡量的是**运行行为与人工判定的 Finding 精确率**，不是正式三臂评测的召回率。三臂评测的精确率、召回率与需求违规召回率仍只引用 `evaluation/` 下的不可变证据，三组证据不得合并分母。

## 一、演示仓重跑：证据锚定校验器首次面对真实 PR

### 设计

三个演示仓（`reposage-demo-*`，15 个 PR，每个 PR 按事故台账反向构造了缺陷）在 2026-09-20 已用旧校验器审过一轮。本次给每个 PR 分支推一个空提交——diff 不变、head 变化——由 webhook 触发 15 个新审查，使锚定校验器在完全相同的输入上与旧结果对照。演练前作为 REVIEWER 驳回了上一轮的 3 条 Finding，用于观察跨轮抑制。

### 结果

| 指标 | 09-20（旧校验器） | 09-22（锚定校验器） |
|---|---:|---:|
| 审查完成 | 15 / 15 | 15 / 15，均为首次尝试 |
| Finding | 55 | 57 |
| 与上轮 `finding_key` 相同 | — | 21 |
| 连续性 NEW / PERSISTING / SUPPRESSED | — | 36 / 20 / 1 |
| validator 警告 | 1 | 9（纠行 8、丢弃 1） |
| 未审查文件 | 0 | 0 |
| embedding 瞬时失败（均被重试覆盖） | 0 | 3 |

纠行集中在 2 个 PR：模型报的行号不等于逐字引用在 diff 新侧的真实位置，校验器按引用纠正。1 条 Finding 因引用了不属于本修订的验收条件被丢弃并留警告。

### 跨轮抑制的一次真实触发与一次真实失效

- 1 条 Finding 以 `SUPPRESSED` 落库，继承自 09-12 那轮被驳回的 Finding：同一 PR 三轮同 key、同 `evidence_hash`、同 `basis_hash`，抑制链跨越了中间一轮。
- 演练前驳回的 3 条里只有 1 条的 key 在本轮复现，且它的 `evidence_hash` 不同——新引用少了行首缩进——因此落为 `PERSISTING` 而非 `SUPPRESSED`。这是 PRD §7「行号与证据文本连续性」限制在真实数据上的样本：抑制的正确性依赖模型逐字引用的稳定性。

### 闭环

mall PR #7 上，1 条 Finding 走完 CONFIRM（REVIEWER）→ CLAIM（DEVELOPER）→ FIXED → VERIFY → CLOSE 五步，审计事件齐全；REVIEWER 作出 APPROVE，Provider 确认合并被审查的 SHA 后本地决定落库。这是本系统第一次在真实 GitHub 仓库上完成"审查→修复→复核→合并"的完整闭环。

## 二、Halo 重放：24 个第三方真实 PR

### 设计

被审对象是 `halo-dev/halo`（Java 博客 CMS，GPL-3.0）。从其近 200 个已合并 PR 中选取**只改后端、有中文描述或关联 issue、不超过 25 个文件与 1500 行新增**的 24 个，fork 后在每个 PR 合并前的 base 上开分支并 cherry-pick 其 squash 提交，再在 fork 上开 PR。代码零改动，作者、时间线、上游 issue 与 review 评论全部真实；24 个 PR 里 18 个是 bug 修复，13 个关联上游 issue。

项目知识为 Halo 自己的 25 篇文档（README、CONTRIBUTING、SECURITY、docs 13 篇、openspec 8 篇）。需求 24 条由 PR 描述、关联 issue 与 review 讨论反推，每条 3～6 条验收条件，共 105 条。

这组数据与演示仓的关键区别：演示仓每个 PR 都埋了缺陷，Halo 的 PR 是维护者审过并合并的修复。因此它衡量的是**引擎在"应当基本没有问题"的代码上报多少、报得对不对**。

### 结果

| 指标 | 值 |
|---|---:|
| 审查完成 | 23 / 24 |
| Finding | 11（需求类 6、代码质量 5） |
| 零 Finding 的 PR | 12 / 23 |
| 人工判定 | 真 7、可辩 4、假 0 |
| 置信度 | HIGH 8、MEDIUM 3 |
| AC 裁定 | COVERED 76（77.6%）、AT_RISK 14、NOT_FOUND 8 |
| validator 警告 | 125（纠行 108、丢弃 14、其余为去歧义） |
| 未审查文件 / 截断 | 0 / 0 |
| 知识召回 | 每次审查恰好 8 条 |
| 模型调用 | 46 次成功、7 次 120 s 超时、2 次 embedding 504 |
| token | prompt 211.8k、completion 56.0k |

首次尝试即完成的 22 个审查端到端平均 6.6 min、中位 7.0 min、最长 16.0 min，其中 provider 累计时延平均 1.4 min，单次模型调用平均 27.8 s；其余为进程内排队（并发上限 2，24 个 webhook 在 90 秒内到达）。

### 11 条 Finding 的判定

判定依据是 PR 合并后的上游主干代码与人工读码。**真**：指出了代码中确实存在的问题；**可辩**：说法成立但上游有意接受或当前无实际影响；**假**：与代码事实不符。

| fork PR | 类别 | 内容 | 判定 |
|---|---|---|---|
| #3 | 需求 | 回归测试只断言 `expectNextCount(1)`，未证明返回内容与修改前一致 | 真 |
| #5 | 需求 | 传入 `pinned` 会置 `hasQuery = true`，从而跳过隐藏文章过滤 | **真** |
| #7 | 需求 | 测试只证明带标签的对象不被覆盖，未证明首次安装时仍会创建 | 真 |
| #9 | 代码质量 | 测试直接 mock 抛 404，未覆盖真实的策略查找路径与 warning 日志 | 可辩 |
| #11 | 需求 | 只有 finder 路径的测试，公开评论端点那条路径无等价证据 | 可辩 |
| #12 | 需求 | 回复排序对所有回复无条件按 priority 排，与"priority 只影响置顶项"不符 | **真** |
| #16 | 需求 | `not(isNull(expression))` 排除 null 但不排除空串 | 真 |
| #17 | 代码质量 | 只支持 `URLClassLoader`，其他类加载器会丢失 UI 资源 | 可辩 |
| #19 | 代码质量 | 根节点选择依赖成员迭代顺序，成环时后代仍可能被当作根 | **真** |
| #22 | 代码质量 | 列目录 IOException 只记日志不重试，瞬时故障后孤儿 JAR 永久残留 | 真 |
| #24 | 代码质量 | 用 `getDescription()` 推导文件路径，description 不是稳定的路径 API | 可辩 |

加粗的三条（#5、#12、#19）指出的是上游维护者审过、合并后至今仍存在的逻辑问题。#5 和 #12 各只需读一个方法就能确认：前者是过滤条件的短路逻辑，后者是 PR 描述与实现不一致。

### 两类应如实说明的 AC 判定偏差

- **不在 diff 里的验收条件**：两条 AC 写的是"release note 标注 action required"，而 release note 在 PR 描述里而不在 diff 里，引擎判 `NOT_FOUND` 是正确行为。这是撰写需求时的失误，说明 AC 必须只描述代码可见的事实。
- **"与修改前一致"类条件**多被判 `AT_RISK`：引擎无法从单个 diff 证明行为等价，判 AT_RISK 而非 COVERED 是保守的正确做法。

### 失败样本

fork PR #23（上游 #10289，9 个文件，diff 49.8k 字符）三次尝试都在第一批调用处 120 s 超时，共 6 次 TIMEOUT。这是 provider 对单次大 prompt 的响应时间超出运行边界（ARCHITECTURE §7.2），不是引擎缺陷；同规模的 #24（45.2k 字符）第二次尝试即成功。它是运行边界表里"单次调用超时 120 s"那一行的真实样本。

## 三、两组数据放在一起说明什么

| | 演示仓（15 PR） | Halo（23 PR） |
|---|---:|---:|
| Finding / PR | 3.8 | 0.48 |
| 零 Finding 的 PR | 0 | 12 |
| AC COVERED 占比 | 3.1% | 77.6% |

两组数字方向完全相反。演示仓的高密度说明引擎能找到刻意埋下的需求缺口；Halo 的低密度且零假阳性说明它不是"见 diff 就报"。这一点演示仓单独给不出，三臂评测也给不出，因为后者的语料同样是构造的。

## 四、有效性威胁

- Halo 的 11 条 Finding 由本文作者一人判定，没有第二判定人；判定依据公开在表中，读者可自行核对。
- 24 个 PR 是按"后端、有描述、规模适中"筛选的，不是随机抽样；大 PR 被规模上限排除。
- "零 Finding"不等于"没有问题"，只能说引擎没有报；对合并后仍有 issue 的 PR 未做召回核对。
- 需求与 AC 由第三方反推，写法会影响 AC 裁定；上述两类偏差就是例子。
- 演示仓重跑与上轮共用同一模型与 Prompt 版本，纠行数只反映校验器的变化，不反映模型质量。
