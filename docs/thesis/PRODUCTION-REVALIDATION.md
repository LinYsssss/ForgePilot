# 部署后调用链复验结果

> 建议论文小节标题：**部署后真实 PR 调用链复验**。本节数据用于说明系统在
> 真实 GitHub PR 快照和真实模型服务下能否完整运行、留痕并保持输入一致，不能
> 用于估计 Finding 的精确率或召回率。

## 实验目的与设计

为验证审查调用链在生产部署后的可运行性与可追溯性，本研究选择三个演示项目
中的 15 个真实 GitHub PR，每个项目 5 个。实验在部署提交 `4121cea` 上执行，
Review Engine 为 `forgepilot-review`，Prompt 版本为 `review-2`，模型为
`gpt-5.6-luna`。

系统规定已完成的 Review 不得覆盖或重跑。为在不改变 PR head 和需求语义的
前提下产生合法的新审查身份，实验为每条处于 `IN_DEVELOPMENT` 状态的需求发布
一个内容相同的第 2 版修订，保留标题、背景、描述、验收条件文本及稳定
`ac_key`，并记录“部署后调用链复验，不改变需求语义”的变更原因。随后按固定
顺序触发审查，前一条到达 `COMPLETED` 或 `FAILED` 后才启动下一条。实验没有
修改 PR 分支，没有删除历史 Review，也没有对新 Finding 作人工裁决。

评价指标包括：

1. **运行完成率**：到达 `COMPLETED` 的 Review 数除以发起数。
2. **AI 调用成功率与关联率**：成功调用数及其中写入正确 `review_id` 的比例。
3. **输入一致性率**：Review 与当前 PR head、输入指纹、需求修订及不可变快照
   同时一致的比例。
4. **覆盖记账完整性**：进入审查、未审查和截断的文件数。
5. **端到端时延**：Review 创建至终态更新时间；P95 使用线性插值的连续百分位。
6. **模型输出分布**：Finding 与 AC verdict 数量，仅作描述性统计。

## 实验结果

表 1 给出调用链的主要结果。15 条 Review 全部完成，45 次 AI 调用全部成功且
全部关联到本轮 Review。所有 Review 的当前输入与不可变快照一致；旧的 15 条
Review 及其人工裁决完整保留，实验结束后没有 `PENDING` 或 `RUNNING` 行。

**表 1 生产调用链完整性结果**

| 指标 | 结果 | 比例 |
|---|---:|---:|
| Review 完成 | 15 / 15 | 100% |
| AI 调用成功 | 45 / 45 | 100% |
| AI 调用关联 `review_id` | 45 / 45 | 100% |
| PR head 一致 | 15 / 15 | 100% |
| 输入指纹一致 | 15 / 15 | 100% |
| 需求修订一致 | 15 / 15 | 100% |
| 不可变快照三项一致 | 15 / 15 | 100% |
| 审查文件 | 30 | — |
| 未审查文件 | 0 | 0% |
| 截断文件 | 0 | 0% |
| 运行结束后的活动 Review | 0 | — |

每条 Review 产生 1 次查询向量调用和 2 次审查生成调用，共消耗 103,324 个输入
token 与 39,677 个输出 token，总计 143,001 个 token。表 2 展示时延统计。

**表 2 逐 Review 时延统计（n = 15）**

| 指标 | 端到端时延 | AI provider 累计时延 |
|---|---:|---:|
| 平均值 | 88.899 s | 88.740 s |
| 中位数 | 79.193 s | 79.080 s |
| P95 | 131.249 s | 131.086 s |
| 最小值 | 52.337 s | — |
| 最大值 | 147.405 s | — |

15 条 Review 的端到端累计时延为 1,333.479 秒，其中 provider 调用累计
1,331.107 秒，占 99.82%。在本实验配置下，审查耗时主要来自外部模型推理，
而不是数据库提交、队列交付或结果持久化。该比例是本轮样本的描述性结果，
不能直接外推到其他模型、网络或 PR 规模。

模型共输出 55 条 Finding，平均每个 PR 3.667 条，中位数 4 条，范围为 1–6 条。
其中 54 条为需求 Finding、1 条为代码质量 Finding；类别分布为需求缺口 43 条、
安全 10 条、API 契约 1 条、正确性 1 条。置信度分布为 HIGH 51 条、MEDIUM
4 条。65 个 AC verdict 中，`AT_RISK` 41 个、`NOT_FOUND` 21 个、`COVERED`
3 个。这些数值描述模型输出结构；由于本轮没有对新 Finding 进行独立人工标注，
它们不能解释为 55 个真实缺陷，也不能据此计算精确率或召回率。

## 结果解释

本轮结果支持三个有限结论。第一，修复后的生产调用链能够在 15 个真实 PR
快照上串行完成，且未留下活动或失败任务。第二，Review chat 与知识召回 embedding
均写入已有 Review ID，解决了旧运行中 AI 调用日志无法归属具体审查的问题。
第三，Review 当前输入与创建时快照保持一致，说明结果可以追溯到明确的 PR head、
输入指纹和需求修订。

这组数据不替代正式三臂评测。正式评测回答“需求与项目知识上下文是否改善模型
输出质量”，使用固定语料、确定性评分和一次性 holdout；本轮生产复验回答“已部署
系统能否在真实集成路径中完成并正确留痕”。论文应分别报告两者，避免将 100%
运行完成率表述为 100% 审查准确率。

## 有效性威胁

- **样本代表性**：15 个 PR 来自 3 个演示仓库，缺陷为有目的构造，不能代表真实
  企业 PR 的规模和分布。
- **执行方式**：为隔离故障并避免并发干扰，实验严格串行，不能证明高并发吞吐。
- **结果真值**：新一轮 Finding 未独立人工裁决，因此只报告输出分布，不报告质量
  指标。
- **输入复用**：PR head 与旧演练相同，仅需求修订身份更新；这有利于控制变量，
  但不覆盖新提交到达时的所有 webhook 竞争场景。
- **环境依赖**：结果来自单一部署、单一模型和当时的网络状态；时延不应外推。
- **覆盖范围**：本轮验证 GitHub 路径，不构成真实 GitLab provider 联调证据。
