# 正式评测的效度分析：语料提示、标签口径与去提示敏感性实验

本文补充说明正式三臂评测（`phase8-formal-38-v1`）的一处构造效度问题，并用两种不调用新数据的分析和一次新实验量化它。正式评测的冻结配置、语料清单、holdout 台账与原始输出一字未动，其结论仍是**唯一预先登记的主结果**；本文全部数字可由 `verify-evaluation-sensitivity.py` 从 `evaluation-sensitivity-20260925.csv` 复算。

## 一、结论

1. **语料把答案的位置和类别写进了需求。** 38 例中有真值缺陷的 31 例，缺陷所在 AC 都以 `[类别]` 开头、以「重点核验 <文件> 第 a-b 行」结尾；需求背景写出缺陷类别；描述性的用例 ID（如 `java-sql-resource-leak`）出现在三臂的提示词开头，需求标题和描述也复述它。这些都是从旧仓语料迁移时带进来的模板文本。
2. **严格口径的 12% / 22% / 32% 主要衡量的是标签对齐，而不是找没找到。** 冻结评分器要求类型、类别、文件与行号区间同时匹配。只放宽类型，第三臂就从 32.3% 升到 83.9%；只比文件与行号，三臂召回率是 71.0% / 90.3% / 96.8%。去掉提示后，按原规则需求两臂降到 0–3%——模型不再能从 AC 抄到语料自有的类别名。
3. **去掉提示后，「上下文有帮助」的方向仍然成立，幅度变小。** 只比位置时，三臂召回率从 67.7% 到 77.4% 再到 83.9%，精确率从 50.0% 到 72.7% 再到 74.3%；需求违规召回（只比位置）为 6/10、9/10、9/10。
4. 样本很小（31 个缺陷、10 个需求违规），各组置信区间大量重叠，以下差值都是描述性的。

## 二、提示出现在哪里

| 位置 | 模板 | 覆盖 |
|---|---|---|
| 提示词开头 | `caseId: <描述性用例 ID>` | 38 例 × 三臂 |
| 需求标题 / 描述 | 「审查 <用例 ID 拆词> 变更…」「针对 <用例 ID> 的 fixture/diff…」 | 38 例（需求两臂） |
| 需求背景 | 「…用于验证增量代码审查对 <类别> 及明确非目标行为的识别边界」 | 31 例写出类别（需求两臂） |
| 缺陷 AC | `[RESOURCE_LEAK] 所有资源句柄……必须正确关闭；重点核验 src/App.java 第 7-7 行。` | 31 / 31 例（需求两臂） |

还有一处标签层面的矛盾：冻结的系统提示要求「只有违反了给出的验收条件才用 REQUIREMENT」，而缺陷 AC 描述的正是那个缺陷；31 条真值里却有 21 条标为 `CODE_QUALITY`。需求两臂里模型按指令标 REQUIREMENT，在原规则下就同时记一次漏报和一次误报。

## 三、三种匹配口径

三种口径都直接调用冻结评分器的 `match_findings`，只把被去掉的条件统一成同一个值：

- **原规则**：类型、类别（含别名表）、文件相同，且行号区间重叠——即冻结报告本身。
- **不看类型**：去掉 REQUIREMENT / CODE_QUALITY 条件，其余不变。
- **只比位置**：再去掉类别，只要求文件相同、行号区间重叠。fixture 都很小，偶然重叠不可排除，这一列是上限。

导出脚本逐例核对：原规则一列与冻结报告的每个用例完全相等。

## 四、冻结结果按三种口径重算（带提示）

全量 38 例（31 个缺陷），精确率 / 召回率：

| 对照臂 | 原规则 | 不看类型 | 只比位置 |
|---|---:|---:|---:|
| 仅 Diff | 12.1% / 12.9% | 12.1% / 12.9% | 66.7% / 71.0% |
| Diff + 需求/AC | 21.6% / 25.8% | 59.5% / 71.0% | 75.7% / 90.3% |
| Diff + 需求/AC + 知识 | 32.3% / 32.3% | 83.9% / 83.9% | 96.8% / 96.8% |

holdout 12 例（9 个缺陷）的第三臂：原规则 20.0% / 22.2%，不看类型 80.0% / 88.9%，只比位置 90.0% / 100%。

## 五、去提示敏感性实验

**设计。** 新的实验身份 `sensitivity-deleaked-38-v1`：同一 38 例、同一冻结 runner 与评分器、同一模型（`gpt-5.6-luna`）、温度 0、超时 120 s、正式评测订正后的同一 provider 端点。只替换第二节列出的提示：用例 ID 换成不透明编号，需求标题 / 背景 / 描述换成中性句，缺陷 AC 只保留规则句本身（如「所有资源句柄……必须正确关闭」），非目标约束 AC 原样保留。2026-09-25 运行一次，114 次调用全部完成，事后没有调整任何配置。改写后的 114 份提示词在 diff 之前都已不含用例名、类别标签或位置。

**结果。** 全量，精确率 / 召回率：

| 对照臂 | 原规则 | 不看类型 | 只比位置 |
|---|---:|---:|---:|
| 仅 Diff | 14.3% / 19.4% | 14.3% / 19.4% | 50.0% / 67.7% |
| Diff + 需求/AC | 0.0% / 0.0% | 21.2% / 22.6% | 72.7% / 77.4% |
| Diff + 需求/AC + 知识 | 2.9% / 3.2% | 17.1% / 19.4% | 74.3% / 83.9% |

需求违规召回（只比位置）：6/10、9/10、9/10；带提示时为 7/10、10/10、10/10。holdout 第三臂只比位置为 61.5% / 88.9%。

## 六、怎么读这两张表

- **原规则口径依赖提示。** 去提示后需求两臂按原规则几乎归零，而仅 Diff 臂基本不变——提示给的是类别名，而语料的类别名（如 `BUSINESS_RULE_RISK`、`CONTRACT_DRIFT`）不看提示几乎猜不中。因此正式结论里「需求违规召回 0% → 80% → 90%」不宜解读为「需求上下文让模型多找到了 80% 的违规」。
- **位置层面的结论更稳。** 只比位置时，需求与 AC 让召回率提高 9.7 个百分点（带提示时为 19.3）、精确率提高 22.7 个百分点；知识在此之上再提高召回率 6.5 个百分点（带提示时同为 6.5），精确率只多 1.6 个百分点。
- **提示对「知识 vs 需求」这一对比的影响较小**，因为两臂拿到的提示一样多；它主要抬高的是「需求臂 vs 仅 Diff」的差距。

## 七、建议的论文口径

1. 正式三臂结果照原样报告，注明它是预先登记、只运行一次的主结果。
2. 在有效性威胁中写明第二节的提示与标签矛盾，并附第四、五节两张表作为事后敏感性分析；不与正式口径合并分母，也不替换它。
3. 结论表述为：「在构造语料上，把需求与验收条件放进上下文提高了缺陷定位的召回率与精确率，加入项目知识进一步提高召回率；去掉语料中的定位提示后方向不变、幅度缩小。」真实第三方代码上的精确率见 [LIVE-EXERCISES.md](./LIVE-EXERCISES.md) 的 Halo 重放。

## 八、有效性威胁

- 两种放宽口径与去提示实验都是**看到正式结果之后**设计的，不是预先登记的分析，只能作描述。
- 去提示实验复用了同样的 38 例（含已经揭晓结果的 holdout），不是一份新的无偏估计，只回答「去掉提示会怎样」。
- 「只比位置」在小 fixture 上会把指向同一行的不同问题算作命中，是上限。
- 中性化后的需求仍保留 AC 规则句，它用自然语言说出了缺陷类别；彻底去掉需要重写需求，那就是另一套语料了。
- 单次运行、温度 0、同一模型与 provider；没有测量运行间方差。

## 数据与复算

- `evaluation-sensitivity-20260925.csv`：228 行 = 2 种条件 × 3 臂 × 38 例，列为三种口径下的匹配数与其中的需求违规匹配数；用例用不透明编号，不含任何用例 ID 或内容。
- 生成：`evaluation/tools/sensitivity_deleaked.py`（`run` 做一次去提示实验，`export` 导出 CSV；两者都先校验冻结文件未变，需要证据机上被 Git 忽略的私有语料与原始输出）。
- 复算：`python3 docs/thesis/verify-evaluation-sensitivity.py`，只用标准库，校验 CSV 的 SHA-256，并断言原规则一列与冻结报告相等。
