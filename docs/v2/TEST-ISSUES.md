## T-010 已确认事实

本次真实 PR 审查已成功完成并生成 8 条 Finding。问题不是模型、Webhook、仓库凭据或知识检索失败。

2026-08-24 代码核实后修正：根因比“页面未承载”更靠前——`ReviewPrompts.java:70` 与 :127 的模型输出 schema，`required` 为 `["type","category","path","line","evidence","acId","sourceIds"]`，**模型从未被要求产出问题说明或修复建议**；`finding` 表也没有对应列。因此这是“从未生产过”，而不是“生产了没展示”，修复必须贯穿契约、校验器、迁移、API 与前端。

另两条相关事实：`finding_key` / `evidence_hash` / `basis_hash` 三个哈希的输入均不含模型散文（V6 注释明确要求如此），所以新增散文字段只要不进这三个哈希即安全；模型已在产出 `category` 且它参与 `finding_key`，但该列未落库。

### 处理结论（2026-08-24，D021 / V9）

两处 schema 各加 `explanation` / `suggestion` / `confidence`（各 2000 字符上限），V9 给 `finding` 追加这三列与 `category`，四列全部可空，业务表仍 19 张。前端改为「问题说明 → 代码证据 → 修复建议」层次，置信度徽章接真实数据，类别作徽章，`finding_key` 与两个哈希收进可核验性折叠区。

实施中发现两条原始台账未记录的事实，均已写入决策记录：

1. **两个版本号朝相反方向移动。** `ReviewPrompts.VERSION` 必须升为 `"review-2"`（其自身 javadoc 规定任一指令或 schema 变更都要跟着升），而 `FindingKeys.RULE_VERSION` 必须保持 `"1"`（没有确定性规则变化；递增它会改写全部 `basis_hash` 并丢弃全部继承抑制项）。台账与任务 PRD 原先只提到后者。
2. **`category` 落库若加 CHECK 而校验器不先做词表映射，模型幻觉值会中止整批 finding 插入**，不是单行。校验器此前从不校验该词表（原始串算完 key 即弃，故无后果）。因此词表映射发生在写库之前、越界存 NULL，而 `finding_key` 继续用原始串以保持逐字节不变。

另有一条只在非空数据库上才暴露的风险已被测试覆盖：`ADD CONSTRAINT ... CHECK` 会立即校验既有行，因此不容忍 NULL 的 CHECK 会在空的测试库上通过、却在有 finding 的真实部署库上让迁移直接失败。`V9MigrationTest` 先迁到 V8、写一条 finding、再迁完，专门锁这一条。
