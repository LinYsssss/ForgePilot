# 网页全链路测试指南

本指南用于在真实部署上通过网页验证 D020 成员目录、多角色与 SCM 身份链路，并接入既有“需求 → PR → Review → Finding → Decision → DONE”主流程。不要使用正式评测 holdout；测试仓库和测试 PR 应使用普通演示数据。

## 1. 准备

准备三个 ForgePilot 账户：负责人、开发者、评审者。注册时分别填写清晰显示名；记录页面显示的平台 ID。开发者准备一个对测试 GitHub/GitLab 仓库至少有读取权限的个人 Token：

- GitHub：Token 必须能调用 `/user` 并读取该仓库；SCM 外部 ID 由 GitHub `/user` 响应中的数字 `id` 自动取得，不手填。
- GitLab：Token 必须能调用 `/api/v4/user` 并读取该项目；外部 ID 由响应中的数字 `id` 自动取得。

Token 只粘贴到“一次性 Token”字段，测试后可在 Provider 撤销。ForgePilot 不保存它。

## 2. 账户与多身份

1. 以开发者登录，打开右上角账户菜单，确认显示“显示名 · @用户名 · ID”。进入“管理资料、密码与 SCM 身份”。
2. 修改显示名，保存并刷新页面；顶部和账户页都应显示新值，用户名与平台 ID 不变。
3. 在“验证新身份”选择 Provider、填写 API 地址、标签（如“公司 GitHub”）、用途和 Token。
4. 提交后确认列表显示 Provider、实例、外部用户名、稳定外部 ID、标签和用途；Token 输入被清空，页面和 Network 响应中没有 Token。
5. 如有第二个远端账号，再添加一个不同标签/用途的身份，确认两者能被明确区分。

## 3. 成员目录与多角色

1. 以负责人创建项目并进入成员页。
2. 分别用开发者/评审者的显示名、用户名或平台 ID 搜索；结果应同时显示三项标识。
3. 多选两人，给开发者选择 `DEVELOPER`，给评审者选择 `REVIEWER`；也可让同一人同时选择两个角色。
4. 点击“一次添加 N 人”。刷新后成员表格应显示正确角色集合。提交前预览里逐行角色可覆盖共同角色；把某行角色全部取消后提交按钮应禁用。
5. 用一个已是成员的账户与一个有效候选组成批次尝试添加；请求应失败且有效候选也不能被部分加入。
6. 以开发者或评审者登录：能查看成员，但看不到批量添加、角色保存或 Leader 转移操作。
7. 如需验证转移，负责人对目标成员点击“转移负责人”并确认；转移后项目仍应只显示一个 Leader，原负责人若原来只有 Leader 则保留 Developer。

## 4. 仓库与身份绑定

1. 负责人在“仓库接入”注册测试仓库，确认 Provider、外部仓库 ID 和 API Base 正确；凭据不回显。
2. 保持“身份绑定需负责人审批”关闭。开发者进入成员页，在“我在本项目使用的 SCM 身份”面板选择兼容身份，粘贴一次性 Token 并绑定。
3. 结果应立即为 `ACTIVE`，显示标签、用途、外部用户名/ID、仓库权限和核验时间。
4. 负责人开启“身份绑定需负责人审批”。开发者重新绑定另一个兼容身份；旧活动绑定保持有效，新请求显示 `PENDING_APPROVAL`。
5. 负责人在成员页批准：旧绑定变为 `SUPERSEDED`，新绑定变为 `ACTIVE`；另建一次待审请求并拒绝，确认其变为 `REJECTED` 且不影响当前活动绑定。
6. 确认负责人只能批准/拒绝，不能替开发者选择某个身份；其他成员也不能操作开发者绑定。

## 5. PR 作者与主链路

1. 负责人创建带 AC 的需求并指派给开发者，开发者生成一次性实现建议。
2. 开发者用刚刚绑定的远端身份在测试仓库创建 `feat/REQ-<需求ID>-...` 分支和 PR/MR。
3. 触发 Webhook/同步后，在“代码审查”确认 PR 的作者已映射为该开发者，需求自动关联。
4. 开发者应能对本人的 PR 请求 Review，并在当前 head 尚无终局 Decision 时修改需求关联；其他 Developer 不应获得该权限。远端用户名相同但稳定 ID 不同也不能冒充。
5. Reviewer 确认 Finding 并 `REQUEST_CHANGES`；开发者修复并推送新 head；确认产生新 Review 且旧 Review 保留。
6. Reviewer 对当前 Review `APPROVE`；负责人最后把需求置为 `DONE`。PR 的 APPROVE 不能自动推进需求状态。
7. 开发者撤销当前 SCM 身份或活动绑定，刷新 PR：`authorUserId` 应被清空，开发者不再获得“本人 PR”权限；远端作者用户名/ID 快照仍保留。

## 7. 资源删除闭环（D022 / V10，对应 AC18）

三类删除是三种策略，验收时要分别确认「删掉了什么」和「什么必须还在」。

1. **批量上传知识**：以负责人在项目知识页一次选择 3 个 `.txt/.md` 文件（其中一个故意改成不受支持的后缀）。确认逐文件报告成败：受支持的成功、不受支持的失败，且失败那个不影响其余两个。
2. **删除知识文档**：删掉刚上传的一个公共知识文档，确认它从列表消失，Chunk/向量计数随之减少；再对一个**需求附件来源**的文档尝试删除，页面应给出「它是需求 N 的附件」的提示而不是删掉它。
3. **删除后不再被召回**：删除前先对该文档内容跑一次实现建议并记下召回来源；删除后重跑，确认它不再出现在「实际召回的知识来源」里。
4. **移除成员**：先把一条需求指派给开发者、让它认领一条 Finding、并完成 SCM 身份绑定。然后以负责人移除该成员，确认：成员从列表消失；那条需求的负责人变为未指派；那条 Finding 回到无人认领；该成员的项目 SCM 绑定消失。
5. **移除后既成事实完好**：刷新该开发者此前创建的 PR，确认远端作者用户名与稳定 ID **仍然显示**（只有本地映射失效，「本人 PR」权限随之消失）；Finding 的历史流转记录、Review 与需求关联记录一条不少。
6. **唯一负责人不可移除**：对负责人自己尝试移除，应被拒绝并提示先转移负责人；完成转移后原负责人可被移除。
7. **删除作废需求**：对一条非作废需求尝试删除，应被拒绝；把它置为作废后再删除，确认它从需求列表和详情消失，而它的 AI 调用记录与 PR 关联记录仍在数据库里可查。
8. **重复删除**：对上述三类各再删一次，应得到明确的「不存在」结果，而不是二次生效或模糊报错。

## 6. 通过标准与证据

通过时应同时满足：成员标识清晰、多角色能力取并集、批量添加原子、Token 无回显/无存储、默认绑定立即生效、严格绑定批准前不授权、PR 按稳定 ID 映射、撤销后权限立即失效、既有主链路完整。

建议保存以下证据到当前 Trellis 任务：关键页面截图、浏览器 Network 中不含 Token 的响应、测试 PR 链接、最终需求/Review 状态，以及任何失败请求的 `{code,message,traceId}`。完成后撤销测试 Token；不要删除或重跑 `evaluation/` 下正式评测资产。
