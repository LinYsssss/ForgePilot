# 代码仓库智能审查平台演示数据与样例仓库设计

## 1. 目标

演示数据决定项目展示效果。这个项目必须准备一个可控的 Java 示例仓库，并在仓库中故意制造几类典型缺陷，让系统能稳定识别并生成带 RAG 证据的审查报告。

推荐样例仓库名称：

```text
mall-order-service
```

## 2. 样例仓库业务背景

`mall-order-service` 是一个简化版电商订单服务，包含：

- 用户登录。
- 订单创建。
- 订单支付。
- 订单发货。
- 订单查询。
- 管理员订单管理。

核心业务规则：

```text
订单只有在支付状态为 PAID 时才能发货。
管理类接口必须校验 ADMIN 权限。
涉及订单和库存的多表写入必须使用事务。
查询接口不得使用字符串拼接 SQL。
```

## 4. 知识库文档内容设计

### 4.1 order-flow.md

必须包含以下内容，方便 RAG 检索：

```text
# 订单业务流程

## 发货规则

订单发货前必须满足以下条件：
1. 订单存在。
2. 订单支付状态必须为 PAID。
3. 订单发货状态必须为 WAIT_SHIP。
4. 发货成功后，订单状态更新为 SHIPPED。

如果未校验支付状态，可能导致未支付订单被发货。
```

### 4.2 security-policy.md

```text
# 接口权限规范

## 管理接口

所有 /admin 开头的接口必须校验用户角色。
只有 ADMIN 角色可以访问订单管理、强制退款、手动发货等管理能力。

Spring Boot 项目中可以使用 @PreAuthorize("hasRole('ADMIN')") 或统一权限拦截器。
```

### 4.3 db-schema.md

```text
# 数据库表结构

## orders

字段：
- id：订单 ID
- user_id：用户 ID
- status：订单状态，包含 CREATED、PAID、WAIT_SHIP、SHIPPED、CANCELLED
- pay_status：支付状态，包含 UNPAID、PAID、REFUNDED
- amount：订单金额

订单发货逻辑必须检查 pay_status = PAID。
```

### 4.4 bug-history.md

```text
# 历史 Bug 记录

## BUG-001 未支付订单被发货

原因：发货接口只判断订单状态，没有判断支付状态。
修复：在 OrderService.shipOrder 中增加 pay_status = PAID 校验。

## BUG-002 管理接口越权访问

原因：新增管理接口没有添加角色校验。
修复：为 /admin/order/** 接口添加 ADMIN 权限校验。
```

## 5. 缺陷 Commit 设计

### 5.1 Commit 1：权限校验缺失

标题：

```text
feat: add admin force ship api
```

问题：

```text
新增 /admin/orders/{id}/force-ship 接口，但没有添加 @PreAuthorize("hasRole('ADMIN')")。
```

目标识别：

```text
AUTH_RISK
HIGH
```

预期证据：

```text
security-policy.md：所有 /admin 开头的接口必须校验 ADMIN 角色。
```

### 5.2 Commit 2：SQL 注入风险

标题：

```text
feat: add order search by keyword
```

问题：

```text
在 Mapper 中使用字符串拼接 SQL：
select * from orders where username like '%" + keyword + "%'
```

目标识别：

```text
SQL_INJECTION
HIGH
```

预期建议：

```text
使用参数绑定或 MyBatis #{keyword}。
```

### 5.3 Commit 3：空指针风险

标题：

```text
fix: optimize order detail response
```

问题：

```text
Order order = orderMapper.findById(id);
return order.getStatus().equals("PAID");
```

没有判断 `order` 是否为空。

目标识别：

```text
NULL_POINTER
MEDIUM
```

### 5.4 Commit 4：事务缺失

标题：

```text
feat: create order with stock deduction
```

问题：

```text
创建订单和扣减库存在同一方法中执行，但方法缺少 @Transactional。
```

目标识别：

```text
TRANSACTION_RISK
HIGH
```

### 5.5 Commit 5：业务规则破坏

标题：

```text
refactor: simplify ship order logic
```

问题：

删除了：

```java
if (!"PAID".equals(order.getPayStatus())) {
    throw new BusinessException("订单未支付，不能发货");
}
```

目标识别：

```text
BUSINESS_RULE_RISK
HIGH
```

预期证据：

```text
order-flow.md：订单发货前必须校验订单支付状态为 PAID。
bug-history.md：历史上曾出现未支付订单被发货问题。
```

## 6. 演示脚本

### 6.1 5 分钟演示流程

```text
1. 登录系统。
2. 创建 mall-order-service 项目。
3. 绑定样例 Git 仓库。
4. 上传 order-flow.md、security-policy.md、db-schema.md、bug-history.md。
5. 等待文档状态变为 INDEXED。
6. 在知识库检索中输入“发货前是否要校验支付状态”。
7. 触发 commit-5 的代码审查。
8. 查看任务状态从 PENDING 到 RUNNING 再到 SUCCESS。
9. 打开审查报告。
10. 展示问题：删除支付状态校验，风险等级 HIGH，证据来自 order-flow.md。
```

### 6.2 面试讲解重点

```text
这个项目不是直接让大模型看代码，而是先通过 Git Diff 提取变更信息，
再通过 RAG 检索项目业务文档、历史 Bug 和代码规范，
最后让大模型基于证据生成审查报告。

耗时任务通过 RabbitMQ 异步执行，并支持失败重试、死信队列和任务幂等。
```

## 7. 演示验收表

| 验收项 | 标准 |
| --- | --- |
| 文档入库 | 上传文档后能生成 chunk 和向量 |
| RAG 检索 | 输入业务问题能检索到对应文档 |
| Git Diff | 能展示目标 Commit 的变更内容 |
| MQ 任务 | 审查任务能异步执行 |
| AI 报告 | 能生成 JSON 并保存为报告 |
| 证据链 | 报告中能看到文档来源 |
| 前端展示 | 页面能看懂问题和建议 |
