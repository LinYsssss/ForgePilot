## 一、素材设计思路

演示 AI 代码审查最容易失败的地方，是评委问一句："这些问题用普通静态扫描不也能查出来吗？"

所以三个仓库里的缺陷刻意分成三类：

| 类别 | 特征 | 演示价值 |
|---|---|---|
| **A 类：通用缺陷** | 形态特征明显：SQL 拼接、URL 参数未编码、原型污染 | 证明基础能力，静态扫描也能发现 |
| **B 类：规则依赖** | 违反知识库里写明的业务规则 | **只有读了文档才可能发现** —— RAG 的核心价值 |
| **C 类：事故重犯** | 重复知识库 `bug-history.md` 里记录过的历史事故 | 最有说服力 —— AI 能说出"这和 BUG-001 是同一个问题" |

注意「越权」与「硬编码」这两个常见说法在本素材里**不是** A 类：越权大多落在 C 类（M7、M8 重犯 BUG-002 / BUG-003）或 B 类（T11 靠 `auth-policy.md` 第 5 节判定），硬编码则落在 P1（费率与文档不符，B 类）和 T13（前端硬编码 API Key，A+B 跨类）。纯 A 类只有 4 条，见第四节。

少数缺陷同时具备两类特征（例如 M5 既是 SQL 拼接，又重犯了 `bug-history.md` 里的 BUG-004），对照表里标成 `A + C` 这样的跨类。43 条按类别的分布见第四节开头。

**演示时重点展示 B 类和 C 类。** 如果 AI 的输出里出现了"根据 `order-flow.md` 第 2 节"或"这与 INC-2024-07 是同类问题"这样的表述，RAG 就算真正跑通了。

## 三、怎么用

### 3.1 传统审查（本机可跑）

1. 先重建三个仓库：`bash scripts/init-demo-repos.sh --verify`（见第七节）
2. 创建项目 → 绑定仓库（provider 选 `LOCAL`，填绝对路径，分支 `main`）
3. 上传 **12 份**知识文档，等状态全部变为 `INDEXED`：该仓库 `docs/` 下 4 份 + `knowledge-shared/` 5 份 + `knowledge-noise/` 3 份（分层与用途见第五节）
4. 创建审查任务，目标提交填 PR 分支的 HEAD，关联刚上传的文档
5. 查看报告，对照第四节的表核验

### 3.2 PR 流程

三个仓库都准备了 PR 分支，diff 是干净的「一个功能一批缺陷」：

```
mall-order-service:          main → feature/promotion-batch-ship
payment-settlement-service:  main → feature/instant-settlement
tenant-user-center:          main → feature/ops-console
```

如果走 SCM Webhook 的完整 PR 流程需要 GitHub/GitLab 侧配合；本机演示可以直接审查分支 HEAD 提交，diff 内容是一样的。

## 五、知识库三层与三档对照实验

### 5.1 三层结构

每个项目要上传的 12 份文档分三层，边界是刻意划出来的：

| 层 | 位置 | 份数 | 用途 |
|---|---|---|---|
| 仓库专属 | `<repo>/docs/` | 4 | 该仓库的业务规则、表结构、安全约定与历史事故。**B 类与 C 类缺陷的判据全在这一层** |
| 通用规范 | `demo-repos/knowledge-shared/` | 5 | 三个仓库共用的工程规范，只写与业务领域无关的通则 |
| 干扰文档 | `demo-repos/knowledge-noise/` | 3 | 与代码审查无关但有真实感的文档，用来检验检索排序 |

- 仓库专属 4 份：mall 是 `order-flow.md`、`db-schema.md`、`security-policy.md`、`bug-history.md`；payment 是 `settlement-rules.md`、`db-schema.md`、`security-policy.md`、`bug-history.md`；tenant 是 `tenant-isolation.md`、`auth-policy.md`、`api-contract.md`、`bug-history.md`
- 通用规范 5 份：`engineering-standards.md`、`security-baseline.md`、`api-design-guide.md`、`data-handling-policy.md`、`code-review-checklist.md`
- 干扰文档 3 份：`frontend-style-guide.md`、`mobile-release-process.md`、`oncall-rotation.md`

通用规范里**不写**具体费率、金额阈值、字段名与事故编号，这些只出现在仓库专属文档里。所以「AI 说得出具体数值」只可能来自专属文档的检索命中，不可能从通用规范推导出来 —— 下面的判定口径就建立在这条边界上。

### 5.2 判定收紧规则

**A 类命中通用规范属正常，不算 RAG 起效；B 类与 C 类必须命中仓库专属文档才算。**

第 2 档（只关联通用规范）**允许**出现这样的表述：「这里违反了 `security-baseline.md` 要求的参数化查询」「导出接口没有行数上限，不符合 `data-handling-policy.md` 对批量导出的约定」。这是通用规范应有的效果，指出「违反了哪条通用规范」不构成分层失败。

但第 2 档**说不出**下面三样东西，说得出才算越界：

- **具体数值**：结算费率 0.6%、最小结算净额 100 分、bcrypt cost ≥ 12、导出行数上限
- **历史事故编号**：`INC-2024-07`、`BUG-001` 这一类
- **专属条款出处**：例如 `tenant-isolation.md` 第 2 节第 3 条「`tenant_id` 必须来自认证上下文，不得来自请求参数」

第 2 档若报出上述任意一项，说明关联范围没控制住（专属文档被误关联），或者模型在编 —— 两种情况都要复查，不能当作检索生效的证据。

### 5.3 三档对照实验

对同一个 PR 分支的 HEAD 审查三次，只改「关联哪些知识文档」，其余参数全部不变。这份口径与 `demo-repos/README.md` 第四节一致。

| 档位 | 关联文档 | 预期发现范围 |
|---|---|---|
| 1 | 无 | A 类，以及跨类那 3 条的 A 面（如 T13 前端硬编码 API Key）。少数形态明显的 B/C 类也可能被报出来 —— 例如 T2 整个漏掉 `tenant_id` 过滤 —— 但说不出依据，指不到具体条款或事故编号 |
| 2 | 仅 `knowledge-shared/` 5 份 | A 类，加上一部分 B 类的「违规」层面：能指出违反了哪条通用规范，但受 5.2 三条限制 |
| 3 | 全部 12 份 | B/C 类命中数应显著上升，输出里应出现专属文档名、章节号与历史事故编号 |

记录模板：

| 档位 | 关联文档 | Finding 数 | 其中 A 类 | B 类 | C 类 | 引用了干扰文档？ |
|---|---|---|---|---|---|---|
| 1 | 无 | | | | | |
| 2 | 仅 knowledge-shared 5 份 | | | | | |
| 3 | 全部 12 份 | | | | | |

第 3 档里 `knowledge-noise/` 的 3 份也在关联范围内，作用是让「检索排序合理」可被证伪：正常情况下它们不该被召回为 Finding 的依据。若某条 Finding 引用了 `oncall-rotation.md` 之类，那是检索排序的问题，应如实记录而不是略过。

### 5.4 RAG 生效 / 没生效的信号

**✅ RAG 生效的信号**
- 输出里引用了文档名或章节："根据 `settlement-rules.md`，手续费应向下取整"
- 指出了历史事故关联："这与 INC-2024-07 是同一类问题"
- 发现了**数值不一致**：代码写 0.8%，文档写 0.6%（P1）—— 这条纯靠代码绝对发现不了
- 指出了跨字段业务规则：`status` 与 `pay_status` 必须分别校验（M1）

**❌ RAG 没生效的信号**
- 只报出形态特征明显的通用问题：SQL 拼接（P10、T5）、URL 参数未编码（T17）、原型污染（T18），以及跨类条目的 A 面（如 T13 的「密钥不该写在前端」）
- 说"建议增加参数校验"这种放之四海皆准的话
- 完全没提到任何文档内容
- 第 3 档 Finding 数量涨了，但没有一条引到 `bug-history.md` 或专属规则文档

## 六、素材的诚实边界

需要说明的几点，避免过度宣称：

1. **缺陷是刻意植入的**，不是真实项目里自然产生的。这在演示场景下是合理的，但不要说成"在真实项目中发现了 43 个问题"。
2. **AI 不一定能全部命中。** 对照表是满分答案，实际命中率取决于模型能力与 RAG 检索质量。命中 B/C 类里的一半以上就已经是很好的结果。
3. **可能出现误报。** AI 也可能报出对照表之外的"问题"，需要人工判断。这恰恰是系统设计里「人工审批」环节存在的理由 —— 可以在答辩时主动讲这一点。
4. **三个仓库的代码可编译但不可运行**，没有数据库与容器依赖，部分类是演示用的桩。它们的用途是被审查，不是被部署。
5. **`knowledge-noise/` 是刻意放的干扰项**，目的是让「检索排序合理」可被证伪，答辩时应主动说明。
6. **通用规范是为演示编写的**，不是从真实企业规范摘录，不宣称对标某套行业标准。
7. **沙箱工具镜像本轮未构建**，补丁会被标记为不可审批并附原因，这是设计内的降级而非故障。

## 七、快速上手命令

```powershell
# 查看三个仓库的分支与提交
git -C F:\202605New\demo-repos\mall-order-service log --oneline --all
git -C F:\202605New\demo-repos\payment-settlement-service log --oneline --all
git -C F:\202605New\demo-repos\tenant-user-center log --oneline --all

# 查看 PR diff（这就是审查对象）
git -C F:\202605New\demo-repos\mall-order-service diff main..feature/promotion-batch-ship
git -C F:\202605New\demo-repos\payment-settlement-service diff main..feature/instant-settlement
git -C F:\202605New\demo-repos\tenant-user-center diff main..feature/ops-console
```

绑定到 RepoSage 时填这三个绝对路径，provider 选 `LOCAL`，分支 `main`，审查任务的目标提交填 PR 分支的 HEAD。知识库每个项目上传 12 份 `.md`（见 5.1）。

### 克隆到新机器时

演示仓库的**文件**在主仓库里，克隆能拿到；它们各自的 `.git` 不会被推送。在克隆出的目录里执行一次重建即可：

```bash
bash scripts/init-demo-repos.sh          # Linux / macOS / Git Bash
pwsh -File scripts/init-demo-repos.ps1   # Windows PowerShell
```

脚本把 author、committer 的姓名、邮箱与时间全部钉死，因此**任意机器重建出的 commit SHA 完全一致**，与本文第二节的表格对得上。加 `--verify` / `-Verify` 可以现场核对 6 个 ref 的 SHA（与 `scripts/demo-repos-expected-sha.txt` 逐条比对，六条全中才退出 0）。

脚本对已初始化的仓库幂等跳过 —— 它只看 `.git` 在不在。**若上一次运行中途失败留下了半成品仓库，脚本不会自愈**，需要先删掉 `.git` 再重跑：

```bash
rm -rf demo-repos/*/.git && bash scripts/init-demo-repos.sh --verify
```

素材的完整结构、patch 的作用与改动流程见 `demo-repos/README.md`。
