# RepoSage 功能测试素材说明

> 编写日期：2026-07-28
> 素材位置：`demo-repos/mall-order-service`、`demo-repos/payment-settlement-service`

本文件配套两个演示仓库使用。核心是**第四节的缺陷对照表** —— 它让你能判断 AI 的输出是真发现了问题，还是在合理编造。

---

## 一、素材设计思路

演示 AI 代码审查最容易失败的地方，是评委问一句："这些问题用普通静态扫描不也能查出来吗？"

所以两个仓库里的缺陷刻意分成三类：

| 类别 | 特征 | 演示价值 |
|---|---|---|
| **A 类：通用缺陷** | SQL 拼接、越权、硬编码密钥 | 证明基础能力，静态扫描也能发现 |
| **B 类：规则依赖** | 违反知识库里写明的业务规则 | **只有读了文档才可能发现** —— RAG 的核心价值 |
| **C 类：事故重犯** | 重复知识库 `bug-history.md` 里记录过的历史事故 | 最有说服力 —— AI 能说出"这和 BUG-001 是同一个问题" |

**演示时重点展示 B 类和 C 类。** 如果 AI 的输出里出现了"根据 `order-flow.md` 第 2 节"或"这与 INC-2024-07 是同类问题"这样的表述，RAG 就算真正跑通了。

## 三、演示流程

### 3.1 传统审查（本机可跑）

1. 创建项目 → 绑定仓库（provider 选 `LOCAL`，填绝对路径，分支 `main`）
2. 上传该仓库 `docs/` 下的 4 个文档到知识库，等状态变为 `INDEXED`
3. 创建审查任务，目标提交填 PR 分支的 HEAD，关联刚上传的文档
4. 查看报告，对照第四节的表核验

### 3.2 PR 流程

两个仓库都准备了 PR 分支，diff 是干净的「一个功能一批缺陷」：

```
mall-order-service:          main → feature/promotion-batch-ship
payment-settlement-service:  main → feature/instant-settlement
```

如果走 SCM Webhook 的完整 PR 流程需要 GitHub/GitLab 侧配合；本机演示可以直接审查分支 HEAD 提交，diff 内容是一样的。

## 五、怎么判断 RAG 真的起作用了

对照表里 **C 类 12 条、B 类 11 条** 是关键。判断标准：

**✅ RAG 生效的信号**
- 输出里引用了文档名或章节："根据 `settlement-rules.md`，手续费应向下取整"
- 指出了历史事故关联："这与 INC-2024-07 是同一类问题"
- 发现了**数值不一致**：代码写 0.8%，文档写 0.6%（P1）—— 这条纯靠代码绝对发现不了
- 指出了跨字段业务规则：`status` 与 `pay_status` 必须分别校验（M1）

**❌ RAG 没生效的信号**
- 只报出 SQL 注入、硬编码这类通用问题（A 类）
- 说"建议增加参数校验"这种放之四海皆准的话
- 完全没提到任何文档内容

**建议做一次对照实验**：同一个提交审查两次，一次关联知识文档、一次不关联，对比 Finding 数量与内容差异。这个对比在答辩时非常有说服力。

## 六、素材的诚实边界

需要说明的几点，避免过度宣称：

1. **缺陷是刻意植入的**，不是真实项目里自然产生的。这在演示场景下是合理的，但不要说成"在真实项目中发现了 25 个问题"。
2. **AI 不一定能全部命中。** 对照表是满分答案，实际命中率取决于模型能力与 RAG 检索质量。命中 B/C 类里的一半以上就已经是很好的结果。
3. **可能出现误报。** AI 也可能报出对照表之外的"问题"，需要人工判断。这恰恰是系统设计里「人工审批」环节存在的理由 —— 可以在答辩时主动讲这一点。
4. **两个仓库的代码不可编译运行**，部分类是演示用的桩。它们的用途是被审查，不是被执行。

## 七、快速上手命令

```powershell
# 查看两个仓库的分支与提交
git -C F:\202605New\demo-repos\mall-order-service log --oneline --all
git -C F:\202605New\demo-repos\payment-settlement-service log --oneline --all

# 查看 PR diff（这就是审查对象）
git -C F:\202605New\demo-repos\mall-order-service diff main..feature/promotion-batch-ship
git -C F:\202605New\demo-repos\payment-settlement-service diff main..feature/instant-settlement
```

绑定到 RepoSage 时填这两个绝对路径，provider 选 `LOCAL`。知识库上传各自 `docs/` 下的 4 个 `.md` 文件。

### 克隆到新机器时的注意事项

两个演示仓库的**文件**在外层仓库里，克隆能拿到；但它们各自的 `.git` 目录不会被推送，所以**分支和提交历史需要在新机器上重建**。

在克隆出的目录里执行一次即可：

```powershell
foreach ($repo in @("mall-order-service","payment-settlement-service")) {
    Push-Location "demo-repos\$repo"
    git init -b main
    git add -A
    git -c user.name="Demo" -c user.email="demo@example.com" commit -m "baseline"
    Pop-Location
}
```

这样能得到可绑定、可审查的本地仓库。若还需要 PR 分支的 diff 效果，参照第四节把对应文件在新分支上改回/改坏即可 —— 或者直接用外层仓库里保留的这份文件状态审查单个提交，缺陷对照表同样适用。
