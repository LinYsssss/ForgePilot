> 编写日期：2026-07-28
> 对应分支：`fix/track-a-core`
> 适用环境：本机（无 Docker、无 PostgreSQL、无 RabbitMQ）

## 一、先看清楚：这台机器上能测什么

这决定了测试清单的边界，不先说清楚会白跑一遍。

| 功能域 | 本机可测 | 依赖 |
|---|:---:|---|
| 登录 / 会话 / 权限 | ✅ | 无 |
| 项目管理、仓库绑定 | ✅ | dev 允许本地路径 |
| 提交浏览、Diff 查看 | ✅ | 本地 git |
| **传统代码审查（含 AI 输出）** | ✅ | mock AI，同步执行 |
| 知识库上传 / 检索 / RAG | ✅ | 内存向量模式 |
| 报告、问题列表、反馈 | ✅ | 无 |
| 分页、错误响应、traceId | ✅ | 无 |
| 对象级权限（越权测试） | ✅ | 无 |
| **Agent Run 全链路** | ❌ | **需要 RabbitMQ** |
| Outbox 自动调度 | ❌ | 需要 RabbitMQ |
| Patch 生成与沙箱验证 | ❌ | 需要 RabbitMQ + Docker |
| SCM Webhook 回写 | ❌ | 需要公网回调或内网穿透 |
| 数据库迁移 / 备份恢复 | ❌ | 需要 PostgreSQL |

**为什么传统审查能跑而 Agent 不能**：默认 `app.review.inline=true`，审查在请求线程内同步完成，不经消息队列；Agent 链路是 `Outbox → agent.step.queue → 消费者` 的事件驱动，没有 Broker 就停在 PENDING。

> 如果你想把 Agent 链路也测了，见第七节。

## 二、启动步骤

### 2.1 后端

首次运行必须提供种子账号，否则**没有任何账号可以登录**（系统没有注册接口，这是有意的）。

```powershell
$env:SEED_ADMIN_USERNAME = "admin"
$env:SEED_ADMIN_PASSWORD = "Reposage@2026Demo"   # 密码有最短长度校验，别用短的
$env:SEED_ADMIN_NICKNAME = "管理员"

Set-Location F:\202605New\backend
mvn -s .mvn/settings.xml spring-boot:run
```

默认已是 dev profile：H2 内存库、Flyway 关闭、AI 用 mock、RAG 用内存模式、允许绑定本地仓库路径。

启动后确认：
- `http://localhost:8080/api/actuator/health` 返回 UP
- 日志里没有 `跳过种子账号创建` 的告警（有的话说明密码太短）

**注意**：H2 是内存库，**重启即清空**。每轮测试要么一次跑完，要么接受重新准备数据。

### 2.2 前端

```powershell
Set-Location F:\202605New\frontend
npm run dev
```

打开 Vite 提示的地址（通常 `http://localhost:5173`）。

> 本机 Node 是 v24，而 `package.json` 要求 `>=20 <23`，可能出现 engines 告警 —— 这正是 P0-07 记录的版本冲突，不影响本轮功能测试，但要知道它存在。

## 三、测试数据（大部分已就绪）

### 3.1 演示仓库 —— 需要先重建一次

`demo-repos/` 下有**三个**演示仓库，它们的 `.git` 不入库，第一次使用前先重建：

```powershell
bash scripts/init-demo-repos.sh --verify          # Git Bash
pwsh -File scripts/init-demo-repos.ps1 -Verify    # PowerShell
```

`--verify` / `-Verify` 会把重建出的 6 个 ref 与 `scripts/demo-repos-expected-sha.txt` 逐条比对，六条全中才退出 0。重建后每个仓库 3 个提交：`main` 上 2 个（源码与构建描述、知识文档），PR 分支上 1 个（被审查的功能，缺陷全在这一次提交里）。

| 仓库 | 语言 | PR 分支 | PR 分支 HEAD | 缺陷编号 |
|---|---|---|---|---|
| `mall-order-service` | Java | `feature/promotion-batch-ship` | `e205e0e` | M1~M10 |
| `payment-settlement-service` | Java | `feature/instant-settlement` | `e51fad4` | P1~P15 |
| `tenant-user-center` | Python + JavaScript | `feature/ops-console` | `7e9e7a4` | T1~T18 |

绑定时填仓库的**绝对路径**（例如 `F:\202605New\demo-repos\mall-order-service`），provider 选 `LOCAL`，分支 `main`；审查任务的目标提交填 PR 分支的 HEAD，就能得到一个干净的「一个功能一批缺陷」的 diff。

三个仓库里的缺陷是刻意植入的，共 43 条，逐条核对见 `docs/演示素材与缺陷对照表.md`；素材结构、重建脚本与 patch 机制见 `demo-repos/README.md`。

### 3.3 需要你自己准备的：边界测试文件

Track A 加固了上传输入边界，要验证它需要几个"坏"文件。用下面的命令一次性生成：

```powershell
$d = "F:\202605New\.test-fixtures"
New-Item -ItemType Directory -Force $d | Out-Null

# 1. 伪装成 markdown 的二进制文件（应被拒绝）
[IO.File]::WriteAllBytes("$d\fake.md", [byte[]](0x4D,0x5A,0x00,0x01,0x02,0x00))

# 2. 非法 UTF-8（应被拒绝）
[IO.File]::WriteAllBytes("$d\broken.md", [byte[]](0xC3,0x28,0x61,0x62))

# 3. 超大文件，3MB（应被拒绝，上限 2MB）
[IO.File]::WriteAllText("$d\huge.md", ("x" * 3145728))

# 4. 不支持的扩展名（应被拒绝）
[IO.File]::WriteAllText("$d\payload.pdf", "hello")

# 5. 空白内容（应被拒绝）
[IO.File]::WriteAllText("$d\blank.md", "   `n`n  ")

# 6. 正常文件（应被接受，作为对照）
[IO.File]::WriteAllText("$d\good.md", "# 标题`n`n这是一段正常的中文正文内容。")
```

> `.test-fixtures` 不在 git 里，测完可以直接删。

## 六、已知现象，不要误判为 Bug

这几条是当前分支的**预期状态**，测试时遇到别当缺陷记：

1. **登录响应体里仍有 token 字段** —— Track B 的 B2 负责移除，让浏览器只依赖 HttpOnly Cookie。
2. **写请求不需要 CSRF Header** —— `app.security.csrf.enabled` 默认 false，合流阶段才统一打开。
3. **MQ 日志、审查任务、审查报告、知识文档四个接口返回分页信封** —— 前端若还按数组渲染会显示异常，Track B 的 B9 负责适配。
4. **前端可能残留硬编码的默认用户名和本机路径** —— B9 清理。
5. **Agent Run 创建后不推进** —— 没有 RabbitMQ，事件停在 Outbox 的 PENDING 状态。这是环境限制，不是 P0-01 复发（调度器已实现，但默认关闭且需要 Broker）。
6. **重启后数据全部消失** —— H2 内存库，符合预期。

## 七、如果想把 Agent 链路也测了

需要一个 RabbitMQ。无 Docker 的情况下有两个选择：

**方案 A：装原生 RabbitMQ**（需先装 Erlang）
装好后启动服务，然后：

```powershell
$env:AGENT_SCHEDULING_ENABLED = "true"       # 打开 Outbox 调度与恢复 watchdog
$env:RABBITMQ_LISTENER_AUTO_STARTUP = "true" # 打开消费者
$env:SEED_ADMIN_USERNAME = "admin"
$env:SEED_ADMIN_PASSWORD = "Reposage@2026Demo"
mvn -s .mvn/settings.xml spring-boot:run
```

届时可验证：Agent Run 创建后 1~2 秒自动进入下一 Step、Timeline 实时更新、Outbox 事件从 PENDING → SENT、Step 状态机推进。

**方案 B：装 Docker Desktop**（推荐）
一次解决更多问题 —— 除了 RabbitMQ，还能解锁：

- 3 个 skipped 的 Testcontainers 测试
- **V19/V20/V21 三个迁移的首次真实执行**（目前从未在任何数据库上跑过）
- A5 数据库完整性的预检与迁移
- Compose 整体启动、镜像扫描、备份恢复演练
- Patch 沙箱验证链路

如果时间只够做一件事，**装 Docker 的收益远大于装 RabbitMQ**。

## 八、测试结论怎么记

计划里有一条硬要求，建议照做：

> 测试结论必须区分"单元/组件测试通过""Testcontainers 集成测试通过""Compose 动态验收通过"。任何 skipped、未安装 Docker、未运行扫描器的项目都必须明确记为**未验证**，不能写成通过。

所以建议按三档记录：

- **已验证（手工）** —— 本文第四、五节实际走过的
- **已验证（自动化）** —— 410 个后端测试
- **未验证** —— Agent 全链路、Patch 沙箱、Webhook 回写、数据库迁移、备份恢复、镜像扫描

答辩时如实说明第三档，比含糊带过更有说服力 —— 能讲清楚"哪些没验证、为什么、怎么补"本身就是工程成熟度的体现。
