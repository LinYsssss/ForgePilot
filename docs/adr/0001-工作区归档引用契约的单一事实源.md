# ADR 0001：工作区归档引用契约的单一事实源

- 状态：已采纳
- 日期：2026-08-04
- 关联：审计条目 F-03/F-04/F-05（.trellis/tasks/08-03-r2-fix-sandbox-chain/）

## 背景

backend 与 sandbox-runner 之间靠 `SandboxJob.workspaceArchiveRef` 交接工作区归档。断链前的状态是：

- backend 侧两个 resolver 凭空拼出 `workspace://agent-run-{id}-{sha}.tar` 形式的引用，**没有任何组件真正把归档写进共享卷**（F-04）；
- Runner 侧 `WorkspaceArchiveResolver` 无条件拒绝含 `:` 的引用，即 backend 的真实产出 **必被拒绝**（F-03）；
- 两侧各写各的校验、测试各喂各的假数据（backend 测试断言 `startsWith("workspace://")`，Runner 测试只用 `repo.zip` 这类裸文件名夹具），漂移在测试里完全不可见；
- 工具镜像未配置时网关只软失败（ENVIRONMENT_INCOMPLETE），健康检查照常 UP（F-05）；
- e2e 验证时另发现审计未收录的上游断点：**RECEIVED 的 Run 无人派发首步**。步骤调度只在
  "上一步完成"时排下一步，首步不存在排入方，守门链路从未真正起跑（生产库 `agent_run`
  表为空即是佐证）。

根因不是格式选错，而是**契约没有单一事实源**。逐处对拍修得了这一次，防不了下一次。

## 决策

1. **契约收敛为一个编解码器**：`WorkspaceArchiveReference.encode（forAgentRun/forPatch）/parse`。
   引用是**裸文件名**——无 scheme、无路径分隔符；`parse` 承载全部语法安全规则（字符白名单、
   `..`、长度、前导 `-`/`.`），白名单本身即拒绝 `:` 与 `/`，scheme 类缺陷从结构上不可再现。
2. **落地形态取 C'（同构镜像）而非共享 Maven 模块（C）**：backend 与 sandbox-runner 是两个独立
   部署物、独立 pom，Runner 刻意保持依赖最小（它持有 Docker socket，是信任边界）。为一个类引入
   共享构件会把两个构建耦合起来，得不偿失。两侧各放一份**逐字节同构**的
   `WorkspaceArchiveReference`，同构性不靠编译期，靠测试（见下）。这与本仓库
   `SandboxJob`/`SandboxJobSigner` 既有的镜像先例一致。
3. **双向金标契约测试钉住线格式**：两侧用**同一批字面量**（`agent-run-42-abcdef1234567.tar`、
   `patch-9-<64hex>.tar`、完整拒绝集含历史断链格式 `workspace://…`）各自测试自己那份编解码器；
   任何一侧单方面改格式，先撞碎本侧金标测试。`SandboxJob` 两侧另有字段序快照测试
   （`workspaceArchiveRef` 钉在第 2 位），防 record 重排破坏 HMAC 规范化序列。
4. **backend 成为归档唯一生产者**：派发作业前 `git archive` 落盘共享卷（写 `.partial` 后原子改名，
   防 Runner 读到半个 tar）；compose 中 backend 读写挂载、Runner 保持 `:ro`，方向不可颠倒。
   正常完成的 Run 在发布步骤就地清理归档；FAILED/TIMED_OUT 保留供运维续跑，由 TTL 清扫兜底。
5. **F-05 升级为启动期快速失败**：生产 profile 下 `SANDBOX_TOOL_IMAGE` 必须非空且按完整
   64 位小写 hex digest 固定（`ProdSecretValidator`），digest 正则收敛到 `PinnedImageDigests`
   单一事实源（评测语料的形状校验与部署的严格校验分档共存）。
6. **首步派发用同事务领域事件**：`WebhookAgentRunService` 在建 Run 事务内发布
   `AgentRunCreatedEvent`，队列层 `AgentRunKickoffListener`（BEFORE_COMMIT）排入第 1 步——
   Run 与首步 outbox 事件要么一起提交、要么都不存在。不选直接注入
   `AgentStepPublisher`（把队列栈拖进 scm 层与其 JPA 切片测试），也不选后台扫描器
   （多一份轮询与延迟，且事务原子性已使"有 Run 无首步"不可能发生，扫描器没有存在必要）。

## 备选方案与取舍

- **A：逐处修改两侧现有校验对拍** —— 拒绝。不解决"没有单一事实源"的根因，下次改格式仍会漂移。
- **B：Runner 放宽接受 `workspace://` scheme** —— 拒绝。扩大解析面（scheme 解析、URI 歧义），
  且引用本质上就是共享卷里的一个文件名，scheme 不携带任何信息。
- **C：共享 Maven 契约模块** —— 理想但成本不匹配。两个独立 pom 需要引入聚合构建或发布私有构件，
  为一个 70 行的类改变部署物边界；且 Runner 依赖最小化是安全属性。若未来共享契约增多
  （第三个类起），应重新评估升级到 C。
- **C'（采纳）**：同构靠双向金标测试而非编译期保证——对本仓库规模，防线足够且不动模块边界。

## 后果

- 改归档引用格式必须同时改两份编解码器与两侧金标字面量，漂移在单元测试层即暴露。
- 同构是测试维护出来的：review 时两份 `WorkspaceArchiveReference` 的 diff 应始终为空
  （包名除外）。
- 存量 `workspace://` 引用不做迁移：断链期间没有任何 Run 能走通取证步骤，不存在需要兼容的
  在途数据。
- 共享卷有了生产者与生命周期（发布清理 + TTL 清扫），不再只增不减。
