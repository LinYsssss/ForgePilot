## 一、最终结论

RepoSage 已具备较完整的业务闭环：项目和仓库管理、Pull Request、知识库/RAG、传统代码审查、Agent 状态机、Finding、Patch、人工审批、SCM 回写、RabbitMQ、独立 Sandbox Runner、模型服务和可观测性。当前工程并非普通 Demo，后端测试和 Agent 领域设计已有较好基础。

但在正式答辩前，不能直接以“已经生产级”表述，原因是仍存在一个确定的核心链路阻断问题、若干可靠性和安全问题，以及 Docker 动态验收尚未完成。

最终策略不是全面重写，而是：

1. 先修复 Agent Outbox 发布闭环和任务恢复；
2. 再修复对象级授权、CSRF、SSRF、敏感数据与事务问题；
3. 然后修复 Docker、Node、依赖和 CI；
4. 最后补核心测试、答辩脚本和文档一致性；
5. 前端只做必要稳定性改造，不进行大规模视觉或框架重写。

完成本方案的 P0 和 P1 后，项目可以合理定位为：

> 一个采用模块化单体、事件驱动 Agent、事务 Outbox、RAG、人工审批和隔离执行机制的智能代码审查平台毕业设计；具备较完整的工程闭环和明确的安全边界，但不宣称支持敌对多租户或超大规模生产集群。

### 2.3 本轮复核后的结论修正

此前结论中有一项需要精确修正：Webhook payloadPreview 并非无限保存，WebhookDelivery 已限制为 1000 字符；但当前实现只截断，没有字段级脱敏、默认关闭策略和保留期治理。因此最终问题应表述为“已做长度限制，但仍存在敏感字段落库和留存治理不足”，不能再表述为“完整 Payload 无限制保存”。

CSRF 风险确认成立：后端是 STATELESS，但 TokenAuthenticationFilter 同时接受 Authorization Bearer 和 HttpOnly Cookie，前端 fetch 使用 credentials: include，而 SecurityConfig 全局关闭 CSRF。只要浏览器 Cookie 是有效认证来源，就必须建立 CSRF 防护或移除 Cookie 认证二选一。

二次复核又确认了以下遗漏，已纳入本文后续 P0/P1 和实施阶段：登录 JSON 仍返回 Token；现有 ProdSecretValidator 已拒绝部分默认密钥，但核心 Sandbox/Seed/Cookie/TTL 校验与自动化测试不完整；登录缺少独立防爆破与账号枚举缓解；Webhook 幂等存在“验签前查重 + 并发先查后写”问题；模型服务缺少正式测试且 status/reload 暴露边界不清；CI 未覆盖 Python、Maven、容器依赖扫描和最小权限；Git 子进程错误输出、输出读取和仓库资源上限仍需收口；Backend 与 Runner 的 ReplayGuard 使用无界进程生命周期 Set。

对象级授权二次抽查结果：Agent Run、AI Call Log、Feedback、Patch Approval 已能沿 Run/Task/Issue -> Project 绑定当前用户，暂未发现新的确定性 IDOR；MQ Log 仍是已确认缺陷。最终修复时仍必须用统一的反向授权测试矩阵覆盖所有 ID 型资源，不能仅凭人工阅读宣布“全部安全”。


## Phase 1：Agent Outbox 可靠发布闭环（最高优先级，1.5～2 天）

### 计划修改文件

- 新增 backend/src/main/java/com/example/codereview/agent/outbox/AgentOutboxScheduler.java
- 修改 AgentOutboxPublisher.java
- 修改 AgentOutboxRepository.java
- 修改 AgentOutboxEvent.java / AgentOutboxStatus.java
- 修改 backend/src/main/resources/application.yml
- 修改 RabbitMqConfig.java 或新增 RabbitTemplate Confirm 配置
- 新增 V19__agent_outbox_delivery_guards.sql
- 增加对应单元测试与 Testcontainers 集成测试

### 数据模型

建议增加：

- claim_token varchar(64)
- lease_expires_at timestamptz
- failed_at timestamptz
- 状态 FAILED
- max-attempts 配置，默认 8

状态机：

~~~text
PENDING --claim(token, lease)--> PROCESSING
PROCESSING --broker ack--> SENT
PROCESSING --nack/return/timeout--> PENDING(nextAttemptAt, attempt+1)
PROCESSING --lease expired--> PENDING
PENDING --attempt >= max--> FAILED
~~~

### 调度策略

- fixedDelay 500～1000ms；
- 单批 20～50 条；
- 每轮先回收过期 PROCESSING，再发布 PENDING；
- 调度方法本身不持有长事务；
- 多实例通过数据库 CAS + claim_token 保证同一事件只有一个有效认领者；
- markSent/markRetry 必须携带 id + claim_token + PROCESSING 条件更新，旧 Worker 不能覆盖新认领结果。

### Broker Confirm

启用：

- spring.rabbitmq.publisher-confirm-type=correlated
- spring.rabbitmq.publisher-returns=true
- spring.rabbitmq.template.mandatory=true

只有收到 Broker ACK 且消息未被 Return，才允许标记 SENT。NACK、Return、Confirm 超时都进入可控重试。

### 必测场景

1. PENDING 自动发布，不需要测试代码手动调用；
2. 不可路由消息不能标记 SENT；
3. Broker NACK/断开进入重试；
4. PROCESSING 超时被回收；
5. 旧 claim_token 不能完成新租约；
6. 达到最大次数转 FAILED；
7. 两个调度线程不能重复有效认领；
8. 真正 RabbitMQ Testcontainer 中完成发布与消费。

### 验收标准

- Agent Run 创建后 1～2 秒内自动进入后续 Step；
- Outbox 不存在无期限 PROCESSING；
- Broker 不可用时数据库不出现假 SENT；
- 恢复 Broker 后任务自动继续。

## Phase 2：Agent Step 短事务、执行租约与周期恢复（1.5～2 天）

### 计划修改文件

- 重构 AgentStepExecutionService.java
- 新增 AgentStepClaimService.java
- 新增 AgentStepCompletionService.java
- 修改 AgentStepRepository.java / AgentStep.java
- 修改 AgentRecoveryService.java
- 新增 V20__agent_step_execution_lease.sql
- 补充执行、并发、恢复测试

### 新执行结构

~~~text
Rabbit Consumer
  -> 短事务 claimStep
       校验 run/step/attempt
       状态置 RUNNING
       写 execution_token、worker_id、lease_expires_at
  -> 事务外 handler.execute
       Git / LLM / RAG / Tool / Sandbox / SCM
  -> 短事务 completeStep 或 failStep
       where execution_token = 当前 token
       更新 step/run
       同事务写下一条 Outbox
~~~

### 关键原则

- AgentStepExecutionService 本身去掉覆盖全方法的 @Transactional；
- 不把 JPA 实体长时间带到事务外进行延迟写回，转换成不可变执行上下文；
- 完成和失败使用 CAS；
- 不使用“固定 15 分钟且无续租”的粗粒度租约；建议初始 lease 2～3 分钟，Worker 每 30～60 秒以 execution_token 心跳续租；心跳停止后 watchdog 才可回收；
- 每类外部调用都必须有小于“当前租约 + 可续租窗口”的超时，整个 Run 仍受 max-elapsed 10 分钟总预算约束；
- Recovery 增加每 60 秒周期检查，而不是只在启动时执行；
- 重复消息返回 DUPLICATE_IGNORED 或 STALE_OR_ACTIVE_IGNORED，不重复执行业务副作用。

### 必测场景

- handler 执行时 TransactionSynchronizationManager 显示无活动业务长事务；
- 同一 Step 并发消息只有一个获得租约；
- Worker 崩溃后租约过期，可恢复；
- 旧 Worker 晚返回不能覆盖恢复后的新结果；
- 完成 Step 与创建下一条 Outbox 保持原子性；
- cancel、retry、external wakeup 原有语义不回归。

## Phase 3：权限、认证与 Web 安全加固（2～3 天）

### 3.1 MQ 日志 IDOR

新增 MqLogQueryService，Controller 不直接访问 Repository：

~~~text
CurrentUser -> ReviewTask -> Project -> owner/role check -> Query logs
~~~

返回规则：

- 无任务：404；
- 任务存在但无权限：403；
- 所有者/允许角色：200；
- 增加分页，默认 20，最大 100。

### 3.2 浏览器认证响应、登录防护与配置校验

浏览器端只保留 Cookie 认证链路：

- AuthResponse 删除 token 字段，登录接口只返回 userId、username、nickname、role；Controller 使用内部 LoginResult 中的 Token 写入 HttpOnly Cookie，内部 Token 不参与 JSON 序列化；
- 若未来需要 CLI/API Token，新增独立端点、作用域、过期时间和撤销机制，不复用浏览器登录响应；
- LoginRequest 增加长度边界；username 统一 trim/normalize 并只允许明确字符集，例如 [A-Za-z0-9._-]{3,64}；password 设置合理最小/最大长度，避免超长 BCrypt DoS；
- role 改为枚举/白名单，Seed 角色不允许环境变量注入任意字符串；生产 Seed 账号仅在显式 bootstrap 开关开启时创建，密码至少 12 位且复用正式密码策略，首次创建后立即关闭开关/清除环境变量；SameSite 只允许 Lax/Strict/None，None 必须同时 Secure=true；Token TTL 必须限制在合理范围；
- 扩展现有 ProdSecretValidator：保留其对 JWT_SECRET、TOKEN_ENCRYPT_KEY、DB_PASSWORD、RABBITMQ_PASSWORD 默认值的拒绝，并补充 SANDBOX_SIGNING_SECRET、启用功能所需的 SCM/Webhook 凭据、Seed 管理员开关/密码策略及对应启动测试；核心 HMAC/加密密钥使用密码学安全随机值，建议至少 32 字节；
- 登录使用独立的有界 TTL 计数器：每 IP 约 10 次/分钟、每规范化 username 约 5 次/5 分钟；成功后清理或衰减失败计数；
- 不存在用户也执行一次预计算 dummy BCrypt matches；用户名错误、密码错误、账号禁用统一对外返回 401“用户名或密码错误”，内部审计保留真实原因；429 返回 Retry-After；
- 自定义 Token payload 不再依赖冒号拼接的隐含约束：优先使用带 version 的结构化 JSON + HMAC；若答辩前不改格式，必须以用户名/角色白名单保证字段不含分隔符并补解析边界测试；
- 增加测试，明确登录响应 JSON 不含 token/accessToken，Cookie 具备 HttpOnly/Secure/SameSite，生产示例密钥会启动失败。

### 3.3 CSRF 最终选择

本项目浏览器端继续使用 HttpOnly Cookie Token，因此启用 CSRF：

- 使用 Spring Security 6.5 的 SPA CSRF 配置语义（csrf.spa() 或等价 SpaCsrfTokenRequestHandler）配合 CookieCsrfTokenRepository.withHttpOnlyFalse，不能只复制一个简化 repository 配置；
- 新增 permitAll 的 GET /api/auth/csrf，方法参数或响应必须实际解析 CsrfToken，确保 deferred token 被加载并写入 XSRF-TOKEN Cookie；
- 登录前先获取 CSRF Token；登录和退出会清除/轮换 Token，前端在登录成功后重新获取，退出后清空内存缓存；
- 前端从 XSRF-TOKEN Cookie 读取原始 Token，在所有非 GET/HEAD/OPTIONS 请求发送 X-XSRF-TOKEN；认证 Cookie 继续保持 HttpOnly；
- /api/webhooks/** 使用独立 HMAC/Token 验证并加入 CSRF ignore，不能因为忽略 CSRF 就跳过 Webhook 验签；
- MockMvc/组件测试覆盖：无 Header 写请求 403、正确 Header 成功、匿名登录 CSRF、登录后轮换、退出、旧 Token 失效、Webhook 不要求 CSRF 但错误签名仍被拒绝；
- Cookie 生产环境 Secure=true、HttpOnly=true、SameSite=Lax/Strict；不接受“SameSite 已足够”作为关闭 CSRF 的理由。

### 3.4 SSRF

新增统一 OutboundUrlPolicy，GitInputValidator 与 ScmHttpSupport 复用：

- 生产只允许 HTTPS；
- 主机必须在 GIT_ALLOWED_HOSTS / SCM_ALLOWED_HOSTS；
- 默认可含 github.com、gitlab.com，其他由环境变量显式加入；
- 拒绝 userInfo、fragment、控制字符和异常端口；
- DNS 解析后拒绝 loopback、private、link-local、multicast、unspecified、云元数据地址；
- 每次重定向重新校验；
- 本地路径只在 dev/demo profile 且位于配置的 demo 根目录；
- 单元测试覆盖 IPv4、IPv6、十进制/混合表示、localhost、169.254.169.254 和重定向。

### 3.5 Webhook

顺序调整：

~~~text
Nginx/应用层限制请求体与 Header 长度
-> 校验 event、deliveryId、installationRef 的长度和字符边界
-> 最小解析 installationRef 并查找启用的安装配置
-> 使用原始字节验签
-> 验签成功后以 (provider, deliveryId) 唯一键原子插入/ON CONFLICT
-> 冲突时读取既有结果，避免并发先查后写 500
-> 归一化和业务处理
-> 保存最小审计元数据并在同一业务事务内关联 runId
~~~

payloadPreview 默认不保存；只保留 payloadHash、eventType、action、status、installationId、runId、时间。未知安装、错误签名和未支持事件默认只计有界指标/安全日志，不把攻击者提供的正文写库；所有外部标识写库或日志前都要限长并去除控制字符。若确需调试，使用默认关闭的开关并做 JSON 字段脱敏和 1000 字符上限。增加 30 天清理任务或管理命令。

### 3.6 加密与密钥

- 现有 ProdSecretValidator 已拒绝 JWT_SECRET、TOKEN_ENCRYPT_KEY、DB/Rabbit 的已知占位值；整改重点是补齐 SANDBOX_SIGNING_SECRET、启用型凭据和自动化启动测试，并将核心 HMAC/加密密钥要求提升为至少 32 字节的密码学安全随机值；prod profile 继续禁止示例值实际生效；
- 对历史明文凭据执行一次性迁移；
- 迁移完成后 decrypt 遇到非 v1 格式直接失败，不再明文透传；
- 日志禁止输出 Token、Webhook Secret、Authorization、Cookie；
- .env.example 只放占位符，不放真实密钥。

### 3.7 可信代理与限流

- deploy/nginx.conf 将 X-Forwarded-For 设置为 remote_addr，不使用会继承客户端输入的 proxy_add_x_forwarded_for；
- backend 端口只绑定 127.0.0.1/容器内网，并配置受控 internal-proxies/forward-headers 策略；不能让客户端绕过 Nginx 直连后端再伪造代理头；
- 登录接口执行独立 IP + username 双维度限流；普通匿名请求按可信 IP，认证后按稳定 userId 限流；Webhook 可按来源 IP/installation 另设更高但有界配额；
- 继续使用单机内存限流，但文档说明不支持多实例全局配额。

### 3.8 浏览器安全头与安全审计

- Nginx 至少增加 Content-Security-Policy、X-Content-Type-Options、Referrer-Policy、Permissions-Policy；HTTPS 环境启用 HSTS；
- 当前前端未发现 v-html/innerHTML，继续禁止把模型输出、Markdown、Diff 作为原始 HTML 注入；如未来需要富文本，必须使用严格白名单净化；
- 同源部署不开放宽泛 CORS；若开发环境需要跨域，只允许明确 origin、method、header，且 credentials=true 时禁止通配符 origin；
- 建立统一安全审计事件：登录成功/失败、退出、凭据新增/修改、项目绑定、Patch 审批、SCM 发布、管理员操作、对象级拒绝；
- 审计记录 actorId、action、resourceType/resourceId、result、traceId、时间和来源 IP 摘要，不记录 Token、Cookie、Webhook Secret、完整 Patch 或 Payload；
- Actuator 对公网仅公开 health；prometheus 只允许容器内网抓取；Compose 部署不再把 backend 管理端口映射到宿主机。

### 3.9 模型服务最小安全边界

- 新增 model-service/tests/test_main.py、test_train_model.py 和 requirements-dev.txt（pytest、pip-audit 等仅开发/CI依赖），避免把测试工具塞入运行镜像；
- model-service 不映射宿主机 8000 端口，只通过 Compose 内网供 backend 调用；
- /model/status 只返回 UP/DEGRADED、modelLoaded、modelVersion，不返回 MODEL_PATH 绝对路径和原始异常；原始异常仅写脱敏日志；
- /model/reload 默认删除或仅在 dev profile 开启；如必须保留，要求内部共享 Token/mTLS，且不能经 Nginx 暴露；
- PredictRequest 对 diffText、filePath、changeType 设置明确 max_length；Nginx/ASGI 限制请求体、并发数和超时；
- joblib 模型只能从只读、可信构建产物加载，并校验版本/哈希；不得加载用户上传的模型文件；
- health 区分“服务存活”和“模型已加载”；允许规则降级时返回 DEGRADED 并打指标，不把静默 fallback 当作完全健康。

### 3.10 Sandbox 重放缓存边界

Backend 与 Runner 两端的 SandboxReplayGuard 都从无界 ConcurrentHashMap Set 改为有界 TTL 缓存：TTL 至少覆盖消息 expiresAt 与允许的时钟偏差，最大容量按峰值任务量配置；记录 nonce 时使用原子 put-if-absent 语义。测试覆盖并发相同 nonce、过期淘汰、容量淘汰、空 nonce 和时钟边界。当前单实例部署只宣称进程内防重放；未来多 Runner 才改用 Redis/数据库共享 TTL 键。

## Phase 4：事务、数据库、分页和异常一致性（1.5～2 天）

### 4.1 Knowledge 上传

先建立明确的输入边界：

- 在 application.yml 显式配置 multipart max-file-size/max-request-size，并在业务层再次校验，例如单文件 2 MiB；
- 只允许 .md/.txt，但扩展名不能作为唯一依据：拒绝 NUL/明显二进制内容、非法 UTF-8、空内容和超长文本；Content-Type 仅作辅助判断；
- originalFilename 只保留清洗后的 basename 用于展示，绝不能拼接成本地文件路径；
- readText 避免无边界 getBytes，按上限读取并给出稳定错误码；

将 upload 拆成：

1. 短事务创建文档，状态 PENDING；
2. 事务外执行 embedding/vector index；
3. REQUIRES_NEW 标记 INDEXED；

禁止在一个事务内执行整个 embedding 流程，也不能 markFailed 后立即被同一事务回滚。

### 4.2 数据库约束

建议新增：

### 4.3 分页

优先分页接口：

- Agent Run / Step / Finding；

### 4.4 异常响应

统一格式：

~~~json
{
  "code": "AGENT_OUTBOX_PUBLISH_FAILED",
~~~

### CSRF、认证与 SSE 生命周期

前端必须按一个可测试的状态机实现，而不是“每次请求临时猜测”：

1. 应用初始化或进入登录页时 GET /api/auth/csrf，读取 XSRF-TOKEN Cookie；
2. 登录 POST 携带 X-XSRF-TOKEN，成功响应 JSON 不接收也不保存 Token；认证仅依赖 HttpOnly Cookie；
3. 登录成功后重新 GET /api/auth/csrf，使用轮换后的 Token；
4. 所有非 GET/HEAD/OPTIONS 请求自动携带最新 X-XSRF-TOKEN；
5. 退出 POST 携带 CSRF；无论退出响应是否成功，都在前端 finally 中关闭 SSE/轮询、清理用户和敏感页面状态，再回到登录页；
6. 服务端认证 Cookie 过期或收到 401 时只触发一次全局失效流程，立即关闭 SSE/轮询并跳转登录，防止并发请求形成跳转风暴；随后重新获取匿名 CSRF Token；
7. SSE 使用同源 Cookie 认证，不允许把 Token 放在 query string、localStorage 或日志中；401/退出/切换项目时立即 close()；异常断线采用有上限的指数退避，超过阈值后回退轮询；
8. 403 显示“无权访问”且不得自动登出；409 展示业务冲突并刷新相关资源；429 读取 Retry-After 禁用按钮并显示剩余时间；5xx 展示 traceId 供排查，不展示堆栈。

如果使用 fetch，需统一 credentials: 'include'；CSRF Cookie 的读取函数只读取 XSRF-TOKEN，不读取认证 Cookie。不得将服务端 Token 写入 localStorage/sessionStorage/Pinia 持久化。

### 有限拆分

App.vue 长度是维护性问题，但不做全量重写。优先拆：

- services/review-api.js
- services/agent-api.js
- services/project-api.js
- composables/useReviewWorkspace.js
- composables/useAgentPolling.js

现有 AgentReviewWorkspace 等组件继续复用。只有当拆分能降低本次修改风险时才进行，不以“行数好看”为目标。

### 前端测试

引入 Vitest + Vue Test Utils；MSW 可选。至少覆盖：

- 初始化获取 CSRF、登录请求携带 CSRF、登录成功后 Token 轮换；
- 登录响应没有 token/accessToken，前端没有 localStorage/sessionStorage Token；
- 登录成功、失败、401 全局失效且只执行一次；
- 403 不清空正常登录态、不显示他人数据；
- 409 刷新冲突资源；429 解析 Retry-After；5xx 展示 traceId；

不要求全面 UI 改版，不要求移动端完整适配；确保答辩常用的 1366×768 和 1920×1080 分辨率下核心操作可见、键盘焦点清晰、颜色对比基本可读。

## 十、答辩高频问题与标准回答

### 为什么不拆微服务？

当前规模下，模块化单体能减少分布式事务和部署复杂度；高风险、资源隔离要求不同的 Sandbox Runner 和模型服务已独立。未来业务量达到明确边界后再按领域拆分，比为了形式提前微服务化更合理。

### Outbox 如何降低消息丢失风险并实现可恢复投递？

业务状态和 Outbox 在同一数据库事务提交；调度器使用数据库租约认领；RabbitMQ Confirm/Return 成功后才标记 SENT；失败可重试，租约过期可恢复；消费者使用 step attempt、execution token 和业务唯一键保证幂等。系统采用至少一次投递，不宣称魔法式“绝对恰好一次”。

### 如何避免 AI 幻觉直接修改代码？

模型结果先经过结构化解析、规则/策略校验、Finding 去重和证据验证；Patch 在 Sandbox 中验证；最终发布需要人工审批。AI 是建议生成器，不是无约束执行者。

### Sandbox 是否绝对安全？

不是。系统通过独立 Runner、签名任务、命令白名单、无网络、非 root、只读根、资源限制降低风险；但 Docker Socket 仍是宿主高权限边界，因此当前定位为可信单机课程设计，不作为敌对多租户平台。

### 如何保证用户不能访问其他人的项目？

认证只确认“你是谁”，Service 层对象授权确认“该资源是否属于你”；MQ 日志、Run、Finding、Patch 等全部沿资源链校验 Project owner，并有 403 反向测试。

### 为什么不能承诺零缺陷？

软件工程不能证明绝对零缺陷。项目通过威胁建模、自动化测试、依赖扫描、动态验收、监控和可恢复设计，把已知高风险问题关闭，并让剩余风险可发现、可解释、可恢复。

### 13.1 Outbox 调度器与租约边界

文件：AgentOutboxScheduler.java、AgentOutboxPublisher.java、AgentOutboxRepository.java。

~~~java
@Component
@RequiredArgsConstructor
class AgentOutboxScheduler {
    private final AgentOutboxLeaseService leases;
    private final AgentOutboxPublisher publisher;

    @Scheduled(fixedDelayString = "${app.agent.outbox.fixed-delay-ms:1000}")
    void tick() {
        leases.requeueExpired();       // 独立短事务
        publisher.publishAvailable(); // claim 短事务，网络发布在事务外，结果 CAS 回写
    }
}
~~~

关键不是 @Scheduled 本身，而是：claim、Rabbit 网络调用、complete/retry 三段分离；所有回写都带 id + claimToken + PROCESSING 条件。Confirm 超时后允许重发，因此消费者必须幂等，整体语义为至少一次。

### 13.2 Agent Step 去长事务

文件：AgentStepExecutionService.java、AgentStepClaimService.java、AgentStepCompletionService.java。

~~~java
public ExecutionOutcome execute(AgentStepMessage message) {
    var claim = claimService.claim(message); // @Transactional 短事务
    if (claim.isEmpty()) return ExecutionOutcome.ignored();

    var ctx = claim.get(); // 不可变 DTO，不把托管 Entity 带出事务
    try {
        var result = handlerRegistry.required(ctx.stepType()).execute(ctx); // 无数据库事务
        return completionService.complete(ctx.executionToken(), result);   // @Transactional + CAS
    } catch (Exception ex) {
        return completionService.fail(ctx.executionToken(), safeError(ex));
    }
}
~~~

complete/fail 更新行数必须为 1；为 0 表示租约已失效，旧 Worker 结果只能丢弃，不能覆盖新执行者。

### 13.4 CSRF 配置与前端请求

文件：SecurityConfig.java、AuthController.java、前端 api/client.js。

Spring Security 6.5 的 SPA 配置应使用 SPA 请求处理语义，而不是只设置 Cookie repository：

~~~java
CookieCsrfTokenRepository repository =
    CookieCsrfTokenRepository.withHttpOnlyFalse();

http.csrf(csrf -> csrf
    .csrfTokenRepository(repository)
    .spa()
    .ignoringRequestMatchers("/api/webhooks/**"));
~~~

如果项目实际依赖的 Spring Security 6.5.x API 签名与上述 DSL 不同，使用等价的 SpaCsrfTokenRequestHandler 配置；最终以编译通过和 MockMvc 覆盖 BREACH/XOR、登录/退出轮换为准，不能为了套用示例降级成不完整配置。

受控端点必须实际解析 deferred token：

~~~java
@GetMapping("/api/auth/csrf")
@ResponseStatus(HttpStatus.NO_CONTENT)
public void csrf(CsrfToken token) {
    token.getToken(); // 强制解析 deferred token，但不把值放进 JSON
}
~~~

该 GET 端点设为 permitAll；显式读取 getToken() 会触发生成并写入可由前端读取的 XSRF-TOKEN Cookie，但响应体不暴露 Token。前端统一客户端：

~~~javascript
const unsafe = !['GET', 'HEAD', 'OPTIONS'].includes(method.toUpperCase())
if (unsafe) headers.set('X-XSRF-TOKEN', readCookie('XSRF-TOKEN'))
return fetch(url, { method, headers, credentials: 'include', body })
~~~

登录前获取 Token，登录成功后重新获取，退出请求也携带 Token；退出/401 后关闭 SSE 与轮询并清理敏感状态。认证 Cookie 仍保持 HttpOnly，Webhook 只忽略 CSRF，不忽略自身 HMAC/Token 验签。

### 13.10 Git 子进程输出、超时与错误脱敏

