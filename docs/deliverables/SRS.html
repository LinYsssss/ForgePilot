1引言

1.1 编写目的

本文档确定 ForgePilot 应当做什么、不做什么，以及每条要求凭什么算作已实现。 它服务三类读者：

  • 评审者——按第 7 章的追溯矩阵逐条核对需求是否落地。
  • 开发者——在动手前确认某项改动属于范围之内还是之外。
  • 接手者——理解现有约束的来源，避免把有意为之的设计当成缺陷去「修」。

1.2 与其他文档的关系

本项目遵循每类事实只在一处定义的原则。本文档定义的是需求条目及其编号； 其余事实在别处定义，本文只引用，不复述：

1.3 需求编号约定

  • FR-模块字母序号——功能需求。模块字母：A 账户会话、B 项目成员、C 需求管理、D 项目知识、E 仓库与 PR、F 代码审查、G 评测。
  • NFR-类别字母序号——非功能需求。类别字母：P 性能容量、S 安全、R 可靠性、M 可维护性、C 兼容可移植。
  • 编号一经分配不再重用。需求作废时保留编号并标注，不删除、不顶替。

1.4 术语

本文使用的项目术语，完整解释见配套文档《ForgePilot 使用与代码手册》第 13 章「术语速查」。此处只列最高频的四个：

术语含义
Requirement / 需求一条研发需求。身份稳定，正文存在不可变的 Revision（修订）里。
AC / 验收条件Acceptance Criterion。附属于某次修订，携带跨修订稳定的 ac_key。
Review / 审查针对一组冻结输入（PR 的某个 head + 某份 diff + 某一版需求）的一次 AI 审查。
Finding / 发现一次审查报出的一个具体问题，带三个确定性哈希以支持跨轮次匹配。

2项目概述

2.1 要解决的问题

通用 AI 代码审查工具只能看到 diff，因此只能回答「这段代码写得好不好」。 它无法回答另一个在真实研发中更常被问到的问题：这次改动有没有做到需求要求的事。

ForgePilot 的做法是把三样东西一起送进模型上下文：变更 diff + 该 PR 关联的需求与验收条件 + 项目知识库检索片段。 审查结论因此能落到具体验收条件上，而不只是代码风格。

2.2 系统边界

ForgePilot 是一个Web 应用，通过 webhook 与 GitHub / GitLab 集成，通过 HTTP 调用 OpenAI 兼容的模型服务。它不做以下事情，这些是边界而非未完成项：

  • 不克隆代码仓库，不执行 Git 命令——只消费 provider API 返回的 patch。
  • 不修改代码、不提交、不合并——AI 只产出分析结果。
  • 不推进任何业务状态——所有状态流转由人触发。

2.3 运行环境

层技术说明
后端Java 21 · Spring Boot 4.1模块化单体，8 个顶层业务包
数据库PostgreSQL 15 + pgvector 0.8.6业务事实源；Flyway 管理 schema

模型服务OpenAI 兼容端点base URL 由部署配置，代码不硬编码任何 host

2.4 设计约束

以下约束不是实现细节，而是需求层面的硬性限制，违反即视为需求未满足：

  • 模块依赖单向无环，由 ArchUnit 在每次构建时强制。
  • 每个项目内引用都携带 project_id，不存在「先按裸 id 查再检查项目」的读路径。
  • 只有一个 Review Engine，只有一个 AI 网关出口。
  • 数据模型 20 张表；新增表需要业务事实与记录在案的理由。
  • Flyway 迁移只追加，已应用的迁移逐字节不可变。

一条容易被忽略的权限设计

Finding 的「认领」只有 DEVELOPER 能做，LEADER 也不能。 这不是遗漏——认领意味着「我来修」，是本人动作。因此系统里没有「指派 Finding」这个端点。

4功能需求

编号需求验收判据

FR-A6「用户名不存在」与「口令错误」不可区分两种失败的响应体逐字节相同，且 traceId 为空

FR-B5覆盖成员的角色集合角色集合不得为空
FR-B6移除成员（硬删），并撤销其在需求指派、Finding 认领、SCM 绑定三处的活权限三处引用全部撤销；漏撤销时删除被外键以 23503 拒绝，而非静默通过

FR-C7首次指派与 READY → IN_DEVELOPMENT 同事务；后续更换负责人不再改变状态—

4.4 项目知识（FR-D）

编号需求验收判据
FR-D1上传 .txt/.md，切片并生成向量单文件上限 5 MB；失败文档显示真实失败原因，不显示为「处理中」或「已就绪」
FR-D2一次选择多个文件上传，逐文件报告成败每个文件独立一次调用、独立一个事务；一个失败不影响其余
FR-D3项目内语义检索，TopK = 8project_id 为 SQL 硬过滤；别的项目的行既不出现也不影响排序
FR-D4需求附件与公共知识分离展示；附件可显式提升为公共知识提升采用复制而非改写，原附件保留归属与历史
FR-D5展示切片数、已嵌入数、向量维度、Embedding Profile 与索引状态任何位置不展示原始向量，无手工向量查询台
FR-D6LEADER 可删除公共知识文档同事务显式删除其切片与向量；需求附件来源的文档被拒绝删除，并说明去哪解除附件
FR-D7拒绝与本项目已有维度不一致的向量写入这是唯一防线：一行维度不匹配会使该项目全部检索以 22000 失败

4.5 仓库接入与 PR（FR-E）

编号需求验收判据
FR-E1每个项目一个活动 GitHub 或 GitLab 仓库，可注册与修改一旦有 PR 存在，仓库稳定身份即冻结，而 API 基地址仍可变更
FR-E2访问令牌与 webhook 密钥只写不回显，静态加密存储响应体、页面、日志任何位置不出现凭据；修改时留空表示保持原值
FR-E3每个账号可验证多个 SCM 身份，各带标签与用途验证使用一次性个人 Token，提交后清空、不回显、不持久化
FR-E4成员为项目选择自己的兼容身份；可选 LEADER 严格审批每成员每项目最多一个活动绑定；LEADER 不能替他人选择身份；待审批期间不参与「本人 PR」权限
FR-E5Webhook 对原始请求字节做认证HMAC 覆盖原始字节；常数时间比较；GitLab 新版签名存在但验不过时绝不降级到旧版
FR-E6认证通过后回头向 provider 做一次权威读取不信任载荷内容；权威字段缺席、为 null 或为容器时显式失败而非存下空串
FR-E7标题或分支名中的 REQ-<id> 自动关联需求，人工可纠正解析失败或跨项目引用不阻塞入库，只是保持未关联
FR-E8关联变更与其审计记录写在同一事务不存在「关联已变但无审计行」或「有审计行但变更未提交」的状态
FR-E9每次出站调用前校验目标 URL 是否被本部署允许每次调用重新校验，因为该配置可由 LEADER 修改而策略可能已收紧
FR-E10乱序到达的旧投递被丢弃带更旧时间戳的快照不覆盖较新状态
FR-E11变更文件清单连同 patch 整份存储超出上限时入库显式失败，不静默截断

4.6 代码审查（FR-F）

编号需求验收判据
FR-F1PR 变更自动创建共享的 PENDING Review与更新 PR 行同一事务；不存在「PR 已更新但 Review 缺失」的已提交状态
FR-F2Review 创建时冻结上下文：head SHA、diff 指纹、需求修订、变更文件清单数据库触发器拒绝事后修改身份列，并拒绝项目与上下文不一致的写入
FR-F3并发抢占围栏：同一次 Review 同时只有一个 worker 能执行抢占为单条原子条件更新；失败方匹配零行；过期 worker 不得完成、失败、续租或追加 Finding
FR-F4大 PR 分批送模型；批次只报告候选与证据，绝不给出裁定小 PR 与大 PR 走完全相同的路径，无捷径分支
FR-F5综合阶段对被审查修订的每一条 AC 给出裁定模型跳过的填为 NOT_FOUND 并记警告；沉默的模型无法缩短报告
FR-F6结构非法的回答获得恰好一次格式修复；仍失败则整次 Review FAILED绝不产出「成功但为空」的报告；FAILED 的 Review 在类型上没有 Report
FR-F7覆盖清单显式标注被截断、已审查与未审查的文件「空的未审查清单」与「缺失的未审查清单」保持可区分；缺失 manifest 不显示为「全部覆盖」
FR-F8Finding 携带三个确定性哈希，支撑跨轮次去重、抑制与血缘三个哈希都不覆盖模型散文（说明、建议、置信度）
FR-F9Finding 人工生命周期：认领 → 标记已修复 → 复核通过/打回；可填备注按角色的按钮矩阵与后端一致；审计永久保留，成员已删时回退数字 id
FR-F10Review 终局裁定为一次性，只允许 PENDING → APPROVE | REQUEST_CHANGES前置条件不满足时列出具体原因
FR-F11新 head 产生新 Review，前次结果保留为历史页面显示「审查已过期」；不自动重审，由人按权限触发
FR-F12停滞的 Review 由对账调度恢复其唯一查询的 FROM 子句只有 review 一张表，因此不可能补建从未创建过的 Review
FR-F13模型置信度只记 HIGH/MEDIUM/LOW 三档不进任何哈希、不参与任何自动门禁或状态流转；UI 与其他三个标记分开呈现
FR-F14REQUEST_CHANGES 对该 head 形成闸门每次读取时现算而非缓存，因为 force-push 会改变 head
FR-F15SUPPRESSED 的 Finding 位于独立折叠组，可按真实规则重开重开只在 continuity = SUPPRESSED 时允许；普通驳回对任何角色都不可逆
FR-F16证据工作台展示审查时的完整上下文含 Requirement、AC、PR 身份、召回知识集合、改动文件与 unified diff；原始 JSON 只在底部折叠诊断区
FR-F17知识区域只称为「本 Review 召回的知识证据集」不声称某一块知识直接支持某一条 Finding

4.7 评测（FR-G）

编号需求验收判据
FR-G1三臂对照实验：Diff / +需求与 AC / +项目知识三臂只改变暴露给模型的上下文，输出走同一 run contract
FR-G2确定性评分器，分别报告各项指标不合成单一综合分；分母为零输出 null 而非伪造为零
FR-G3配置冻结与一次性 holdout 台账模型面与评分文件由内容哈希钉住；holdout 只运行一次，不可重跑
FR-G4无凭据条件下从保留的原始输出重算全部指标重算不发起任何 provider 调用，不读 API key
FR-G5失败与未运行的 case 保持显式工具绝不把它们改写成空的成功预测；COMPLETED 且零 finding 是有效空结果

在 4,101,304,320 字节主机上：backend 768 MiB（heap 384 / direct 128 / metaspace 128）， PostgreSQL 512 MiB，连接池 5。两个并发 Review 各含 300 文件与 3,989,101 字符的规范化清单， 经生产网关、60,000 字符批次、校验、持久化与围栏全链路完成，共 152 次模型调用； 两条均 COMPLETED、execution_attempt=1、truncated=false。 采样峰值 heap 83,167,816 字节，连接池 active/pending 1/0，无 OOM、无重启。

5.2 安全（NFR-S）

编号需求验收判据
NFR-S1口令使用适合存储口令的慢哈希BCrypt；数据源口令无默认回退值
NFR-S2写请求需携带 CSRF 令牌缺失或错误的令牌是访问被拒的唯一来源；令牌经 Cookie 下发、Header 回显
NFR-S3凭据静态加密provider token 与 webhook 密钥加密存储；不做密钥轮换（需要密钥版本列与重加密扫描，属新结构）
NFR-S4Webhook 认证使用常数时间比较被截断的摘要只判为不相等，不泄露长度信息
NFR-S5出站请求受策略控制防止诱导服务器访问内网地址
NFR-S6发往模型的内容先做敏感信息脱敏与预算裁剪掩码疑似凭据；该处理为纯函数，不因「看起来含 token」拒绝整份文档
NFR-S7需求文本、文档、PR 标题与代码注释全部视为不可信数据—
NFR-S8错误响应不泄露存在性跨项目资源与不存在的资源同答；两种登录失败逐字节相同
NFR-S9公开端点的任何失败不得以堆栈逃逸校验完成前的每种失败都答成同一种「无法验证」
NFR-S10模型调用留下审计记录的是「一次尝试」，重试留两行；超时与失败分开记录
NFR-S11人工决策全部留痕Finding 每次流转、PR 关联每次变更、三类资源每次删除均永久记录
NFR-S12无需认证即可触达且做昂贵工作的端点须限流登录 20 次／分、注册 5 次／10 分、webhook 60 次／分，均按对端地址；限流装在认证之前，被限的登录不付 BCrypt 代价。不采信 X-Forwarded-For——它可伪造，采信等于取消限流，代价是代理之后全部客户端共享一份配额

5.3 可靠性（NFR-R）

编号需求验收判据
NFR-R1webhook 重复投递是幂等的同一快照重复到达不产生重复 PR 行或重复 Review
NFR-R2崩溃的 worker 不得永久占住 Review租约过期后可被重新抢占；重新抢占同事务丢弃前次 Finding
NFR-R3报告不得比它所属的 Review 活得更久写结果与状态转换同事务，租约丢失即整体回滚
NFR-R4模型不可达不导致无限重试标记 FAILED 并停下等人工重试
NFR-R5约束冲突不得被捕获后在同一事务内继续执行冲突到达统一处理器时其事务必定已回滚
NFR-R6并发写入由行锁串行化LEADER 转移、仓库重配置、PR 同步均先取行锁

5.4 可维护性（NFR-M）

编号需求验收判据
NFR-M1模块依赖单向无环由 ArchUnit 在每次构建强制；反向需求只能用只读 facade 或进程内事件
NFR-M2数据库约束由数据库本身强制，而非仅由服务层约束测试通过 JdbcTemplate 绕到应用代码之下写入，并点名期望的 SQLState
NFR-M3数据库行为只对真实 PostgreSQL + pgvector 验证禁止内存数据库替代、禁止「Docker 缺失就跳过」、禁止 @Disabled 与 assumeTrue
NFR-M4Flyway 迁移只追加已应用的迁移逐字节不可变——改动会使部署以校验失败无法启动
NFR-M5测试零跳过跑不起来的测试必须让构建失败
NFR-M6前端不引入状态管理库、UI 组件库或 HTTP 客户端库由 lint 策略检查禁止依赖清单
NFR-M7颜色只在设计令牌文件中定义lint 拒绝其他文件中出现原始色值

5.5 兼容与可移植（NFR-C）

6明确不做的范围

以下项目不是未完成的需求，而是明确划在范围之外的决定。 把它们列进本文档，是为了让「没做」与「漏做」可区分。

不做理由
通用聊天助手、对话历史、流式会话、多轮记忆产品定位是审查而非对话。AI 能力全部为一次性调用。
Agent、Planner、Tool、Memory、自动改代码或提交AI 不改变任何业务状态，这是权限模型的基础。
多仓库、多 SCM 连接、通用 Commit 审查一个项目一个活动仓库是当前的边界。
本地 clone、Git CLI只消费 provider API 返回的 patch。
相关代码语义检索、代码向量库、AST / 调用图知识库只索引文档，不索引代码。
消息队列、Redis、微服务、独立沙箱模块化单体足以承载当前边界。
第二个 Review Engine、第二条流水线唯一引擎是架构不变量。
向量索引见下条独立说明。
额外一级菜单六入口是导航契约，由测试锁定。
向量索引是已决策的非目标，不是缺失的迁移

冻结的 Embedding Profile 是 4096 维，超过 pgvector 0.8.6 全部精确索引形态的维度上限。 能建出来的两种形态——二值量化（压成 1 bit 按汉明距离排序）与截断到前 2000 维——都是有损预筛， 采用它们还必须再补一个 rerank 阶段。

而在 MVP 语料规模下，顺序扫描给出的就是精确余弦序。 这三件事被写成测试（KnowledgeVectorIndexTest）而不是研究笔记， 因为这条论据会过期：pgvector 一旦放宽维度上限，该测试就会失败，而那次失败正是回来重新决策的信号。

8已知限制

本章列出已实现但有边界的部分。它们不是缺陷，但在评价系统能力时必须计入。

限制 1 · 评测结论的准确范围

三臂评测比较的是上下文构成，不是某条检索管线。评测 runner 自行组装上下文、 对后端零引用；第三臂把 case 的知识文件全文渲入 prompt， 既不做 embedding 调用也不做 TopK 检索。

因此结论应表述为「把需求与项目知识放进上下文有用」， 不能表述为「ForgePilot 的 pgvector 检索有效」。检索是产品能力、有自己的测试， 但不是这组数字所评价的对象。

限制 2 · 评测样本规模

holdout 为 12 例，且缺陷为手工构造。报告因此给出 95% Wilson 置信区间而非点值， 并明确声明这两点限制泛化能力。holdout 只运行过一次，按约定不可重跑。

限制 3 · 归档不冻结写入

project.status 目前不 gate 任何写路径，因此归档只是从工作区列表收起， 该项目的需求、知识、仓库与审查仍然可写。 将归档变为只读闸门需要在五个模块的写入口增加检查，属范围外。

限制 4 · 测试套件存在潜伏的类执行顺序依赖

已确认：仅重命名 BatchOneApiTest 类名（无任何代码行变化） 会导致其 4 个测试在完整构建中失败，而单独运行该类 5/5 全绿。 失败点为匿名请求未下发 CSRF cookie。原因是测试框架默认的类执行顺序改变后， 某个先运行的类留下了影响状态。根因尚未定位。

当前处置：保留历史类名不改，套件维持全绿。 本限制记录在此，以免后续新增测试类时被误判为新引入的缺陷。
