1运行拓扑

下面这条链是 2026-08-28 在部署机上实际核对过的，不是设计意图：

公网
  │  Cloudflare 边缘
  ▼
cloudflared            宿主机 systemd 服务，不是容器
  │  systemctl status cloudflared
  ▼
127.0.0.1:18081        docker-proxy，只监听回环
  ▼
fp-demo-frontend-1     nginx，容器内 8080
  │  /          → SPA 静态文件
  │  /healthz   → 本地返回 200，不经后端
  │  /api/      → proxy_pass http://backend:8080
  ▼
fp-demo-backend-1      Spring Boot，容器内 8080；另发布在 127.0.0.1:18080
  ▼
fp-demo-postgres-1     pgvector/pg15，不发布任何端口
  ▼
fp-demo_postgres-data  唯一的持久化卷

1.1 三件值得记住的事

  • 没有任何端口对公网开放。18080 与 18081 都绑在 127.0.0.1 （FORGEPILOT_BIND_ADDRESS），外部流量只能从 cloudflared 进来。 这不只是加固，还是限流可信的前提——见 3.3 与安全文档残余风险 #4。
  • cloudflared 不在 Compose 里。它是宿主机的 systemd 服务。 docker compose down 不会停它，重启它也不需要动容器。 「站点打不开但三个容器都 healthy」时，第一个要查的就是它。
  • 后端那个 18080 是给运维用的旁路。业务流量都走 nginx。 对比这两个地址的返回，是判断「后端坏了」还是「nginx/前端坏了」最快的办法。

2承重的环境变量

全部配置在 .env（不入库）里，样例见 .env.example。 下表只列配错了会出事的那些；其余变量有合理默认，可以不管。

变量缺失/配错的后果能不能热改
FORGEPILOT_DB_PASSWORD 无兜底默认值。缺失时应用起不来，且报错指向错误的方向——见 5.1 否，改完要重建容器
FORGEPILOT_SCM_SECRET_KEY 无兜底默认值。它加密全部仓库令牌与 webhook 密钥；换掉它等于把已存的凭据全部作废，且无法解回 否。换之前先读 5.2
FORGEPILOT_BIND_ADDRESS 改成 0.0.0.0 会让应用端口绕过 cloudflared 直接暴露，限流随之失去可信来源 否
FORGEPILOT_JAVA_TOOL_OPTIONS 这一串是实测出来的容量包络，不是偏好。改它会让已记录的容量结论失效 否
FORGEPILOT_AI_* 留空则 AI 审查不可用，但应用照常启动，其余功能不受影响 否，但影响面仅限审查
FORGEPILOT_*_PER_MINUTE 等三项 限流配额。填 0 会让应用起不来（没有「关闭」这个取值）；填太小对 webhook 是丢投递 否
这套栈没有「改配置热生效」这回事

所有配置在启动时读入。改 .env 之后必须 docker compose up --detach（Compose 会识别环境变化并重建受影响的容器）。 只 restart 不会重读 .env——这是个很容易浪费半小时的陷阱。

3健康检查

三个容器各有自己的健康检查，它们证明的东西不一样，不要混着看：

容器检查它证明了什么
postgres pg_isready 数据库进程在接受连接。不证明迁移跑过、数据没坏
backend /actuator/health/readiness Spring 上下文起来了、数据源连上了、Flyway 校验通过了。这是真正有信息量的那个
frontend /healthz nginx 活着。它由 nginx 本地返回，完全不经过后端——前端 healthy 时后端可能已经死了

3.1 手工核对

# 三个容器的状态与健康
docker compose -p fp-demo ps

# 后端自身（旁路，不经 nginx）
curl -s http://127.0.0.1:18080/actuator/health

# 经 nginx 的同一个契约——两者不一致就说明问题在代理这一层
curl -s http://127.0.0.1:18081/api/actuator/health

# 外部入口
systemctl status cloudflared

3.2 暴露面契约

管理端点只开 health。/actuator/metrics 必须返回 404——不是 401、不是 403，而是「根本不存在」。 这条由 ActuatorExposureTest 与 scripts/phase1-compose-smoke.sh 双重把关。 如果你在排障时发现 metrics 能访问，说明有人开了 capacity profile 或改了暴露配置， 那是个安全问题：这些端点没有任何认证。

3.3 客户端地址是怎么传下来的

nginx 设置 X-Forwarded-For $proxy_add_x_forwarded_for，后端开 server.forward-headers-strategy: native，由 Tomcat 的 RemoteIpValve 解析—— 它只信任内网网段的代理，从右往左取第一个非内网地址。 真实客户端地址永远排在任何客户端自己伪造的值右边，所以伪造无效。

这条链决定了限流按人计数而不是按代理计数。 它成立的前提是「cloudflared 是唯一入口」；这个前提由部署配置保证，代码无法自证。 动 FORGEPILOT_BIND_ADDRESS 或在 nginx 前面再加一层之前，先回来读这一节。

4日常操作

下面的命令都假设你在仓库根目录，Compose 项目名是 fp-demo。

4.1 升级到新版本

git pull
docker compose -p fp-demo up --build --detach --wait

--wait 会阻塞到全部健康检查通过，失败则以非零码退出—— 所以它是可以直接写进脚本的。不要用 --force-recreate 去「确保干净」：那会连 postgres 一起重建。

4.2 只重启后端

docker compose -p fp-demo restart backend

注意 restart 不重读 .env（见第 2 章的提示框）。改了配置要用 up --detach。

4.3 看日志

# 跟随后端日志
docker compose -p fp-demo logs -f backend

# 起不来时看最后一次启动的完整输出
docker compose -p fp-demo logs --tail 200 backend

日志里不会出现凭据、令牌、口令或其哈希，也不会出现 provider 的原始报错消息 （它可能引用模型回答）。所以「日志里没有细节」有时是设计使然，不是日志级别不够。 错误响应里的 traceId 可以直接在日志里搜到对应那一行—— 这是把「用户看到的」与「日志记录的」对上的唯一手段。

4.4 备份与恢复

# 备份：逻辑导出，跨版本可用
docker compose -p fp-demo exec -T postgres \
  pg_dump -U forgepilot forgepilot | gzip > forgepilot-$(date +%F).sql.gz

# 恢复：只往一个空库里灌
gunzip -c forgepilot-YYYY-MM-DD.sql.gz | \
  docker compose -p fp-demo exec -T postgres psql -U forgepilot forgepilot
恢复之前先想清楚 Flyway

导出里包含 flyway_schema_history。把一份旧备份恢复到一个跑着新代码的部署上， 后端会在启动时发现「库里的迁移记录少于代码里的迁移文件」并尝试补跑——这通常是对的。 但反过来（新备份 + 旧代码）会直接以校验失败拒绝启动。 恢复前先确认这两边的版本关系。

4.5 回滚

代码可以回滚，数据库迁移不能。Flyway 迁移是只追加的，没有 down 脚本， clean 也被禁用了。回滚到一个迁移数更少的旧版本，后端会因为 库里存在它不认识的迁移记录而拒绝启动。

所以可行的回滚只有两种：回到迁移数相同的某个版本（纯代码回退）， 或者回退代码 + 恢复对应时点的数据库备份。没有第三种。

5起不来：症状对照

这一章按你实际看到的报错来组织，而不是按原因。 本项目起不来的几种方式，报错信息都不怎么指向真正的原因。

5.1 FATAL: password authentication failed

最可能的原因不是密码错了，是密码根本没传进去。 spring.datasource.password 写的是 ${FORGEPILOT_DB_PASSWORD}， 没有兜底默认值——这是有意的，一个默认值就是一把到处都能悄无声息生效的弱密钥。 变量缺失时 Spring 把未解析的 ${...} 当字面量原样传下去，于是失败发生在 数据源初始化阶段，表现为认证失败，而不是「缺少配置项」。

先查 .env 里有没有这一行、Compose 是否读到了它： 

docker compose -p fp-demo config | grep FORGEPILOT_DB_PASSWORD

确认之后再去怀疑密码本身是否与卷里那份数据不匹配（换过密码但卷是旧的，也会这样）。

5.2 FlywayValidateException／checksum mismatch

这是本项目最容易踩、也最容易被误判的一条

backend/src/main/resources/db/migration/*.sql 里的文件 已经应用过的那些必须逐字节不变。Flyway 默认在迁移前校验校验和， 改一行注释、改一个空格，都会让后端在已有数据的部署上起不来。 「我只是改了个注释」不是免责理由——校验和是对文件内容算的。

处置：把那个迁移文件恢复成与线上库一致的内容。要确认改了哪一个：

docker compose -p fp-demo exec -T postgres \
  psql -U forgepilot forgepilot -c \
  "select version, description, checksum, success from flyway_schema_history order by installed_rank;"

需要新增行为时，永远是加一个新的迁移文件，不是改老的。 这条同时也是评测证据链的要求。

5.3 上下文启动失败，报缺少 forgepilot.scm.secret-key

同样是「无兜底默认值」的设计：缺了它应用就不启动，而不是用一个弱默认值把所有仓库凭据加密掉。 补上 FORGEPILOT_SCM_SECRET_KEY 即可。

但不要「随便补一个」

这把密钥加密了库里全部仓库访问令牌与 webhook 密钥。 换成另一个值，那些密文永远解不回来了——系统不会报错，只会在下一次 调用 provider 时失败。本项目不做密钥轮换（安全文档残余风险 #2）。 如果原值确实丢了，唯一的出路是：换新密钥，然后手工重新配置每一个仓库的凭据。

5.4 起不来，日志里是限流配置的 IllegalArgumentException

三个限流配额都必须是正整数。想「关掉限流」而填 0 会让应用直接起不来—— 这是刻意的：没有「关闭」这个取值。要放宽就填一个大数。

5.5 后端反复重启，没有明确报错

先看是不是被 OOM 杀了。后端的 mem_limit 是 768 MB，JVM 堆上限 384 MB， 宿主机总内存约 4 GB： 

docker inspect fp-demo-backend-1 --format '{{.State.OOMKilled}} {{.State.ExitCode}}'
dmesg | tail -30 | grep -i "killed process"
free -m

如果确实是内存，不要直接调大 mem_limit 或堆：那一串 JVM 参数是实测出来的容量包络， 动它会让已记录的容量结论失效。先看是不是有别的东西在抢内存（第 7 章有实测基线）， 以及 FORGEPILOT_REVIEW_CONCURRENCY 是不是被调高过——受限主机上它应该是 1 或 2。

6起来了但不对

6.1 用户报「登录一直失败」，返回 429

限流生效了。三个端点各有配额，都按客户端地址计数： 登录 20 次／分、注册 5 次／10 分、webhook 60 次／分。 响应体是统一错误结构，code 为 too_many_requests。

先判断这是防护生效还是误伤。如果一整个办公室从同一个出口 IP 访问， 20 次／分是共享的——那是误伤，调大 FORGEPILOT_LOGIN_ATTEMPTS_PER_MINUTE。 如果是单个地址在刷，那就是它该做的事，不要动。

计数在进程内，重启后端即清空——这是最快的解除手段，代价是所有会话不受影响但配额全部重置。

6.2 webhook 投递不到／PR 没有产生 Review

按这个顺序查，每一步都能把范围砍一半：

  1. provider 侧的投递记录：它有没有发出来，收到了什么状态码。
  2. 收到 401 → 签名校验没过。webhook 密钥不匹配，或者 5.3 说的密钥被换过。
  3. 收到 429 → 撞了 60 次／分的配额。两个 provider 都不重试投递，被限就是丢了。把配额调大。
  4. 收到 2xx 但没有 Review → 投递被接受但认定为无关（仓库未绑定、事件类型不关心、或 PR 变更量超过上限被整体拒绝）。查后端日志里对应的 traceId。

6.3 Review 一直 PENDING

Review 由一个有界线程池执行，并发上限 FORGEPILOT_REVIEW_CONCURRENCY（默认 2）， 队列 64。队列满时新任务被拒绝而不是堆积，被拒的 Review 保持 PENDING， 由对账任务捡回来——它每 30 秒跑一次，把超过 600 秒没被认领的 PENDING 重新排队， 并回收租约超过 300 秒没续期的任务。

所以「PENDING 几分钟」是正常的排队。超过十分钟仍不动才需要查： 多半是 AI 网关调不通（见 6.4），或者线程池里的任务卡在一个不返回的出站调用上。

6.4 AI 审查全部失败

每一次模型调用都在 ai_call_log 留一行，记录的是「一次尝试」—— 重试会留两行，超时和失败分开记录。这是排查这类问题唯一的权威来源： 

docker compose -p fp-demo exec -T postgres \
  psql -U forgepilot forgepilot -c \
  "select created_at, status, model from ai_call_log order by id desc limit 20;"

全是失败且集中在同一时间点，通常是 FORGEPILOT_AI_* 配置或 provider 侧的问题。 注意日志里不会有 provider 的原始报错原文（它可能引用模型回答）， 只有改写后的失败原因。

6.5 前端能打开，但所有写操作被拒（403）

缺失或错误的 CSRF 令牌是 403 的唯一来源。这个设计让 403 的含义单一： 看到 403 就不必怀疑权限，只查令牌。

常见成因是浏览器里存着一份过期的 XSRF-TOKEN cookie。 让用户硬刷新（清掉站点 cookie 后重新加载）即可。 权限不足返回的是 404 或 403 的其他路径，但不来自这一层。

6.6 审查跑完了，钉钉没收到消息

通知是尽力而为的旁路：失败只在后端日志里留一行，不重试、不改审查状态。 所以「审查正常、消息没到」是一种预期内的组合，不是系统故障。

钉钉不用状态码报告拒收

关键词不匹配、签名不对、token 失效——全都答 HTTP 200，真正的结果放在 响应体的 errcode 里。因此排查这类问题只能看日志， 而不能看「有没有报错」。发送器会把钉钉自己的说法原样记下来： 

docker compose -p fp-demo logs backend | grep -i dingtalk

按日志里的那一行对照处理：

日志含义处置
（没有任何 dingtalk 行） 钉钉以 errcode:0 收下了 消息应该在群里。每一条失败路径都会记日志，所以沉默只剩这一种解释
errcode:300005
token is not exist		 webhook 地址里的 access_token 在钉钉那边不存在 机器人被删过或重建过——重建会换全新 token。到「仓库接入」页整组重填当前地址
errcode:310000
keywords not in content		 机器人配了「自定义关键词」，而消息里没有那个词 把那个词填进配置卡的「自定义关键词」，它会被拼进消息标题
errcode:310000
sign not match		 加签密钥不对 从机器人安全设置里重新复制 SEC… 并整组重填
has no enabled notification channel 该项目没配渠道，或渠道被停用 「仓库接入」页那张卡，勾上「启用推送」
DingTalk was unreachable 出站网络问题 查主机到 oapi.dingtalk.com 的连通性
换过加密密钥就都解不开了

换过 FORGEPILOT_SCM_SECRET_KEY 的话，已存的 webhook 地址与加签密钥 永久无法解密，表现同样是消息发不出去——见 5.3。此时必须整组重填。

消息里没有可点链接，是因为 FORGEPILOT_BASE_URL 没配。留空是有意的默认： 一个指向 127.0.0.1 的链接比没有链接更糟。改完记得用 up --detach 而不是 restart（第 2 章）。

6.7 站点打不开，但三个容器都 healthy

问题在容器外面。按这个顺序：

systemctl status cloudflared          # 隧道进程
journalctl -u cloudflared --since -1h # 隧道日志
curl -s http://127.0.0.1:18081/healthz # 本机能不能到 nginx

最后那条返回 ok 而外部访问不通，就基本可以确定是隧道或 Cloudflare 侧的问题， 与这套应用无关。

7容量与余量

2026-08-28 在部署机上的实测基线。它的用处是：下次觉得「是不是内存不够」时有个对照。

容器实测占用上限余量
fp-demo-backend-1398.5 MiB768 MiB52%
fp-demo-postgres-149.3 MiB512 MiB10%
fp-demo-frontend-16.3 MiB64 MiB10%

宿主机：总内存约 3.9 GB，其中可用约 2.1 GB；磁盘 39 GB，已用 47%。

这几个数字不是随便设的

JVM 参数串与三个 mem_limit 是一次完整容量测量的结果， 在 backend/Dockerfile、compose.yaml、.env.example 三处保持逐字一致，而且没有任何自动检查在维护这个一致性。 改任意一处，另外两处要同步改，并且已记录的容量结论作废、需要重跑整套容量协议。 核对三处是否一致： 

grep -ho -- '-Xms128m[^"}]*NativeMemoryTracking=summary' \
  backend/Dockerfile compose.yaml .env.example | sort -u

期望输出恰好一行。

数据库连接是另一条容易忽略的界：Hikari 池上限 5，PostgreSQL 侧 max_connections=30。审查并发之所以定在 2，一部分原因就是要给 web 层留出连接。

8绝对不要做的事

不要会发生什么
docker compose down --volumes 删掉整个数据库。项目、需求、审查、审计全部消失且不可恢复。这条命令只对一次性的演示项目适用，永远不要指向要保留数据的部署
改已应用的 Flyway 迁移文件 后端在下次启动时以校验和失败拒绝启动。改注释也算。见 5.2
换 FORGEPILOT_SCM_SECRET_KEY 库里所有仓库令牌与 webhook 密钥永久无法解密，且不会立刻报错。见 5.3
改 evaluation/ 下被哈希钉住的 9 个文件 评测冻结失效，结论不再可信。其中 contracts/metrics.md 看起来就是一份普通文档，尤其容易误改
把 FORGEPILOT_BIND_ADDRESS 改成 0.0.0.0 应用端口绕过 cloudflared 直接暴露；限流失去可信的地址来源，Actuator 也随之暴露给任何能连到该端口的人
扩大 Actuator 暴露面 这些端点没有任何认证。在加上认证之前，暴露面就只能是 health
把 Docker inspect 输出或环境变量转储存档 它们含有凭据。复现指南对此有明文规定
