ForgePilot 后端有 175 个类。想读懂它，从「第一个类」开始读是没用的——因为你不知道谁调用谁。 这份文档换一个办法：拿一次真实的 pull request，从它敲开服务器的那一瞬间，一路跟到审查结果落进数据库。 途中经过哪个类就讲那个类，贴的是仓库里的真实代码。走完这 12 站，你就摸清了这个系统的主干。

01

请求到达

backend/src/main/java/com/forgepilot/scm/github/GitHubWebhookController.java
这一站在做什么

有人在 GitHub 上开了一个 pull request。GitHub 会主动往我们服务器上一个约定好的地址发一个 HTTP POST—— 这叫 webhook（「回调钩子」：你事先告诉 GitHub「有事就打这个电话」，它就在事情发生时打过来）。 这个类就是接电话的人。

真实代码

@PostMapping(PATH)                              // PATH = "/api/scm/github/webhook"
@ResponseStatus(HttpStatus.ACCEPTED)             // 成功就回 202
void receive(@RequestBody byte[] body,
        @RequestHeader(name = "X-Hub-Signature-256", required = false) String signature,
        @RequestHeader(name = "X-GitHub-Event", required = false) String event) {
  • @PostMappingSpring Boot 的注解，意思是「HTTP POST 打到这个路径时，执行下面这个方法」。你不用自己写路由表，框架扫到这个注解就接好线了。
  • byte[] body这里是关键。请求体没有被解析成对象，而是拿的原始字节。原因见下一站。
  • required = false这两个 header 允许缺失。缺了不是框架报错，而是走我们自己的拒绝逻辑——错误信息要由我们控制。

紧接着的保护块

ScmRepository repository;
JsonNode payload;
try {
    payload = parse(body);
    JsonNode repositoryNode = payload.path("repository");
    repository = sync.authenticate(ScmProvider.GITHUB,
            instanceIdentityOf(required(repositoryNode.path("html_url"))),
            required(repositoryNode.path("id")), body, signature);
} catch (ApiException rejected) {
    throw rejected;
} catch (RuntimeException malformed) {
    throw unverifiable();                        // 一律答成「无法验证」
}
为什么要套这个 try

这个端点是公开的、任何人都能打。如果一个恶意载荷能让代码抛出一个意料之外的异常， Spring 默认会返回一个带堆栈信息的错误页——那既泄露内部结构，又不符合我们统一的错误格式。

代码注释里点了两个真实能触发的例子：在该出现字符串的位置塞一个 JSON 对象， 或者构造一个超过 63 字符的域名标签让 IDN.toASCII 炸掉。

所以校验完成之前的每一种失败，都答得和「签名错误」一模一样。 攻击者无法通过错误信息的差异来试探——这叫不可区分性， 和「用户名不存在」与「密码错误」必须同答是同一个道理。

最后两行

if (!PULL_REQUEST_EVENT.equals(event)) {
    return;                                     // 已验明身份，但本部署对这类事件无事可做
}
sync.apply(repository, github.fetch(repository, pullRequestNumber(payload)));

第一段处理的是 GitHub 在你创建 hook 时发来的那个 ping：它是合法的，只是我们不关心。 最后一行是本站的出口——注意它先 fetch 再 apply，这是第 3 站的主题。

一个容易被忽略的设计

路径是 /api/scm/github/webhook，里面没有 projectId。 因为 GitHub 不知道你的项目编号，它只知道自己那个仓库。 所以定位项目的办法是：从载荷里取仓库的 html_url 和 id，反查我们库里哪个项目接了这个仓库。

02

先验明身份

backend/src/main/java/com/forgepilot/scm/WebhookSignatureVerifier.java
这一站在做什么

这个端点谁都能打，那怎么确认这个请求真的来自 GitHub、而不是有人伪造的？ 办法是共享密钥：你在 GitHub 上配 hook 时设一个密钥，我们库里也存一份。 GitHub 发请求时，用这个密钥对请求体算出一个指纹放在 header 里；我们用自己那份密钥重算一遍，两个指纹一致就说明对方也知道密钥。

这个「用密钥对内容算指纹」的算法叫 HMAC。

真实代码

boolean matches(byte[] body, String secret, String signatureHeader) {
    if (signatureHeader == null || !signatureHeader.startsWith(GITHUB_PREFIX)) {
        return false;
    }
    byte[] expected = HexFormat.of()
            .formatHex(hmac(secret.getBytes(UTF_8), body))
            .getBytes(UTF_8);
    byte[] provided = signatureHeader.substring(GITHUB_PREFIX.length())
            .toLowerCase(Locale.ROOT).getBytes(UTF_8);
    // 常数时间比较，且对长度安全：被截断的十六进制摘要只会判为不相等。
    return MessageDigest.isEqual(expected, provided);
}
两个不能改的细节

一、HMAC 必须覆盖原始字节，而不是解析后再重新序列化的 JSON。 这就是上一站为什么用 byte[] body。JSON 解析再序列化会改变字节——键的顺序、空格、数字格式都可能变， 指纹就对不上了。所以原始字节必须一路带到这里。

二、比较必须用 MessageDigest.isEqual，不能用 equals 或 ==。 普通的字符串比较发现第一个不同的字符就立刻返回，所以「第一个字符就错」比「只有最后一个字符错」返回得更快。 攻击者可以测量这个时间差，一个字符一个字符地把正确签名试出来——这叫时序攻击。 MessageDigest.isEqual 无论内容如何都花同样的时间。

GitLab 那半边

GitLab 有两代机制：新版按 Standard Webhooks 规范签名，老版直接发明文密钥。代码里的规则是—— 如果新版签名存在但验不过，绝不降级去试老版。 否则攻击者只要构造一个「新版签名故意写错」的请求，就能把整个校验降到更弱的那条路上。

03

不信载荷，回头再问一次

backend/src/main/java/com/forgepilot/scm/github/GitHubClient.java
这一站在做什么

签名已经验过了，载荷确实来自 GitHub。但代码依然不用载荷里的内容， 而是拿着 PR 编号主动向 GitHub 的 API 再读一次。

为什么？因为 webhook 只是一个信号——「有事发生了」。载荷可能是旧的（重发的投递）、 可能是残缺的（不同事件类型给的字段不一样）。而这次主动读取拿到的是当下的权威状态。 这个区分在代码里有名字：webhook 是信号，PullRequestSnapshot 才是事实。

真实代码 —— 一个看起来很啰嗦、但极其重要的方法

private static String required(JsonNode parent, String field, String label) {
    JsonNode node = parent.path(field);
    if (!node.isValueNode() || node.isNull()) {
        throw ApiException.unprocessable(
                "The provider's pull request is missing " + label + ".");
    }
    String value = node.asString();
    if (value.isBlank()) {
        throw ApiException.unprocessable(
                "The provider's pull request has an empty " + label + ".");
    }
    return value;
}
这个方法为什么必须存在

Jackson（Java 的 JSON 库）的 JsonNode.asString() 对缺失的节点和 null 节点都返回空字符串 ""， 而不是抛异常。看起来很宽容，实际是个陷阱：

  • 如果不检查，缺失的 base.sha 会变成 base_sha = "" 写进数据库。
  • 数据库那一列是 NOT NULL——而 "" 满足 NOT NULL，所以数据库抓不住。
  • 然后 diff 指纹会基于一个空 SHA 算出来，这次 Review 的身份从此就是错的。

author_external_user_id 更糟：它是授权键——系统靠它判断「这个 PR 是不是你开的」。 如果它变成 ""，所有「幽灵作者」的 PR 会共享同一个身份，权限就串了。

所以规则是：权威字段缺席、为 null、或是个容器，都必须大声失败，而不是存下坏数据。

另一条：代码里绝不硬编码 host

请求的基地址来自数据库里那一列 api_base，不是写死的 api.github.com。 这不是为了测试方便——是因为自建 GitHub Enterprise / GitLab 实例必须能用。 而同一个设计顺带让集成测试能把仓库指向一个本地回环的桩服务，不需要真实凭据。

每次调用还会用 OutboundUrlPolicy 重新校验地址一次——因为这一列可由项目负责人配置， 而安全策略可能在此期间收紧了。这是防 SSRF（诱导服务器去访问内网地址）的那道闸。

04

写进数据库，并发出一个事件

backend/src/main/java/com/forgepilot/scm/PullRequestSyncService.java
这一站在做什么

把「已验明身份的投递 + 权威快照」变成数据库里的一行 pull_request。 如果这个 PR 已经存在（比如作者又推了一个 commit），就更新它；不存在就新建。 最后发出一个进程内事件，通知下游「这个 PR 变了」。

真实代码（节选主干）

public void apply(ScmRepository detached, PullRequestSnapshot snapshot) {
    ScmRepository repository = repositories
            .findWithLockByProjectIdAndId(detached.getProjectId(), detached.getId())
            .orElseThrow(PullRequestSyncService::unauthenticated);

    String fingerprint = ReviewInputFingerprint.of(repository.getProvider().name(),
            repository.getInstanceIdentity(), repository.getExternalId(), snapshot);
    String manifest = manifest(snapshot.changedFiles());

    PullRequest existing = pullRequests
            .findWithLockByProjectIdAndRepositoryIdAndExternalNumber(
                    projectId, repository.getId(), snapshot.externalNumber())
            .orElse(null);

    if (existing != null) {
        if (isOlderThan(snapshot.sourceUpdatedAt(), existing.getSourceUpdatedAt())) {
            return;                                // 乱序到达的旧投递，丢弃
        }
        existing.applySnapshot(...);
        existing.mapAuthor(authors.userIdFor(projectId, snapshot.authorExternalUserId()));
        pullRequests.flush();
        publish(existing);
        return;
    }
    // ... 新建分支，末尾同样 publish(created)
}
  • findWithLock…行锁。读这一行的同时锁住它，直到本次事务结束别人不能改。否则两个 webhook 同时到达会互相覆盖。
  • fingerprint把「仓库身份 + head + 变更清单」算成一个哈希。它回答「这是不是同一次审查」——第 6 站会用到。
  • isOlderThan网络投递不保证顺序。带着更旧时间戳的投递必须丢弃，否则新状态会被旧状态覆盖。
  • publish(…)发事件。注意它在 return 之前、且在同一个事务内部。
什么是「事务」，为什么这里反复强调

数据库事务是一组操作的「全有或全无」包装：要么全部生效，要么全部不生效，中间状态外界看不到。 Spring 里给方法加 @Transactional 就开一个。

这里为什么重要：事件在事务内部发布，且监听器是同步的。 所以下游创建 Review 这件事，和更新 PR 这件事，在同一个事务里。 结果是不存在「PR 已更新但 Review 没建」的已提交状态——要么两件都成了，要么两件都没发生。

变更文件清单是「存下来」的，不是「用时再拉」

整份清单连同每个文件的 patch，作为一个 JSONB 值（PostgreSQL 里可查询的 JSON 类型）存在这一行上。 为什么不等要用的时候再向 GitHub 拉？因为那样每次重看审查结果都可能拿到不同的 diff—— 而这次审查的结论是针对当时那份 diff 得出的。证据必须冻结。

超出上限时入库显式失败，而不是静默截断——否则日后 Review 会被告知它「看过」一份其实不完整的清单。

05

事件被同步接住

backend/src/main/java/com/forgepilot/review/PullRequestChangedListener.java
这一站在做什么

上一站发出的事件在这里被接住。这是进程内事件——不是消息队列，就是同一个 JVM 里的一次方法调用， Spring 帮你把「谁发」和「谁收」解开耦合。

为什么要用事件，而不是直接调用

因为依赖方向。这个系统有一条硬规则：review 可以依赖 scm， 但 scm 不能依赖 review。如果 PullRequestSyncService 直接 new ReviewService() 调过去，依赖图上就出现了一个环——而这条规则由 ArchitectureRulesTest 在每次构建时用 ArchUnit（一个专门检查架构约束的测试库）强制。

事件把箭头反了过来：scm 只是「广播一件事发生了」，它不知道谁在听； review 主动去听。编译期的依赖方向仍然是 review → scm。

必须是同步监听器

Spring 还提供 @TransactionalEventListener，它在事务提交后才执行。 这里不能用它——那样「PR 已提交、Review 还没建」就成了一个真实存在的已提交状态， 而如果紧接着进程崩溃，这个 PR 就永远不会有 Review 了。

顺带一个实现期的坑：这个类和另外两个模块的同类监听器起初都叫 ProjectMemberRemovingListener——Spring 默认拿简单类名做 bean 名字， 三个同名直接 ConflictingBeanDefinitionException 启动失败。所以现在它们各有不同的名字。

06

创建一次 Review：冻结上下文

backend/src/main/java/com/forgepilot/review/ReviewService.java · Review.java
这一站在做什么

在 review 表里建一行，状态是 PENDING（等着被执行）。 关键在于：这一行把这次审查的全部输入都冻结了下来—— 哪个 PR 的哪个 head、哪份 diff（用指纹标识）、哪一版需求、以及当时那份变更文件清单。

「一次 Review」的身份是什么

是那组输入，不是那个 PR。所以：作者推一个新 commit → head 变了 → 指纹变了 → 那是一次新的 Review， 之前那次成为历史记录（页面上显示「已过期」）而不是被覆盖。

这也是为什么系统能诚实地说「这条审查结论是针对当时那份代码的」——因为它真的把当时那份代码存下来了。

数据库层面的保护

这些身份列不是靠「大家都别改」维持的。数据库上有触发器（trigger：数据写入时自动执行的检查） 直接拒绝事后修改它们，也拒绝「项目与上下文互相矛盾」的写入。

设计口径是：校验发生在写入之前，触发器是最后一道防线，不是第一道。 因为触发器一旦触发，中止的是整批插入，而不是那一行。

还有一件事在这一站发生：自动投递建出的 PENDING Review 不算终局裁定。这很重要——因为 PR 作者能否纠正需求关联，判据是「当前 head 上有没有人做过终局裁定」。如果把判据写成「有没有 Review」，那作者的纠正窗口在自动投递那一刻就永久关闭了，实际上不可达。

07

后台线程「抢」这个任务

backend/src/main/java/com/forgepilot/review/ReviewClaimRepository.java
这一站在做什么

现在有一行 PENDING 的 Review 等着被做。后台线程池里的线程会来「抢」它。 同一次 Review 可能有多个线程想做（比如一个卡住了、定时任务又来捡）， 必须保证只有一个能抢到——否则会产出两份互相矛盾的报告。

真实代码 —— 整个并发控制的核心，就这一条 SQL

@Modifying(clearAutomatically = true, flushAutomatically = true)
@Query(value = """
        UPDATE review
           SET status = 'RUNNING',
               execution_attempt = execution_attempt + 1,
               execution_token = cast(:token AS uuid),
               lease_until = now() + (:leaseSeconds * interval '1 second'),
               updated_at = now()
         WHERE project_id = :projectId
           AND id = :reviewId
           AND (status = 'PENDING'
                OR (status = 'RUNNING' AND lease_until < now()))
        """, nativeQuery = true)
int claim(@Param("projectId") long projectId, @Param("reviewId") long reviewId,
        @Param("token") String token, @Param("leaseSeconds") int leaseSeconds);
这条 SQL 怎么读

它是一条语句，做了三件事：把状态改成 RUNNING、把尝试次数 +1、 生成一个只有本次持有者知道的随机令牌 execution_token 和一个到期时间 lease_until。

而 WHERE 里那个条件是闸门：只接纳还没人做的（PENDING）， 或者有人做但已经超时的（RUNNING 且租约过期）。

返回值是 int——影响了几行。1 表示抢到了，0 表示没抢到。

为什么不能「先查再改」

直觉写法是：先 SELECT 看看状态是不是 PENDING，是就 UPDATE。 这是错的——两次操作之间有一个时间窗口，另一个线程可能正好在这中间也查到 PENDING， 于是两个线程都认为自己抢到了。

写成一条带条件的 UPDATE 就没有这个窗口：数据库保证这条语句是原子的。 两个线程同时执行，失败方会拿胜者已提交的数据重新求值 WHERE， 发现租约在未来，于是匹配到零行、返回 0。

这也是为什么整个文件都是原生 SQL 而不是用 ORM： ORM 的「脏检查」机制报告不了「你匹配到了零行」这件事，而这里影响行数本身就是判定结果。

时间从哪来

所有时间都用数据库的 now()，而 PostgreSQL 会在事务开始时把它冻结。 也就是说参照时间可能偏旧一点。这个方向是安全的那一侧：偏旧的时间只会找出更少的过期租约， 因此绝不会抢占一个还活着的 worker。

08

worker 主流程与三道围栏

backend/src/main/java/com/forgepilot/review/ReviewExecutor.java
这一站在做什么

抢到任务之后的完整流程：跑分析 → 处理失败 → 写结果。三个分支各有讲究。

真实代码 —— 全文只有这么长

void run(long projectId, long reviewId) {
    Optional<Claim> taken = claim(projectId, reviewId);
    if (taken.isEmpty()) {
        return;                                    // 没抢到，安静退出
    }
    Claim claim = taken.get();

    Optional<ReviewPipeline.Report> report;
    try {
        report = pipeline.analyse(claim, () -> renew(claim));
    } catch (ApiException providerFailure) {
        fail(claim);                               // ① 模型调不通
        return;
    }
    if (report.isEmpty()) {
        fail(claim);                               // ② 回答校验不过
        return;
    }

    finishingTransaction.executeWithoutResult(status -> {
        pipeline.store(claim, report.get());
        if (!complete(claim)) {
            status.setRollbackOnly();               // ③ 租约丢了，回滚
        }
    });
}

① 模型调不通 → 标记 FAILED，而不是让异常逃逸

如果让异常直接抛出去，这一行会一直停在 RUNNING 直到租约过期， 然后定时任务重新抢占它、再去调那个同样不可达的 provider——无限循环。 标成 FAILED 会停下来等人处理，而人可以手动点重试。

② 回答校验不过 → 什么都不写

注意是 fail() 而不是写一份空报告。 因为一份「零条问题」的报告读起来和「这个 PR 很干净」一模一样， 而实际情况是「我们没能得到一个能用的回答」。这两件事的处置完全相反。

③ 租约丢了 → 回滚，报告不得比它所属的 Review 活得更久

分析花了几分钟，这期间租约可能已经过期、被另一个线程接管了。 所以写结果和「把状态改成 COMPLETED」必须在同一个事务里， 并且 complete() 是带条件的——它要求令牌匹配且状态仍是 RUNNING。 匹配不上就整个回滚：这个尝试已不再拥有那一行，而另一个尝试正在产出它自己的结果。

最常被遗忘的那道围栏

租约已过期的 worker 连「把这次 Review 标记为 FAILED」都不许。 所以 fail() 那条 SQL 也带着令牌条件。 如果这里不加围栏，一个已经死掉的尝试就能把取代它的那个尝试判为失败。

同理，续租本身就是心跳——租约过期就是停滞信号， 所以这个系统没有第二套存活检测机制，也不需要一张独立的心跳表。

重新抢占时那个必须同事务的删除

如果一个 worker 崩了，另一个来重新抢占，它必须先删掉崩溃那次留下的 finding。 原因是 finding 表的外键指向 (project_id, id, execution_attempt)—— 旧 finding 持有旧的尝试编号，在它们还存在时去递增该编号会以 23503 （外键违例的错误码）失败，把这个 Review 永久钉死，而唯一能解开它的 worker 恰恰已经死了。

顺带说一个被明确否决的方案：给外键加 ON UPDATE CASCADE 也能让递增成功， 但绝不可用——它会静默地把已死尝试的 finding 重新标记为新尝试的产出。 那比完全没有围栏更糟，因为它在伪造证据。

09

组装上下文、切成批次

backend/src/main/java/com/forgepilot/review/ReviewPipeline.java · ChangedFileBatcher.java
这一站在做什么

把送给模型的东西凑齐：变更 diff + 需求正文 + 验收条件 + 检索到的项目知识。 这就是 ForgePilot 与普通 AI 审查的全部区别所在——后三样是普通审查没有的。

然后按字符预算切成若干批次，因为一个大 PR 塞不进一次模型调用。

批次绝不下结论 —— 这是整个引擎最重要的一条规则

批次只报告候选问题和验收条件的证据片段， 不给任何裁定。校验器里连 acVerdicts 这个字段都不读。

为什么？因为一个批次只看到了 diff 的一部分。 两个批次从同一处改动的两半出发，会对同一条验收条件得出相反的裁定。 所以下结论的资格只属于下一站那个能看到全部证据的综合阶段。

推论：小 PR 和大 PR 走完全相同的路径。 一个只改了一个文件的变更也会产生一个批次、也要经过综合阶段。 没有「小 PR 直接出结论」的捷径分支——那条捷径就是一条第二流水线，而它被明令禁止。

放不下的东西怎么办：可以裁，但绝不能悄悄地裁

一个文件会被放进「未审查」清单，当它：超出变更文件数上限、provider 压根没给 patch（二进制文件）、或者连完整一行都塞不进一个批次。过长的 patch 会在行边界处裁剪并加以标注。

而「空的未审查清单」与「缺失的未审查清单」必须保持可区分——所以这个字段总是写入，哪怕什么都没被裁掉。缺失 manifest 绝不能在页面上显示成「全部覆盖」。

一个批次失败，整次 Review 失败

第一个「解析不过、那唯一一次格式修复也救不回来」的批次，会让整个阶段以失败收场， 并丢弃此前各批次已经产出的东西。

这次丢弃正是要点：一个只报告了五个批次中三个的 Review 看上去是完整的， 而它对另外两个批次的判断是错的。

10

调模型：唯一的出口

backend/src/main/java/com/forgepilot/ai/AiGateway.java · PromptSanitizer.java · AiFailurePolicy.java
这一站在做什么

全代码库只有这一个类能发出对模型 provider 的 HTTP 请求。 它管 HTTP、鉴权、超时、重试和调用记录，而且不认识任何业务类型—— 它不知道什么是 Requirement、什么是 Finding。

它怎么做到「不认识业务」还能记录归属

调用日志需要知道这次调用属于哪个项目、哪条需求。但如果 AiGateway 直接接收 Requirement 对象， ai 就依赖了 requirement，依赖图就乱了。

解法是 AiCallContext：只传不透明的 Long id。 网关把它们原样写进日志，从不解读。所以 ai 至今只依赖 common。

三条不可动的规则

一、重试只有一次，且只对瞬时错误（429 / 5xx / 网络）。 全代码库别处没有任何重试，也必须保持没有——这条例外只授权给网关。

二、日志记的是「一次尝试」而不是「一次调用」。 重试过的调用会留下两行。这是事后审计「确实只重试了一次」的唯一手段。

三、TIMEOUT 与 FAILED 必须分开记。 两者都属瞬时失败、都重试一次，看起来可以合并。但只有分开保留， 运维事后才分得清 provider 是答得不对还是根本没答。

发出去之前的最后一道处理

PromptSanitizer 做两件事：掩码看起来像凭据的字符串、把载荷裁剪到预算内。 它是纯函数——不写日志、不碰数据库、不抛异常。

最后这点是刻意的：一份文档不会因为「看起来含 token」而被拒绝，只会去掉那部分后照常发送。 拒绝非法输入是另一件事、另有归属（KnowledgeUploadValidator）。

校验回答：让空报告无法表达

backend/src/main/java/com/forgepilot/review/ReviewOutputValidator.java
这一站在做什么

模型返回了一段 JSON。这一站把它变成一个对本次 Review 上下文而言为真的结果—— 或者变成一个「失败」裁定。模型可能编造不存在的文件路径、引用别的修订的验收条件、 或者返回压根不是 JSON 的东西。

真实代码 —— 用类型把「成功的空报告」变成不可表达

public record Outcome(ReviewStatus status, ReviewOutput output, String failureReason) {

    public Outcome {                              // record 的紧凑构造器，每次创建都跑
        if (status == ReviewStatus.COMPLETED) {
            if (output == null || failureReason != null) {
                throw new IllegalArgumentException(
                    "A completed validation carries its output and no reason.");
            }
        } else if (status == ReviewStatus.FAILED) {
            if (output != null || failureReason == null) {
                throw new IllegalArgumentException(
                    "A failed validation carries a reason and no output.");
            }
        } else {
            throw new IllegalArgumentException(
                "Validation ends in COMPLETED or FAILED.");
        }
    }

    static Outcome completed(ReviewOutput output) {
        return new Outcome(ReviewStatus.COMPLETED, output, null);
    }
    static Outcome failed(String reason) {
        return new Outcome(ReviewStatus.FAILED, null, reason);
    }
}
这段代码在做一件很聪明的事

它把「绝不产出一份成功但残缺的报告」从一条要靠人记住的规则， 变成了一条类型系统层面的事实。

COMPLETED 必须带着 output 且不能有失败原因；FAILED 必须带着原因且不能有 output。 任何写出「成功 + 空报告」的代码在创建对象的那一刻就会抛异常，而不是安静地产出一份误导人的报告。

同一个思路在 ReviewPipeline.Report 上再出现一次：失败的 Review 根本没有 Report， 而不是有一个空的。Optional.isEmpty() 就是判据。

两种失败的处置完全不同

情况处置为什么
结构非法
不是 JSON、缺 findings 数组		给一次格式修复；仍不行则整次 Review FAILED「模型返回了零条问题」与「模型返回的东西根本不像一个回答」会导向相反处置。混为一谈，正是一次失败的 Review 开始看起来像「PR 很干净」的方式。
单条断言可疑
路径不存在、AC 属于别的修订		丢弃那一条，记进 warnings，Review 继续一条幻觉引用不该毁掉整份报告。但静默丢弃也不行——那只会让运维拿到一份更短的报告，却没有任何办法知道它被缩短过。
修复只能一次，不能写循环

代码里是 try / catch / try 的两层结构，而不是 while。 因为在这里写个循环，会悄悄把 AI 网关自身那次有界重试放大成四次调用。

沉默的模型无法把报告缩短

被审查修订的每一条验收条件最终都会有裁定。 模型跳过的那些被填成 NOT_FOUND，并记一条警告—— 这样「模型什么都没说」与「模型说了没有」保持可区分。

落库：三个哈希与那把外键锁

backend/src/main/java/com/forgepilot/review/FindingKeys.java · Finding.java
这一站在做什么

把通过校验的问题写进 finding 表。每条 finding 带三个确定性哈希—— 同样的输入必然算出同样的值。它们让系统能回答：这条问题是上一轮那条问题，还是一条新问题？

哈希作用
finding_key批内去重 + 跨 Review 匹配。作者推新 commit 后重新审查，靠它判断「这还是那条老问题」。
evidence_hash标识那段逐字引用的代码证据。
basis_hash标识产生这条 finding 的判定依据（含规则版本）。
整个系统最脆弱的一条规则

三个哈希都不得覆盖模型自己写的散文。 explanation（问题说明）、suggestion（修复建议）、confidence（置信度） 是回答里唯一允许随措辞自由变动的字段。

一旦它们中任何一个渗进哈希，同一个问题就会在每一轮换个说法后变成「新问题」—— 跨轮次去重、抑制与血缘会同时失效。而要到下一轮审查才看得出来， 所以这不是那种会立刻暴露的 bug。

与此配套的是两个朝相反方向移动的版本常量，很容易改错：

  • ReviewPrompts.VERSION——schema 变了就要递增，现在是 "review-2"。
  • FindingKeys.RULE_VERSION——必须保持 "1"。它进 basis_hash，一改就让全部历史 finding 的血缘断掉。
类别为什么要在应用层先映射

finding.category 在数据库上有一个 CHECK 约束，限定合法取值。 但一个到达 CHECK 的非法值会中止整批插入，而不是它自己那一行—— 所以 CHECK 忘掉的一个合法类别，会把同一次审查里其他所有 finding 一起带走。

因此：应用侧先映射到闭合枚举再插入，CHECK 只当最后防线， 并且有一个测试逐个走完枚举去比对 SQL 里那份清单。 「与应用侧词汇不一致的 CHECK 比没有 CHECK 更糟」——这句话在代码注释里就写着。

走到这里，一次 Review 完成了

状态变成 COMPLETED，页面上能看到：每条验收条件的裁定、findings、覆盖清单（含哪些文件没被审查）、 以及审查时的完整上下文快照。接下来全是人的事—— 开发认领并修复、评审复核、负责人记录那次一次性的 Decision。 AI 到此为止，它不推进任何状态。

术语速查

抢占多个线程竞争同一个任务，靠一条原子 SQL 保证只有一个成功。
幂等同样的操作做多次和做一次结果相同。webhook 会重复投递，所以处理必须幂等。
