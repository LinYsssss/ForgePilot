1.2 测试要回答的问题

本项目的测试不以覆盖率为目标，而以「锁住哪个不变量」为目标。每条测试都应能回答：如果这条断言被删掉，什么错误会溜过去？答不上的测试不写。

由此形成四类目标：

  • 契约不被悄悄改变——API 响应结构、导航与路由形态、错误体结构。
  • 约束由数据库本身强制，而不是只由某个服务层调用者遵守。
  • 并发与失败路径真的走过——抢占竞争、租约过期、provider 不可达、结构非法的回答。
  • 接线真的存在——每个组件单独测都通过、而没有任何生产代码调用它们，是本项目真实发生过两次的故障形态。

2.2 硬性禁令

数据库测试中禁止的四件事

禁止内存数据库替代（H2 等）、禁止「Docker 缺失就跳过」的分支、 禁止 @Disabled、禁止 assumeTrue 守卫。

理由：一个跑不起来的数据库测试必须让构建失败。 这里的假绿会藏住模型依赖的约束行为——而那些行为恰恰是不能靠服务层保证的部分。 这条禁令由 lint 检查强制：grep -rniE 'h2|DisabledIf|assumeTrue|@Disabled' 必须无匹配。

2.3 三条从故障中学到的测试原则

原则一：服务层测试证明不了 MVC 映射

三个 DELETE 端点首次交付时只有服务层测试。路径接线与状态码没有任何证明—— 一个写错的路径会在服务层测试里全绿，到了前端就是 404。 补充的 BatchOneApiTest.theThreeDeleteEndpointsAreWiredAndInvisibleAcrossProjects 在真实 HTTP 之上断言路径、204 状态码与跨项目不可见性。

项目归档端点按同一原则处理：theArchiveEndpointsAreWiredAndReversible 走真实 HTTP，同时断言归档什么都不删。

原则二：组件全绿而无人调用

本项目发生过两次：一次是全部验收条件通过，而 AiGateway.chat 没有任何生产调用方； 另一次是引擎每个部分单独测过，而 ReviewExecutor.run 抢到 Review 后就停了。

组件测试按构造看不到这个问题——每个测试在「没人调用它」时通过得一样好。 所以 ReviewPipelineIntegrationTest 从 scm 发布的事件出发、断言数据库里的行， 中间只替换 provider，其余全是真实组件。

原则三：会过期的论据要写成测试，不要写成笔记

「为什么这个部署没有向量索引」是一条基于 pgvector 当前能力的论断。 写成 markdown 里的研究结论，它会静默过期；写成 KnowledgeVectorIndexTest， pgvector 一旦放宽维度上限，测试就会失败——而那次失败正是回来重新决策的信号。

该测试三个用例分别钉住：三种索引形态各自的拒绝理由、唯一能建出的两种形态都是有损预筛、顺序扫描在冻结维度上给出精确余弦序。

4.3 几个值得单独说明的用例

数据库约束测试绕到应用代码之下

DatabaseConstraintTest 通过 JdbcTemplate 直接写入，绕过全部服务层， 并点名它期望的 SQLState：23505（唯一冲突）、23503（外键违例）、23514（CHECK 违例）。

一条只被服务强制的约束等于没被强制——未来任何调用者都能绕开它。

迁移测试针对非空表

ALTER TABLE … ADD CONSTRAINT … CHECK 会校验表中已有的行。 因此一条不容忍 NULL 的 CHECK 在新建的空 schema 上必然通过，然后在任何已有数据的部署上直接让迁移失败。

FoundationDatabaseTest 迁移的是空 schema，看不见这件事。 所以 V9MigrationTest 与 V10MigrationTest 采用唯一有效的形状： 先迁到上一版、写入一行、再迁剩下的。

并发测试要求交错被观察到，而不是被假设

ScmIdentityFreezeConcurrencyTest 不用 sleep 等待，而是向 PostgreSQL 询问 另一个线程是否真的阻塞在那一行上。否则这个测试在「线程池根本没启动任务」时也会通过， 退化成它本要补充的单线程用例。

架构规则是可执行的，不是文档约定

ArchitectureRulesTest 8 个用例强制八包依赖单向无环、禁止的包名不存在、 scm 不依赖 review。它导入的是生产类， 所以测试作用域的监听器不会削弱这条规则。

5.1 lint 策略检查的内容

npm run lint 不是通用代码风格检查，而是四条项目策略：

  • 无 tab、无行尾空格。
  • 原始色值只允许出现在 tokens.css，其他文件必须用设计令牌。
  • 禁止依赖清单：状态管理库、UI 组件库、HTTP 客户端库、图表库共 13 个包名。
  • 扫描范围含 src/、tests/ 与根级配置文件。
jsdom 的两处能力缺口影响了实现选择

jsdom 30.0.1 不实现 <dialog>（showModal 与 close 均为 undefined）， 也不实现 navigator.clipboard。

这两点是实测确认后才做的设计决定：归档确认层因此采用卡片内联面板而非模态框； 复制按钮的剪贴板调用必须包 try/catch，失败时不报错也不拦路——项目名就在旁边的只读输入框里可手动选中。

一次真实的近失事件

在一轮「文档只保留当前功能」的清理中，evaluation/contracts/metrics.md 曾被当作普通指标说明文档 列入待清理项。它在冻结哈希列表内——改动它会使 verify-freeze 永久无法通过， 而 holdout 只运行过一次且不可重跑，冻结证据一旦失效就无法重建。

检查后确认该文件内容无需改动，未被修改。由此形成流程要求： 动 evaluation/ 下任何文件前，先运行 verify-freeze 取得那份列表，再与改动清单比对。

7部署验证

冷启动脚本创建独立 Compose 项目与全新数据卷，校验完成后只删除它自己创建的临时资源。它断言：

  • 三个健康检查全部通过，反向代理可达（后端 /actuator/health，经前端代理 /api/actuator/health）。
  • PostgreSQL 版本 ≥ 15，vector 扩展已安装，距离运算返回预期值。
  • Flyway 十条版本化迁移全部成功，最高版本 V10 成功。
  • public 中恰好这二十张业务表，按 C 排序逐字符比对（不依赖容器 locale）。
本次报告期内修复的一个缺陷

该脚本此前仍断言「8 条迁移、到 V8」与一份缺少 project_deletion_record 的 19 表清单—— V9 与 V10 落地时都漏了同步更新。

后果：它是复现指南指定的冷启动证明，也是 CI 每次构建运行两次的作业， 对当前 schema 必然失败。 而 FoundationDatabaseTest 里的 20 表清单是正确的，所以 mvnw verify 一直全绿—— 后端测试证明不了一个 shell 脚本的期望值。

已修正并对照运行中的部署逐项核验：迁移数 10、V10 成功、表名字符串与 information_schema 逐字节一致。 由此形成的规则：新增建表迁移必须同步三处—— FoundationDatabaseTest.EXPECTED_TABLES、脚本的 expected_tables、 以及同一脚本内的迁移计数与版本成功检查。

8.3 有意不做的测试

以下测试刻意没有写，理由记录在此以免后续被当作缺口补上：

  • 不为 DTO / record 的 getter 写测试——它们没有行为，测试只会重复声明。
  • 不重复测已由类型系统保证的性质——例如「FAILED 的 Review 没有 Report」是构造器强制的，写测试只是复述编译器。
  • 不为覆盖率补测——本项目不设覆盖率目标；答不上「锁住哪个不变量」的测试不写。
  • 不测模型输出质量——那属于评测体系，用固定语料与确定性评分器度量，不属于单元测试。

8.4 已知限制：Finding 行号连续性

状态：已知 · 暂不改规则

finding_key 当前包含 patch 新侧行号。无关插入，甚至空提交导致行号整体移动时， 即使 evidence_hash 与代码证据没有变化，同一 Finding 也可能被记录为 NEW， 从而无法继承上一轮的 SUPPRESSED 状态，削弱 P10 的自动抑制效果。

彻底修正需要调整跨 Review 的 key/hash 规则并处理历史数据，超出本次低成本改动范围； 因此这里将它作为已知限制明确记录，不把它误写成已解决的连续性保证。

9已发现的缺陷

9.1 未修复：测试套件存在潜伏的类执行顺序依赖

状态：已确认 · 根因未定位 · 已规避

现象

仅重命名 BatchOneApiTest 类名与注释（diff 中没有任何代码行变化）， 导致该类 4 个用例在完整构建中失败，全部倒在同一个辅助方法上， 断言为 GET /api/auth/me must issue the XSRF-TOKEN cookie，实际取得的 cookie 为 null。

决定性证据

  • 单独运行该类：5/5 全绿。
  • 完整构建：4/5 失败。
  • SecurityConfig 与该测试类的 diff 均为纯注释。

分析

测试框架默认按文件系统顺序执行测试类。重命名改变了该类的排序位置， 使某个先运行的类留下的状态影响到匿名请求的 CSRF cookie 下发。污染源尚未定位。

处置

已回退重命名，保留历史类名，套件恢复 333/333。 由此形成的规则：phase1-quick.json、phase1-compose-smoke.sh、 BatchOneApiTest 这类历史名字一律保留，只清理散文。

影响

后续在 com.forgepilot 下新增测试类可能再次触发， 而失败信息（CSRF cookie 为 null）完全指不到真正的原因。 诊断特征是「单类运行绿、全量运行红」——出现该特征时应先用单类运行确认是顺序依赖， 不要去改 SecurityConfig。

2026-08-29 的复现尝试

两次尝试均未复现：以 -Dsurefire.runOrder=reversealphabetical 跑完整套件全绿；当日新增三个测试类（ReviewInsightTest、 DingTalkSenderTest、NotificationChannelTest）之后套件仍然全绿—— 而上面那条「影响」正预测新增测试类可能触发它。

三个数据点说明这个缺陷比当时判断的更窄，但根因依然未定位。 复现不了就不能宣布它消失，也正因如此没有为它加任何「以防万一」的处置： 给一个复现不了的问题贴 @DirtiesContext，只会多付一个 Spring 上下文， 并让下一个人误以为它已被解决。

9.2 已修复：冷启动脚本与当前 schema 不一致

详见第 7 章。根因是「加表需同步三处」缺少机制保障，其中两处在 V9/V10 落地时被遗漏，且后端测试按构造无法发现。

9.3 已修复：文档中的过期数字

七个文件（含 README.md、CLAUDE.md、AGENTS.md 与三个子项目 README） 仍写着「332 个测试 / 37 个测试」，而当时实际为 333 / 42；产品文档中也一处未提及已交付的项目归档能力。 当轮已修正。但这一类缺陷会复发，而且确实复发了：本报告之后新增限流（338）、 覆盖度与校准（348）、通知（358 → 364），每一次这些手写数字都再度落后， 包括本报告自己——它在 2026-08-29 被发现仍写着 333。

当日的处置不是再改一次数，而是把两类数字分开：结构性数字 （包数、表数、迁移数、导航数、路由数）由测试断言，改动即变红，可以放心写死； 用例数不被任何东西钉住，因此第 4 章现在明确标注它是某一次运行的快照， 并注明日期与产生它的命令。一个标着日期的数字过期时是诚实的，一个不标日期的数字过期时是错的。

9.4 测试执行过程中暴露的一个方法学问题

把构建输出管进 tail 会掩盖真实的失败

本轮有两次执行将 Maven 输出通过管道传给 tail。管道的退出码来自最后一个命令， 因此 tail 的 0 掩盖了 Maven 的 BUILD FAILURE，一次真实失败被误读为通过。

正确做法：重定向到日志文件再检索，并显式检查退出码。 本报告的所有结果均按此方式取得。

10.2 可以支持的结论

  • 业务规则、状态机与授权边界有自动化验证，且约束由数据库本身而非仅服务层强制。
  • 并发与失败路径真的被执行过，不是靠代码审查推断——抢占竞争、租约过期、provider 不可达、结构非法的回答各有用例。
  • 架构约束可执行，依赖方向由构建强制而非文档约定。
  • 评测证据完整且可核验，重算不需要任何凭据。

10.3 不能由本报告支持的结论

三条界限

不能得出「界面正确」。视觉、布局、键盘可达性与动效均无自动化覆盖， 且本轮新增功能的人工验收尚未执行。

不能得出「与真实 GitHub / GitLab 集成已验证」。 webhook 认证与 provider 读取对回环桩服务测试充分，但未对真实凭据与真实投递做过端到端演练。

不能得出「AI 审查质量」。那由评测体系度量，样本为 12 例 holdout 且缺陷手工构造， 报告给出 95% Wilson 区间并明确声明泛化限制。

10.4 建议的后续工作

  1. 定位 9.1 的顺序依赖污染源——它会让未来任何新增测试类随机变红，且报错指向错误方向。
  2. 执行 8.2 的两批人工验收，把结果记入清单。
  3. 为「加表需同步三处」增加机制保障——目前靠规范约束，而它已被遗漏过一次。
  4. 用一次性账号做真实 provider 端到端演练，补上 10.3 第二条界限。
