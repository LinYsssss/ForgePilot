1.2 测试要回答的问题

本项目的测试不以覆盖率为目标，而以「锁住哪个不变量」为目标。每条测试都应能回答：如果这条断言被删掉，什么错误会溜过去？答不上的测试不写。

由此形成四类目标：

  • 契约不被悄悄改变——API 响应结构、导航与路由形态、错误体结构。
  • 约束由数据库本身强制，而不是只由某个服务层调用者遵守。
  • 并发与失败路径真的走过——抢占竞争、租约过期、provider 不可达、结构非法的回答。
  • 接线真的存在——每个组件单独测都通过、而没有任何生产代码调用它们，是本项目真实发生过两次的故障形态。

2.2 硬性禁令

数据库测试中禁止的四件事

禁止内存数据库替代（H2 等）、禁止「Docker 缺失就跳过」的分支、 禁止 @Disabled、禁止 assumeTrue 守卫。

理由：一个跑不起来的数据库测试必须让构建失败。 这里的假绿会藏住模型依赖的约束行为——而那些行为恰恰是不能靠服务层保证的部分。 这条禁令是工程规范里的固定收尾检查，不在 CI 里：grep -rniE 'h2|disabledWithoutDocker|DisabledIf|assumeTrue|@Disabled' backend/pom.xml backend/src 必须无匹配（本次执行无匹配）。

2.3 三条从故障中学到的测试原则

原则一：服务层测试证明不了 MVC 映射

三个 DELETE 端点首次交付时只有服务层测试。路径接线与状态码没有任何证明—— 一个写错的路径会在服务层测试里全绿，到了前端就是 404。 BatchOneApiTest.theThreeDeleteEndpointsAreWiredAndInvisibleAcrossProjects 在真实 HTTP 之上断言路径、204 状态码与跨项目不可见性。

项目归档端点按同一原则处理：theArchiveEndpointsAreWiredAndReversible 走真实 HTTP，同时断言归档什么都不删。

原则二：组件全绿而无人调用

本项目发生过两次：一次是全部验收条件通过，而 AiGateway.chat 没有任何生产调用方； 另一次是引擎每个部分单独测过，而 ReviewExecutor.run 抢到 Review 后就停了。

组件测试按构造看不到这个问题——每个测试在「没人调用它」时通过得一样好。 所以 ReviewPipelineIntegrationTest 从 scm 发布的事件出发、断言数据库里的行， 中间只替换 provider，其余全是真实组件。

原则三：会过期的论据要写成测试，不要写成笔记

「为什么这个部署没有向量索引」是一条基于 pgvector 当前能力的论断。 写成 markdown 里的研究结论，它会静默过期；写成 KnowledgeVectorIndexTest， pgvector 一旦放宽维度上限，测试就会失败——而那次失败正是回来重新决策的信号。

该测试三个用例分别钉住：三种索引形态各自的拒绝理由、唯一能建出的两种形态都是有损预筛、顺序扫描在冻结维度上给出精确余弦序。

4.3 几个值得单独说明的用例

数据库约束测试绕到应用代码之下

DatabaseConstraintTest 通过 JdbcTemplate 直接写入，绕过全部服务层， 并点名它期望的 SQLState：23505（唯一冲突）、23503（外键违例）、23514（CHECK 违例）。

一条只被服务强制的约束等于没被强制——未来任何调用者都能绕开它。

迁移测试针对非空表

ALTER TABLE … ADD CONSTRAINT … CHECK 会校验表中已有的行。 因此一条不容忍 NULL 的 CHECK 在新建的空 schema 上必然通过，然后在任何已有数据的部署上直接让迁移失败。

FoundationDatabaseTest 迁移的是空 schema，看不见这件事。 所以 V9MigrationTest 与 V10MigrationTest 采用唯一有效的形状： 先迁到上一版、写入一行、再迁剩下的。

并发测试要求交错被观察到，而不是被假设

ScmIdentityFreezeConcurrencyTest 不用 sleep 等待，而是向 PostgreSQL 询问 另一个线程是否真的阻塞在那一行上。否则这个测试在「线程池根本没启动任务」时也会通过， 退化成它本要补充的单线程用例。

架构规则是可执行的，不是文档约定

ArchitectureRulesTest 8 个用例强制九包依赖单向无环、禁止的包名不存在、 scm 不依赖 review。它导入的是生产类， 所以测试作用域的监听器不会削弱这条规则。

5.1 lint 策略检查的内容

npm run lint 不是通用代码风格检查，而是四条项目策略：

  • 无 tab、无行尾空格。
  • 原始色值只允许出现在 tokens.css，其他文件必须用设计令牌。
  • 禁止依赖清单：HTTP 客户端、状态管理、CSS 框架、UI 组件库与图表库共 14 个包名。
  • 扫描范围含 src/、tests/ 与根级配置文件。
jsdom 的两处能力缺口影响了实现选择

jsdom 30.0.1 不实现 <dialog>（showModal 与 close 均为 undefined）， 也不实现 navigator.clipboard。

这两点是实测确认后才做的设计决定：归档确认层因此采用卡片内联面板而非模态框； 复制按钮的剪贴板调用必须包 try/catch，失败时不报错也不拦路——项目名就在旁边的只读输入框里可手动选中。

6.2 冻结完整性验证

两条命令在不接触任何凭据的前提下证明证据未被篡改，均通过：

python3 evaluation/tools/formal_evaluation.py verify-freeze
python3 evaluation/tools/postfreeze_provider_correction.py verify

前者按内容哈希核对 9 个模型面与评分文件；后者绑定实际使用的端点， 同时确认模型、温度、Prompt、评分器、语料与划分均未变更。

一次真实的近失事件

在一轮「文档只保留当前功能」的清理中，evaluation/contracts/metrics.md 曾被当作普通指标说明文档 列入待清理项。它在冻结哈希列表内——改动它会使 verify-freeze 永久无法通过， 而 holdout 只运行过一次且不可重跑，冻结证据一旦失效就无法重建。

检查后确认该文件内容无需改动，未被修改。由此形成流程要求： 动 evaluation/ 下任何文件前，先运行 verify-freeze 取得那份列表，再与改动清单比对。

CI 每次构建都做两次全新卷冷启动。两个独立的 Compose 项目各自从空卷起栈，scripts/phase1-compose-smoke.sh 断言以下契约后再清理自己创建的项目与卷；提交 370bfc4 的 CI 上两次均通过：

  • PostgreSQL 版本 ≥ 15，vector 扩展已安装，距离运算返回预期值。
  • Flyway 十五条版本化迁移全部成功，最高版本 V15 成功。
  • public 中恰好这二十一张业务表，按 C 排序逐字符比对（不依赖容器 locale）。

线上演示栈 fp-demo 以保留数据的方式升级。每次发布只重建 backend 与 frontend 镜像，PostgreSQL 容器与数据卷不动，迁移由后端启动时应用。2026-11-14 只读核对：三个容器均 healthy，flyway_schema_history 中 15 条版本化迁移全部成功、最高 V15，public 下 21 张业务表；健康接口在本机经前端代理与公网均返回 UP。逐次发布的镜像身份、备份与核对命令记录在对应的 Trellis 任务里，不在本报告重复。

冷启动脚本的期望值不被后端测试覆盖

脚本自己断言迁移条数、最高版本与完整的表清单；FoundationDatabaseTest 里另有一份表清单， mvnw verify 只证明后者——后端测试证明不了一个 shell 脚本的期望值。 V9 与 V10 落地时脚本就漏了同步，停在「8 条迁移、19 张表」：复现指南指定的冷启动证明与 CI 的这项作业 对当时的 schema 必然失败，而后端套件一直全绿。

由此形成的规则：每新增一条迁移，同步脚本里的迁移计数与最高版本检查； 迁移新建了表，再同步 FoundationDatabaseTest.EXPECTED_TABLES 与脚本的 expected_tables。 这条规则目前靠规范约束，没有机制保障。

8.3 有意不做的测试

以下测试刻意没有写，理由记录在此以免后续被当作缺口补上：

  • 不为 DTO / record 的 getter 写测试——它们没有行为，测试只会重复声明。
  • 不重复测已由类型系统保证的性质——例如「FAILED 的 Review 没有 Report」是构造器强制的，写测试只是复述编译器。
  • 不为覆盖率补测——本项目不设覆盖率目标；答不上「锁住哪个不变量」的测试不写。
  • 不测模型输出质量——那属于评测体系，用固定语料与确定性评分器度量，不属于单元测试。

8.4 已知限制：Finding 身份的连续性

状态：已知 · 暂不改规则

finding_key 包含 patch 新侧行号与模型给出的类别，evidence_hash 基于逐字引用。 无关插入造成行号整体移动、同一问题换了类别标签、或引用少了行首缩进时， 同一 Finding 都可能被记录为 NEW，从而无法继承上一轮的 SUPPRESSED，削弱 P10 的自动抑制效果。 自动化测试钉住的是规则本身（同输入得同 key、哈希不覆盖模型散文），钉不住模型两轮之间是否给出同样的行号与类别。

彻底修正需要调整跨 Review 的 key/hash 规则并处理历史数据；当前作为已知限制记录，不把它写成已解决的连续性保证。

9已发现的缺陷

本章只收测试或审读实际抓到的问题，以及它们留下的规则。五条均已修复；仍然存在的限制在第 8 章。

9.1 已修复：测试套件依赖类的执行顺序

状态：根因已定位 · 已修复（只动测试侧）

现象。仅重命名 BatchOneApiTest（diff 中没有任何代码行变化）， 该类就在完整构建中失败：断言 GET /api/auth/me must issue the XSRF-TOKEN cookie，实际取得的 cookie 为 null；单独运行该类全绿。

根因。污染源不在应用代码，而在测试装配：spring-security-test 的 .with(csrf()) 在装配请求时，把共享过滤器链里 CsrfFilter 的 CsrfTokenRepository 换成一个包着 HttpSessionCsrfTokenRepository 的测试替身，token 因此落进 session 而不写回响应 cookie。 替换在请求结束后仍留在原处：同一 JVM 里只要有一个类用过它，其后所有类都改走 session 仓库。 谁先谁后由测试类的文件名顺序决定，所以一次重命名就足以换来失败。

修复。6 个测试类共 14 处 .with(csrf()) 改走应用真实的双提交路径 （PostgresTestBase.spaCsrf()：cookie 与 header 回显同一个值），不再有任何全局副作用。 生产代码未改——SecurityConfig 的 SPA 接线本身是对的。在仓库外的副本里把该类改名后， 原先稳定失败的那条命令 139/139 通过。

留下的线索。若再出现「单类运行绿、全量运行红」，先查是否有测试类用了 SecurityMockMvcRequestPostProcessors.csrf()，不要去改 SecurityConfig。 根因定位之前，这个问题有一个半月复现不了；那段时间没有为它加 @DirtiesContext 之类的兜底—— 给一个复现不了的问题贴处置，只会多付一个 Spring 上下文，并让下一个人误以为它已被解决。

9.4 已修复：文档中的过期数字

多份文档曾手写测试用例数，而用例数几乎每次提交都在变：每修正一次，下一次提交又让它落后， 包括本报告自己。处置不是再改一次数，而是把两类数字分开：结构性数字 （包数、表数、迁移数、导航数、路由数）由测试断言，改动即变红，可以写死； 用例数不被任何东西钉住，因此只出现在本报告里，并标明取数日期与产生它的命令。 一个标着日期的数字过期时是诚实的，一个不标日期的数字过期时是错的。

9.5 测试执行过程中暴露的一个方法学问题

把构建输出管进 tail 会掩盖真实的失败

早期执行曾两次将 Maven 输出通过管道传给 tail。管道的退出码来自最后一个命令， 因此 tail 的 0 掩盖了 Maven 的 BUILD FAILURE，一次真实失败被误读为通过。

正确做法：重定向到日志文件再检索，并显式检查退出码。 本报告的所有结果均按此方式取得。

10.2 可以支持的结论

  • 业务规则、状态机与授权边界有自动化验证，且约束由数据库本身而非仅服务层强制。
  • 并发与失败路径真的被执行过，不是靠代码审查推断——抢占竞争、租约过期、provider 不可达、结构非法的回答各有用例。
  • 架构约束可执行，依赖方向由构建强制而非文档约定。
  • 评测证据完整且可核验，重算不需要任何凭据。

10.3 不能由本报告支持的结论

三条界限

不能得出「界面正确」。视觉、布局、键盘可达性与动效均无自动化覆盖； 已有的浏览器检查（8.2）是只读的，且早于最近几次界面改动。

不能得出「与两家平台的真实集成都已验证」。GitHub 有真实 PR 与一次真实合并的线上演练； GitLab 与钉钉只对回环桩服务验证过，没有真实实例上的端到端记录。

不能得出「AI 审查质量」。审查链路的集成测试用脚本化响应替代模型，证明的是调用链接通与规则执行。 模型质量由评测体系度量：holdout 仅 12 例且缺陷为手工构造，报告给出 95% Wilson 区间并明确声明泛化限制； 当前提示词版本 review-6 还没有独立的真实样本与人工真值。

  1. 补做人工验收：按 frontend/MANUAL-ACCEPTANCE.md 用三种角色在真实浏览器里走一遍写操作，重做三档宽度检查，并把结果留档。
  2. 用一次性账号做真实 GitLab 与钉钉演练，补上 10.3 第二条界限。
  3. 为 review-6 建立独立样例与人工真值，分开记录命中、误报与漏报；不调参、不重跑已冻结的 holdout。
  4. 为「迁移与冷启动脚本同步」增加机制保障——目前靠规范约束，而它已被遗漏过一次。
