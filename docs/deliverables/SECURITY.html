ForgePilot 安全设计说明

ForgePilot 持有三类高价值秘密：用户口令、代码仓库的访问令牌、以及 webhook 签名密钥。 它还有一个公开且未认证的 HTTP 端点，以及一条把用户内容发往第三方模型服务的出站通路。 本文说明针对这些面的防护措施、每条措施的具体实现，以及明确未被防护的部分。

1范围与威胁模型

1.1 保护对象

资产泄露后果存储形态
用户口令账号被冒用BCrypt 哈希，不可逆
仓库访问令牌攻击者获得目标代码仓库的读写权AES-256-GCM 密文
Webhook 签名密钥攻击者可伪造投递，注入虚假 PR 状态AES-256-GCM 密文
一次性个人 Token攻击者获得该用户的 provider 身份读取权从不存储
需求、知识文档、diff项目内容外泄明文（业务数据）
评测冻结证据实验结论不可信内容哈希钉住

1.2 假定的攻击者能力

  • 能向任意公开端点发送任意字节——包括畸形 JSON、超长字段、构造过的域名。
  • 能测量响应时间与响应差异——用于时序攻击与存在性探测。
  • 能诱导已登录用户的浏览器发出请求——CSRF。
  • 能控制送进系统的内容——需求正文、知识文档、PR 标题、代码注释。
  • 可能是一个已认证的普通用户，试图访问其他项目的资源。

1.3 假定不设防的范围

明确的信任边界

数据库与应用进程之间的网络被视为可信（同一 Compose 网络，PostgreSQL 不对外暴露端口）。 宿主机与部署者被视为可信——能读取 .env 的人本就掌握全部秘密。 模型服务提供方被视为半可信：会收到脱敏后的业务内容，但不被授予任何写权限。

2认证与会话

2.1 口令存储

使用 Spring Security 默认的 BCrypt——一种为存储口令设计的慢哈希，使暴力破解昂贵。

数据源口令没有默认回退值。未配置的部署启动失败，而不是悄悄用一个弱默认值跑起来。ScmSecretKeyStartupTest 断言这一点。

2.2 两种登录失败在字节层面不可区分

「用户名不存在」与「口令错误」共用同一个响应体，且 traceId 为空。

为什么 traceId 必须为空

统一错误处理器只在同时记录原因的地方才生成 traceId。 如果这里逐响应生成一个值，两种登录失败就会在字节层面变得可区分—— 攻击者据此可以枚举哪些用户名存在。

这条约束写在 SecurityConfig 的常量注释里，因为它看起来像「忘了填 traceId」，实际是刻意的。

2.3 会话与改密联动

会话是服务端进程内 HttpSession。user_account 上有一列 session_version：

  1. 会话建立时，把当时的 session_version 捕获进 HttpSession。
  2. SessionVersionFilter 在每个请求上把会话里的值与库中的值比对。
  3. 改密时递增库中的值。

结果：一次改密杀掉除执行改密那个会话之外的全部会话。 执行者不必重新登录，其他设备上的会话在下一个请求即失效。

2.4 CSRF

采用 Spring Security 7.1 内置的 SPA 接线（CsrfConfigurer::spa）：Cookie 仓库 + 一个使每个响应都带上 XSRF-TOKEN 的处理器。

那个处理器不是可选的

没有它，延迟生成的 token 永远不会写出——前端拿不到令牌，所有写请求都会被拒。 前端侧由 lib/http.ts 统一在写请求上回显该令牌，凭据使用 same-origin cookie。

缺失或错误的 CSRF 令牌是访问被拒的唯一来源——这使 403 的含义单一，便于排查。

2.5 端点暴露面

管理端点只暴露 health。ActuatorExposureTest 断言：

  • /actuator/health → 200，含 "status":"UP"
  • /actuator/metrics → 404（不是 401、不是 403——它根本不存在）
  • /api/auth/me 未认证 → 401

2.6 速率限制

三个端点带应用层限流，实现是 common/RateLimiter（固定窗口计数器）加 common/RateLimitFilter（超配额时直接以 429 与统一错误体作答的 servlet 过滤器）。 配额在 application.yml 的 forgepilot.security.* 下，可用环境变量覆盖。

端点默认配额它防的是什么
POST /api/auth/login20 次／分钟／地址口令暴力枚举
POST /api/auth/register5 次／10 分钟／地址账号洪泛
POST /api/scm/*/webhook60 次／分钟／地址未认证请求消耗资源（下方说明）

被限的只有这三个「无需认证即可触达、且会做昂贵工作」的端点：登录要算一次 BCrypt， 注册要写一行，webhook 投递在验签之前就要解析 JSON 并查库定位仓库、验签之后还要发起一次出站的 权威读取——所以对 webhook 的洪泛是有放大效应的。已认证成员的正常操作不限流，否则批量添加成员之类的 动作会被误伤。

两个 auth 限流器装在认证之前，这是它的意义所在

它们挂在 UsernamePasswordAuthenticationFilter 之前。装在认证之后的话， 每一次被限的登录仍会先付一次 BCrypt 的代价——而那正是这道限流要省下的东西。 这类装配错误在单元测试里全绿，因此 AuthApiTest 有一条走完整 MVC 链的测试， 确认限流确实在真实过滤器链里生效并答出那个唯一的错误体。

键空间打满时放过，而不是拒绝

限流表对「单个窗口内跟踪多少个不同地址」封了顶（10 000），内存因此有上界。超顶之后对新地址一律放过。 反过来写会让这道限流可被利用：攻击者用大量伪造源地址把表填满，此后每个正常用户都被拒—— 那是把防护措施变成了拒绝服务的放大器。极端情况下宁可退化成不限流。 RateLimiterTest 锁住这一条，以及配额本身与窗口翻转（否则第一个窗口用完就永久拒绝）。

同一条链上装两个限流器，第二个曾整个失效

RateLimitFilter 继承 OncePerRequestFilter，而基类默认用类名 做「本请求已过此过滤器」的标记。auth 链上装着本类的两个实例，第一个打上标记之后， 第二个会在每个请求上整个跳过自己——注册限流因此完全失效，而注册照常返回 201， 没有任何报错或日志。修法是让标记按实例名区分（覆写 getAlreadyFilteredAttributeName()）。这一条现在由 AuthApiTest 里 针对注册端点的独立测试锁住：只测登录是发现不了它的。

地址取 getRemoteAddr()，而它是否等于真实客户端取决于 server.forward-headers-strategy。本部署设为 native：nginx 是唯一入口， 会把真实地址追加进 X-Forwarded-For，Tomcat 的 RemoteIpValve 只信任内网网段的代理并从右往左取第一个非内网地址，因此客户端自己伪造的 X-Forwarded-For 拿不到信任。不开这个开关才是危险的——那时每个请求都记成 nginx 那一个地址，配额变成全体共享，而被丢掉的 webhook 投递不会被 provider 重试。 剩下的风险见第 10 章第 4 条。

3授权与项目隔离

3.1 单一授权入口

项目内一切操作的授权只经由 ProjectAccessService （requireMember / requireRole）。其他模块不允许自己去读成员表。

这个约束的价值是可审计性：想知道「哪些操作要求 LEADER」，搜索这一个方法的调用点即可，不必逐个模块排查。

3.2 项目角色刻意不做成全局权限

ProjectRole 不是 Spring Security 的 authority。 全局安全体系只区分「已认证」与「匿名」；项目角色是项目内概念，在服务层判定。

如果把项目角色提升为全局 authority，一个用户在 A 项目的 LEADER 身份就可能被误用于 B 项目。

3.3 项目隔离靠 schema 而非纪律

每个项目内外键都携带 project_id，因此所有读路径都带 projectId。代码库里不存在「先按裸 id 查、之后再检查项目」的写法。

为什么这不只是编码规范

「先查再检查」有两个问题：一是检查可能被遗漏；二是即使不遗漏也已经泄露了信息—— 查询本身能区分「id 存在但属于别人」与「id 不存在」。

带 project_id 的复合键让这个区分在数据库层就不成立。 ProjectAuthorizationTest 与 BatchOneApiTest 断言： 外项目的 id 与从未签发过的 id 返回相同状态码。

3.4 权限判定用稳定 id，不用用户名

「这个 PR 是不是我开的」按项目级稳定外部 user id 判定，绝不按用户名。 用户名可以被重新分配——按名字匹配会把别人的 PR 交给一个改过名的账号。

没有已核验 SCM 身份的成员匹配不到任何东西，这是 fail-closed 的方向。

3.5 一条容易被忽略的权限设计

Finding 的「认领」只有 DEVELOPER 能做，LEADER 也不能。 认领意味着「我来修」，是本人动作。因此系统里没有「指派 Finding」这个端点—— 少一个端点，也少一个授权面。

4凭据管理

4.1 静态加密

参数取值
算法AES-256-GCM（AES/GCM/NoPadding）
IV 长度12 字节，每次加密随机生成
认证标签128 位
信封格式IV ‖ 密文（IV 前置，解密时按固定长度切分）
密钥来源环境变量 FORGEPILOT_SCM_SECRET_KEY

选 GCM 而非 CBC 的理由是它自带认证：密文被篡改会在解密时失败，而不是解出一段垃圾明文。

4.2 只写不回显

访问令牌与 webhook 密钥是只写字段：

  • 响应体不包含它们——ScmRepositoryResponse 在类型层面就没有这两个字段。
  • 页面任何位置不回显，前端表单提交后清空。
  • 修改时留空表示保持原值，因此改别的字段不需要重新粘贴凭据。
  • 不写入日志。

4.3 一次性个人 Token 从不存储

成员验证自己的 SCM 身份时提交一个个人 Token。它被用于一次 provider 调用， 然后即被丢弃：不返回、不持久化、不记日志。

系统存下来的只是验证结果——远程用户名与稳定外部 id。

4.4 冻结证据的完整性

评测的模型面与评分文件（共 9 个）由内容哈希钉住。 verify-freeze 在不接触任何凭据的前提下核对它们未被改动。

冻结记录本身只保存 apiKeyPresent: true/false，从不保存密钥或授权头。

5Webhook 认证

这是系统唯一公开且未认证的入口，因此防护最密。

5.1 HMAC 覆盖原始请求字节

控制器接收的是 byte[] body，不是解析后的对象。 HMAC 必须覆盖原始字节——JSON 解析再重新序列化会改变字节（键序、空格、数字格式），指纹就对不上。

原始字节因此一路带到验签处，这是签名机制成立的前提，不是实现偏好。

5.2 常数时间比较

比较使用 MessageDigest.isEqual，不是 equals 或 ==。

为什么普通比较不行

字符串比较发现第一个不同字符就立刻返回，因此「第一个字符就错」比「只有最后一个字符错」返回得更快。 攻击者测量这个时间差，可以逐字符把正确签名试出来——这是时序攻击。

该方法还对长度安全：被截断的十六进制摘要只会判为不相等，不泄露长度信息。

5.3 GitLab 双代机制不降级

当前版本 GitLab 按 Standard Webhooks 签名，较老安装发送明文秘密 token。 规则是：Standard 形式存在但校验不通过时，绝不降级到更弱的旧版形式。

否则攻击者只需构造一个「新版签名故意写错」的请求，就能把整个校验降到较弱的那条路径上。

5.4 校验前的任何失败都答成同一种

控制器把「解析载荷 → 定位仓库 → 验签」整段包在保护块里：

try {
    payload = parse(body);
    repository = sync.authenticate(...);
} catch (ApiException rejected) {
    throw rejected;
} catch (RuntimeException malformed) {
    throw unverifiable();          // 一律答成「无法验证」
}
这个保护块防的是两件事

一、堆栈逃逸。端点是公开的。一个恶意载荷若能触发意外异常， 默认错误页会带出堆栈与内部结构，且脱离统一错误契约。 代码注释点了两个真实能触发的例子：在该出现字符串的位置放一个容器节点， 或让一个超过 63 字符的 DNS label 走到 IDN.toASCII。

二、不可区分性。「载荷畸形」「仓库不存在」「签名错误」答得一模一样， 攻击者无法据错误差异探测本部署接入了哪些仓库。

5.5 认证之后仍不信任载荷

签名验过只证明发送方知道密钥，不证明载荷内容是当下事实。 因此系统回头向 provider 做一次权威读取：webhook 是信号，权威快照才是事实。

这同时防住重放：带更旧时间戳的快照被丢弃，不覆盖较新状态。

5.6 权威字段必须大声失败

Jackson 的 asString() 对缺失与 null 节点都返回空字符串。不检查的后果：

  • 缺失的 base.sha 变成 base_sha = "" 入库。
  • 该列是 NOT NULL，而 "" 满足 NOT NULL——数据库抓不住。
  • diff 指纹基于空 SHA 算出，这次审查的身份从此是错的。

author_external_user_id 更严重：它是授权键。 若变成 ""，所有「幽灵作者」的 PR 会共享同一个身份，「本人 PR」权限就串了。 GitHubClientGuardTest 20 个用例专门覆盖这条路径。

6出站请求控制

6.1 为什么需要这道闸

scm_repository.api_base 由项目负责人配置，用于支持自建实例。 这使它成为一个 SSRF 入口：指向 169.254.169.254 就能读取云元数据服务， 进而可能取得云凭据。

6.2 策略内容

检查规则
协议只允许 http 与 https
主机白名单唯一放行途径：forgepilot.scm.allowed-hosts 中的显式主机
内网地址解析后逐个地址拒绝 loopback、any-local、link-local、site-local
大小写协议与主机统一转小写后比较，防大小写绕过

注意解析后再判定：仅检查字符串无法防住一个解析到 127.0.0.1 的公网域名。 link-local 的拒绝正是覆盖 169.254.0.0/16 这个云元数据网段。

6.3 每次调用重新校验

每次出站调用前都重新校验地址，而不是在配置保存时校验一次。 因为该列可由负责人随时修改，而安全策略也可能在此期间收紧。

6.4 不硬编码任何 host

provider 的 base URI 全部来自 api_base，代码中不硬编码任何 host。 这既是自建实例支持的需要，也顺带让集成测试能把仓库指向回环桩服务—— 白名单里加入 127.0.0.1，策略本身仍然开启，而不是为测试关掉它。

7AI 相关安全

7.1 唯一出口

全代码库只有 AiGateway 能向模型服务发出请求。 它管 HTTP、鉴权、超时与那唯一一次重试，且不认识任何业务类型—— 业务归属以不透明的 Long id 经 AiCallContext 传入。

单一出口的安全价值：所有发往外部的内容必然经过同一处脱敏，不存在绕过路径。

7.2 发送前的处理

PromptSanitizer 做两件事，且只做这两件：掩码疑似凭据的字符串、把载荷裁剪到预算内。

它是纯函数，这是刻意的

不写日志、不碰数据库、不抛异常。 一份文档不会因为「看起来含 token」而被整份拒绝，只会去掉那部分后照常发送。

拒绝非法输入是另一件事、另有归属（KnowledgeUploadValidator 在入库前拦截）。把两件事混在一处会让上传变得不可预测。

7.3 全部用户内容视为不可信

需求文本、知识文档、PR 标题与代码注释全部是不可信数据。它们会进入 Prompt。

7.4 真正的防线是「AI 不改变任何业务状态」

诚实说明：本系统不防 Prompt 注入

PromptSanitizer 不是 Prompt 注入防护——它只掩码凭据。 一个精心构造的需求正文确实可能影响模型的输出内容。

系统的实际防线是架构层面的：AI 不改变任何业务状态。 它不能推进需求状态、不能修改代码、不能提交、不能合并、不能授予权限、不能删除任何东西。 模型输出的全部去处是——通过校验后写入 finding 表，等待人工处置。

因此注入成功的最坏后果是一条误导性的审查意见出现在页面上等待人看， 而不是任何自动执行的动作。这是把「无法可靠防住的输入」限制在「无权限的输出」上的设计选择。

7.5 模型输出同样被视为不可信

ReviewOutputValidator 对模型回答逐项核验，且核验发生在写入之前：

  • 路径必须是本次调用被展示过的变更文件之一——一个批次无法对它从未见过的文件作出报告。
  • 验收条件 id 必须属于本次被审查的那个修订——来自别的修订的 AC 读起来同样合情合理，但它针对的是另一段文本。
  • 无证据的 finding 被丢弃：没有逐字引用就没有确定性的东西可供哈希。
  • 散文字段有长度上限（2000），模型不遵守时在此截断。

被丢弃的断言记入 warnings 而非静默移除——静默丢弃只会让运维拿到一份更短的报告，却无法知道它被缩短过。

7.6 失败不放大成调用风暴

  • 重试只有一次，且只对瞬时错误（429/5xx/网络）。全代码库别处没有任何重试。
  • 格式修复只有一次，写成 try/catch/try 而非循环——循环会把网关那次有界重试放大成四次调用。
  • provider 不可达时 Review 标为 FAILED 并停下等人工，而不是让异常逃逸后被对账任务反复重新抢占、反复重调。

8审计与留痕

8.1 三类永久记录

表记录什么关键设计
ai_call_log每一次模型调用尝试重试留两行——这是事后审计「确实只重试了一次」的唯一手段；TIMEOUT 与 FAILED 分开记录，以便区分「答得不对」与「根本没答」
finding_eventFinding 每一次人工决定同时记录操作者意图与机械的 from/to 状态对；actorId 指向 user_account 而非成员关系，成员离开项目不抹掉记录
pull_request_requirement_eventPR↔需求关联的每次变更与变更本身同一事务——关联变了却无审计行、或有审计行却描述了未提交的变更，两者都比没有审计更糟

8.2 删除台账

project_deletion_record 记录三类资源的删除事实。 它的 resource_id 故意没有外键——被引用的行按定义已经不存在， 没有可指向的目标。加一个外键会使这张表无法记录它存在的全部理由。

这张台账反过来保护了项目本身

project_deletion_record.project_id 有一条指向 project(id) 的外键， 且没有 ON DELETE。因此硬删一个项目会被这张记录删除行为的台账挡住—— 要硬删就得先销毁删除审计。

这正是项目「删除」被实现为归档的原因：数据库先做了这个决定。

8.3 不外送、不聚合

审计记录只存在于业务数据库，不外送到任何日志聚合或监控系统。 这减少了泄露面，代价见第 10 章残余风险第 7 条。

8.4 日志中不出现的内容

  • 凭据、令牌、webhook 密钥、口令与其哈希。
  • provider 的原始报错消息——它可能引用回答，而回答可能引用 Prompt。失败原因经过改写后才进入运维可见输出。
  • Docker 检查输出与环境变量转储不得作为证据归档（复现指南明文规定）。

10残余风险

以下风险已知，且当前未防护或仅被部分缓解。列出它们，是因为一份只写防护措施的安全文档会被误读为「没有剩余风险」。

#风险现状与理由影响
1 不防 Prompt 注入 见 7.4。防线是架构性的——AI 无任何写权限 最坏后果是一条误导性审查意见等待人工处置，无自动执行动作
2 凭据加密不做密钥轮换 轮换需要密钥版本列加一次重加密扫描，属新结构，明确划在范围外 密钥泄露后必须手工重新配置全部仓库凭据
3 单一对称密钥 所有项目的凭据用同一个 FORGEPILOT_SCM_SECRET_KEY 该密钥泄露即全部仓库凭据泄露，无项目级隔离
4 限流的可信度取决于「nginx 是唯一入口」这个部署前提 见 2.6。forward-headers-strategy: native 让 Tomcat 从 X-Forwarded-For 解析客户端地址，且只信任内网网段的代理 若哪天应用端口被直接暴露、绕过 nginx，客户端伪造的 X-Forwarded-For 就会被采信，限流形同虚设。这个前提由部署配置保证，代码无法自证
5 无多因素认证 本地账号只有口令一个因素 口令泄露即账号失守；改密可踢出其他会话，但这是事后手段
6 归档不冻结写入 project.status 不 gate 任何写路径；变为只读闸门需改五个模块 已归档项目的需求、知识、仓库与审查仍可写入
7 审计不外送 只存业务库，无外部聚合 取得数据库写权限者可篡改审计；无独立副本可比对
8 TLS 依赖部署侧 应用自身不终结 TLS；出站连接的证书校验依赖 JDK 默认信任库 反向代理配置不当会使会话 cookie 与凭据在明文信道上传输
9 知识文档无内容分级 上传的项目知识会整体进入检索与 Prompt，无「不发往模型」的标记 误上传的敏感文档会被发往模型服务；凭据类字符串由掩码兜住，其余内容不会

10.1 建议的处置优先级

  1. 确认应用端口没有绕过 nginx 暴露（#4）——整套限流的可信度都压在「nginx 是唯一入口」上。Compose 默认把端口绑在 127.0.0.1（FORGEPILOT_BIND_ADDRESS），改动它之前先想清楚这一条。不需要改代码。
  2. 确认部署侧 TLS 配置（#8）——不需要改代码，但配置错误的后果最严重。
  3. 知识文档分级（#9）——一个「不参与检索」的标记即可显著降低误发风险。
  4. 密钥轮换与项目级密钥（#2、#3）——需要迁移与重加密，规模较大，适合作为独立工作。

风险 #1 与 #6 是有意接受的设计取舍，不建议在当前范围内改动；#5 与 #7 取决于部署场景，单机演示环境下优先级低。
