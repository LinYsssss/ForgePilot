01系统是什么

普通的 AI 代码审查看到的只有 diff，所以它只能回答「这段代码写得好不好」。 ForgePilot 的出发点是另一个问题：这次改动有没有做到需求要求的事。 为此它把三样东西一起送进模型上下文——变更 diff、该 PR 关联的需求与验收条件、以及项目知识库里检索到的片段。

一条完整的因果链

整个系统只为这一条链服务，其余都是它的支撑：

需求 + 验收条件人工录入，不可变修订
PR 到达webhook 认证 + 权威读取
REQ-n 关联自动猜测，人工可纠正
上下文冻结head + diff 指纹 + 需求修订
分批送模型批次只给候选，不下结论
综合阶段唯一有资格下裁定的地方
Finding 落库三个确定性哈希
人工闭环认领 → 修复 → 复核 → Decision

三个角色

角色能做什么
LEADER建项目、加成员、写需求并冻结、上传项目知识、配置仓库、记录最终 Decision、归档项目。一个项目恰好一个 LEADER，只能显式转移。
DEVELOPER认领 Finding、标记已修复、绑定自己的 SCM 身份、对自己的 PR 纠正需求关联。
REVIEWER复核 Finding（通过或打回）、记录最终 Decision。

同一个人可以同时是开发和评审，权限取能力并集。

能力边界（会被问到，所以先说清）

语义检索没有向量索引

这是决策，不是遗漏。冻结的 Embedding Profile 是 4096 维， 超过 pgvector 0.8.6 全部精确索引形态的上限；能建出来的两种（二值量化、截断到 2000 维） 都是有损预筛，还得再补一个 rerank 阶段。MVP 语料规模下顺序扫描给出的就是精确余弦序， KnowledgeVectorIndexTest 在冻结维度上把这三件事逐条钉住了。

评测结论的准确表述

三臂评测比较的是上下文构成，不是某条检索管线。评测 runner 自己组装上下文、 对后端零引用，第三臂把 case 的知识文件全文渲进 prompt，既不做 embedding 调用也不做 TopK 检索。 所以 21.62% → 32.26% 证明的是「把需求与项目知识放进上下文有用」， 不是「ForgePilot 的 pgvector 检索有效」。检索是产品能力、有自己的测试，但不是这组数字评的东西。

归档不冻结写入

project.status 目前不 gate 任何写路径（全库只有 ProjectResponse 读它用于展示）， 所以归档只是从工作区列表收起来，该项目的需求、知识、仓库、审查仍然可写。

AI 置信度不参与任何自动门禁

模型自报的把握未经校准，所以只记 HIGH/MEDIUM/LOW 三档而不是数字——精确数字会暗示它校准过。 它不进任何哈希，也不推进任何状态。

02部署与启动

需要 Docker（Compose v2）、Git。跑前端门禁或后端构建时另需 Node 24 / Java 21，本机没有 JDK 时走容器路径。

首次部署

  1. 准备环境变量 从模板复制，然后务必改掉数据库口令与 FORGEPILOT_SCM_SECRET_KEY。 .env 被 Git 忽略。聊天与 embedding 的值可以留空——空栈演示和确定性重算都不需要它们。 
    cp .env.example .env
  2. 冷启动自证 这个脚本会新建一个独立 Compose 项目和全新数据卷，等三个健康检查、校验反向代理、pgvector、 Flyway 十条迁移与恰好二十张业务表，然后只删掉它自己建的那套临时资源。 
    FORGEPILOT_BACKEND_PORT=28080 \
FORGEPILOT_FRONTEND_PORT=28081 \
scripts/phase1-compose-smoke.sh forgepilot-phase1-defense-clean
  3. 正式启动 
    docker compose up --build --detach --wait
    后端健康契约是 /actuator/health；经前端代理是 /api/actuator/health。
  4. 创建第一个账号 没有任何迁移携带种子数据，所以仓库里不存在任何口令。第一个账号通过 POST /api/auth/register 建立，注册者创建项目时在同一个事务里成为该项目 LEADER。

一次完整走查

  1. LEADER 建项目与需求 建项目 → 加成员并分配角色 →「研发需求」写一条带验收条件的需求。 DRAFT 阶段正文可原地编辑；DRAFT → READY 在同一个事务里冻结。 冻结后任何变更都是发布 seq + 1 的新修订并填写变更原因，旧验收条件永久保留。
  2. 上传项目知识 「项目知识」上传 .txt / .md，可一次选多个文件。 每个文件是独立一次调用、独立一个事务，所以逐文件报告成败，一个失败不影响其余。 上传后能看到切片数、已嵌入数、向量维度、Embedding Profile 与索引状态。
  3. 配置仓库 「仓库接入」注册 GitHub 或 GitLab：外部仓库 ID、API 基地址、访问令牌、webhook 密钥。 最小权限：GitHub repo（公开仓库 public_repo），GitLab read_api。 成员各自在 /account 用一次性个人 Token 验证自己的 SCM 身份（GitHub read:user / GitLab read_user）。
  4. PR 到达，Review 自动建立 webhook 先对原始字节认证，再回头向 provider 做一次权威读取（不信任载荷内容）， 标题或分支里出现 REQ-<id> 时自动关联需求，然后创建共享的 PENDING Review。 关联只是入库时的一次猜测，最终话语权在页面：LEADER 随时可改，PR 作者在当前 head 尚无终局 Decision 时也可改。
  5. 人工闭环 DEVELOPER 认领并标记已修复 → REVIEWER 复核通过或打回 → LEADER 或 REVIEWER 记录一次性的 Review Decision。 每次流转可填备注，审计永久保留。
  6. 新 head 让旧 Review 成为历史 推新 commit 后，之前那次 Review 变为「已过期」，而需求状态始终由人控制—— AI、Webhook、PR、Review 一律不得推进需求状态。

删除与归档的三种语义

三类资源三种策略，不一致是结论而不是妥协——决定它的是三组外键语义：

资源语义为什么
知识文档硬删切片与向量是纯派生数据，随文档一起消亡（同事务显式删 chunk）。
项目成员硬删成员关系是活权限。删除时靠进程内事件让三个模块各自撤销指派、认领与绑定。
作废需求软删ai_call_log 与 pull_request_requirement_event 都挂在这一行上，物理销毁它就是销毁调用审计、抹掉一件已发生的 PR 关联事实。
项目归档数据库先做了决定，见下。
项目为什么只能归档

project_deletion_record.project_id 有一条指向 project(id) 的外键且没有 ON DELETE。 也就是说，那张记录删除行为的台账自己会拒绝项目被硬删——要硬删就得先销毁删除审计， 而那张表存在的全部理由正是让这件事不可能发生。 所以走归档：ARCHIVED 从 V2 起就在 ck_project_status 里，零迁移。

归档入口要求一字不差重新输入项目名：不 trim、不忽略大小写、不认前缀。 项目名旁有复制按钮。归档可逆，「恢复」在已归档折叠组里。

此外 project_deletion_record 是「不建通用 audit_event」的唯一记录在案例外。它的 resource_id 故意没有外键——被引对象按定义已经不存在，没有可指向的目标。这条例外不推广：针对存活实体的多态审计表仍然不建。

两条推论决定了很多代码的形状：

  • 反向需求只能用只读 facade 或事件。scm 需要问需求存不存在，但不能碰 RequirementRepository，于是有 RequirementDirectory；project 删成员要让三个下游撤销引用，但不能依赖它们，于是用进程内事件 ProjectMemberRemoving 反转方向。
  • 同时需要自己的表与 PR 推导的逻辑归 review。反过来会在 ArchUnit 最重要的那条规则面前摆上一个环。所以审查活动状态由 review 而非需求端点提供。
实现期踩过的坑

三个模块的成员移除监听器起初都叫 ProjectMemberRemovingListener—— Spring 默认 bean 名取简单类名，直接 ConflictingBeanDefinitionException 启动失败。 现名 RemovedMemberAssignmentListener / RemovedMemberClaimListener / RemovedMemberBindingListener。

监听器必须同步；@TransactionalEventListener 是错的工具。 而漏掉一个监听器不会静默通过：那三处外键没有 ON DELETE， 未撤销的引用会让删除以 23503 被拒——外键本身就是撤销完整性的证明。

ApiException允许被调用方看到的失败，自带它映射到的 HTTP 状态码与错误码。notFound() / conflict() / forbidden() / unprocessable() 是全代码库统一的抛出方式。

安全口径

「用户名不存在」与「口令错误」在字节层面不可区分：两者共用同一个响应体，且 traceId 为空——逐响应生成一个值会让二者可区分。同理，别的项目的资源与从未签发过的 id 也必须同答 404，否则状态码本身就泄露了存在性。

原生 <details> 不会因点击外部而关闭——必须自己补 pointerdown、Escape + 回焦、路由三条路径，并在卸载时摘监听。

贯穿全表的三条规则

  • 每个项目内外键都带 project_id。所以读路径都带 projectId，不存在「按裸 id 查了之后再检查项目」的写法。代价是几乎每个关联都重复一个已映射的列，而 Hibernate 7 会拒绝启动——统一解法是「写入走标量 xxxId，关联的每个 @JoinColumn 都 insertable = false, updatable = false」。
  • 唯一的 ON DELETE 是 pull_request.author_user_id。别处硬删都被外键拒绝，直到有决策定义其语义。三种删除语义的级联都显式写在服务里，未被撤销的引用会让删除以 23503 失败——外键本身就是撤销完整性的证明。
  • 没有种子数据。任何迁移都不携带口令。
加表要同步改三处

漏掉任何一处都不会让单元测试变红：FoundationDatabaseTest.EXPECTED_TABLES、 scripts/phase1-compose-smoke.sh 的 expected_tables、以及同一脚本里的 migration_count 与按版本取 success 的那一行。 V9/V10 落地时后两处都漏了，脚本长期停在「V8 + 19 张表」，CI 的 compose job 与冷启动自证因此一直是失败的—— 而 mvnw verify 全绿，后端测试证明不了一个 shell 脚本。

两个 CHECK 陷阱

ALTER TABLE … ADD CONSTRAINT … CHECK 会校验表里已有的行。 不容忍 NULL 的 CHECK 在新建的空 schema 上必然通过，然后在任何已有数据的部署上直接让迁移失败。 FoundationDatabaseTest 迁移的是空 schema，看不见这件事——所以加受约束列时要像 V9MigrationTest 那样， 先迁到上一版、写一行、再迁剩下的。

而与应用侧词汇不一致的 CHECK 比没有 CHECK 更糟：一个到达约束的值会中止整批插入而不是它自己那一行， 所以 CHECK 忘掉的一个合法类别会把同一次审查里其他所有 finding 一起带走。 应用侧先映射到闭合枚举，CHECK 只做最后防线，并用测试逐个走完枚举比对两份清单。

11红线

下面三类文件改一个字节就会造成实际损坏，而损坏不会在编辑时报错。

一 · 被配置冻结哈希钉住的 9 个评测文件

contracts/formal-manifest.schema.json、contracts/metrics.md、 contracts/run.schema.json、contracts/score-report.schema.json、 formal/config.json、tools/category-aliases.json、 tools/formal_evaluation.py、tools/run_development.py、tools/score.py

改其中任何一个，verify-freeze 就再也无法通过——而 holdout 只跑过一次且不可重跑，冻结证据一旦失效就无法重建。 metrics.md 尤其危险：它读起来就是一份普通指标说明文档，做「文档只保留当前功能」这类清理时极容易顺手改掉。 evaluation/README.md 不在冻结列表里，可以自由改写。

动 evaluation/ 下任何文件前，先跑一次 verify-freeze 拿到那份列表，再比对 git status。

二 · Flyway 迁移被 live 库的 checksum 校验

validate-on-migrate 取默认 true，而部署库的 flyway_schema_history 存着每个版本的 checksum。 编辑已应用迁移里的一行注释就会改变 checksum，后端在真实部署上直接以 FlywayValidateException 起不来。 所以 backend/src/main/resources/db/migration/*.sql 在任何注释或文档清理里都必须逐字节不变—— 那里现在仍留有历史决策编号与「batch 2/3」叙述，这是有意保留而不是漏改。

迁移是只追加的：永不编辑、永不重编号已应用的迁移，只加下一个版本。重命名一个已应用的迁移会同时弄坏测试和每一个既有数据库。

三 · 两个朝相反方向移动的版本常量

ReviewPrompts.VERSION 现为 "review-2"，schema 变化时递增。 FindingKeys.RULE_VERSION 必须保持 "1"——它进 basis_hash， 一改就让全部历史 Finding 的血缘断掉。

三个哈希都不得覆盖模型散文。explanation、suggestion、confidence 是回答里唯一允许随措辞自由变动的字段；任何一个渗进哈希，同一个问题就会在每轮换个说法后变成「新问题」，跨轮去重、抑制与血缘同时失效——而且要到下一轮审查才看得出来。

四 · 测试套件有潜伏的类执行顺序依赖

把 BatchOneApiTest 改名（只改类名与注释，没有任何代码行变化）会让它在完整 verify 里 4 个测试失败， 全部倒在 GET /api/auth/me must issue the XSRF-TOKEN cookie；而单独跑 -Dtest= 该类5/5 全绿。 Surefire 默认 runOrder=filesystem，改名把它挪到了另一个位置，某个先跑的类留下的状态让匿名请求不再下发 CSRF cookie。根因未定位。

所以：phase1-quick.json、phase1-compose-smoke.sh、BatchOneApiTest 这类历史名字一律保留，只清理散文。 遇到那条断言失败，先用 -Dtest=<类名> 单跑确认是顺序依赖，不要去改 SecurityConfig。

数据库测试的禁令

数据库行为只对真实 PostgreSQL + pgvector 验证，绝不用替代品。PostgresTestBase 为整个测试运行持有一个 pgvector/pgvector:0.8.6-pg15-bookworm 容器。

数据库测试里禁止：H2 或任何内存替代、「Docker 缺失就跳过」的分支、@Disabled、assumeTrue 守卫。一个跑不起来的数据库测试必须让构建失败——这里的假绿会藏住模型依赖的约束行为。

几条被测试钉住的形态

  • routes.spec.ts 断言锁死导航与路由形态（6 入口 / 11 路由）。
  • ArchitectureRulesTest 强制八包依赖单向、无环。
  • DatabaseConstraintTest 通过 JdbcTemplate 绕到所有应用代码之下写入，并点名期望的 SQLState（23505 / 23503 / 23514）。只被服务强制的约束等于没被强制。
  • KnowledgeVectorIndexTest 把「为什么没有向量索引」写成测试而不是研究笔记——因为这条论据会过期：pgvector 一旦放宽维度上限，该测试就会失败，而那次失败正是「回去重新决策」的信号。
  • ReviewPipelineIntegrationTest 从 scm 发布的事件出发、断言数据库里的行，中间只替换 provider。它存在的理由是这个项目真实发生过两次的故障形态：每个组件都测过、而没有任何生产代码调用它们。
  • V9MigrationTest / V10MigrationTest 先迁到上一版、写一行、再迁剩下的——这是唯一能抓住「CHECK 校验既有行」那个陷阱的形状。
一条复盘教训

三个 DELETE 端点首次交付时只有 Service 层测试，路径接线与状态码没有任何证明—— 路径写错会在 Service 测试里全绿、而在前端 404。 新增端点时记住：Service 测试证明不了 MVC 映射。

13术语速查

只解释这些词在本项目里的含义，不做完整定义。与走查文档的术语表同一份。

术语在这个项目里的意思
webhook「有事打这个电话」。你在 GitHub 上登记一个 URL，PR 有变动时 GitHub 主动 POST 过来。
HMAC用一个双方都知道的密钥，对一段内容算出的指纹。对方能算出同样的指纹，就证明它知道密钥。
时序攻击通过测量比较操作花的时间来推断正确答案。防法是让比较无论对错都花同样时间。
SSRF诱导服务器去访问它本不该访问的地址（通常是内网）。防法是每次出站前校验目标地址。
Spring BootJava 的 Web 框架。你写带注解的类，它负责建 HTTP 路由、管理对象生命周期、开关数据库事务。
beanSpring 帮你创建并管理的对象。默认用类的简单名作标识，所以两个模块出现同名类会启动冲突。
注解 @Xxx写在类或方法上的标记。框架扫到它就施加对应行为，比如 @Transactional 就是「给这个方法包一个事务」。
事务数据库的「全有或全无」包装：要么全部生效，要么全部不生效，中间状态外界看不到。
行锁读一行的同时锁住它，本次事务结束前别人不能改。用来让并发操作排队而不是互相覆盖。
JPA / HibernateJava 的 ORM：把数据库表映射成对象，你操作对象它生成 SQL。本项目在影响行数即判定结果的地方刻意绕开它写原生 SQL。
外键「这一列的值必须在另一张表里真实存在」的约束。违反时数据库报错 23503。
复合外键由多列一起构成的外键。本项目用它同时保证「同项目 + 正确父行 + 存在」三件事。
CHECK 约束「这一列的值必须满足某个条件」。注意它失败时中止的是整批插入。
触发器数据写入时数据库自动执行的检查或动作。本项目用它拒绝事后篡改 Review 的身份列。
部分唯一索引只对满足条件的行要求唯一，例如「每个项目至多一个 LEADER」。它保证「至多」，「至少」得靠服务端。
Flyway数据库版本管理工具。每次 schema 变更写一个编号 SQL 文件，它按顺序执行并记录。已执行的文件改一个字节就会让启动失败。
schema数据库的结构本身——有哪些表、哪些列、哪些约束。
JSONBPostgreSQL 里可查询的 JSON 列类型。本项目用它整份存下变更文件清单。
pgvectorPostgreSQL 的向量扩展，让数据库能存向量并按相似度排序。
embedding把一段文本转成一串数字（向量），语义相近的文本向量也相近。用来做「按意思找」而不是「按关键词找」。
余弦距离衡量两个向量方向差异的算法。本项目用它做相似度排序。
TopK「取最相似的前 K 条」。本项目 K = 8，且强制限定在同一项目内。
facade只读的门面类。别的模块只能通过它问问题，碰不到底层仓库，也碰不到内部机制。
依赖反转本该 A 调 B，但依赖方向不允许，于是让 A 广播事件、B 主动来听。编译期的箭头方向就反过来了。
ArchUnit专门检查架构约束的测试库。本项目用它强制八个包的依赖单向、无环。
进程内事件同一个 JVM 里的解耦调用，不经过消息队列。本项目要求它同步执行。
租约 / 围栏租约是「我持有这个任务，有效期到某时刻」；围栏是「每次写入都检查我还持有它」。防止过期的 worker 继续写。
抢占多个线程竞争同一个任务，靠一条原子 SQL 保证只有一个成功。
幂等同样的操作做多次和做一次结果相同。webhook 会重复投递，所以处理必须幂等。
不变量系统在任何时刻都必须为真的性质，例如「每个项目恰好一个负责人」。
reconciliation定时巡检，把「已落库但不再推进」的任务重新放回轨道。
CSRF诱导已登录用户的浏览器发出非本意的请求。防法是写请求必须携带一个攻击者拿不到的令牌。
BCrypt专门用于存密码的哈希算法，故意算得慢，让暴力破解昂贵。
SQLState数据库错误的标准编码。本项目直接按码断言：23505 唯一冲突、23503 外键违例、23514 CHECK 违例、22000 向量维度不一致。
Testcontainers测试时用 Docker 起一个真实数据库。本项目禁止用内存数据库替代。
SurefireMaven 跑测试的插件。它默认的类执行顺序是本项目一个已知脆弱点的来源。
Precision / Recall查准率（报出来的有多少是真的）与查全率（真的有多少被报出来）。评测同时报两者，不合成单一分数。
Wilson 区间小样本比例的置信区间算法。评测用它给出区间而不是只给一个点值。
