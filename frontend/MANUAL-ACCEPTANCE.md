# 前端人工验收清单

自动化测试覆盖请求契约、路由、角色动作面和结构化证据，但不能替代真实浏览器中的视觉、键盘和真实后端联调。验收时使用 1440、768、390 CSS px，分别检查正常动态和“减少动态效果”。结果写入当前 Trellis 任务的 `result.md`。

对应基线：六个一级入口 + 顶部居中导航与单页面单 Logo，定义见 `../docs/v2/ARCHITECTURE.md` §6。

## 1. 全局外壳与账户

- [ ] 桌面顶部应用栏：横版 Logo 在左，“工作台 / 项目 / 研发需求 / 项目知识 / 仓库接入 / 代码审查”六个入口在页面水平中心，账户操作在右；页面上没有侧栏，也没有为补齐左右宽度差而偏移的导航。
- [ ] 切换需求、知识、仓库与审查时保留当前 `project` 查询参数。
- [ ] `64rem` 以下顶部栏变为两行，导航可横向滚动且六个入口全部可达，不出现抽屉或折叠菜单。
- [ ] 登录页只出现一个应用图标（`logo-app.png`），没有并排的第二份品牌资源；浏览器标签页 favicon 就是它。
- [ ] `Tab` 可聚焦“跳到主要内容”，所有控件均有可见焦点环且顺序与视觉顺序一致。
- [ ] 正常模式保留粒子、网格、扫描线、光球、雷达、激光、流光和路由转场；减动效模式停止持续与大幅运动但不改变内容。
- [ ] 点击用户名展开的账户弹层里**没有任何口令输入**，只有账户摘要和“管理资料、密码与 SCM 身份”链接。
- [ ] 账户弹层在点击页面其他区域、按 `Esc`、以及跳转路由时都会关闭；按 `Esc` 后焦点回到用户名按钮。
- [ ] 账户区显示“显示名 · @用户名 · 平台 ID”；`/account` 可修改显示名并在刷新后保持。
- [ ] `/account` 可分别验证多个 GitHub/GitLab 身份；标签、用途、外部用户名与稳定 ID 清晰可区分，一次性 Token 提交后清空且响应不回显。
- [ ] `/account` 的“修改密码”与显示名同处账户设置面：当前密码、新密码、确认密码均为密码输入，不一致时只在本地报错；成功后当前会话仍可用、三项口令清空，并提示其他会话失效。
- [ ] `/account` 一次性个人 Token 字段下给出该 Provider 的 Token 创建页入口与最小权限（GitHub `read:user` / GitLab `read_user`）；改成自建实例地址后入口跟着变，地址不可解析时退化为路径文本而不是死链。
- [ ] 三档宽度均无页面级横向滚动和控制台错误。

## 2. 项目、成员、知识与仓库

- [ ] LEADER 可按显示名、用户名或平台 ID 搜索已有账号，多选后一次添加，公共角色与逐行角色覆盖均正确；任一行失败时整批不产生部分成员。
- [ ] 项目卡的操作区是**两列且不留半格空位**：LEADER 看到六个入口（成员管理 / 项目知识 / 仓库接入 / 研发需求 / 代码审查 / 归档项目），非 LEADER 看到五个且最后一个占满整行。
- [ ] 点「归档项目」就地展开确认区：项目名在只读框内可点选中、「复制」按钮可用（复制失败时不报错、仍可手动选中）；**必须一字不差地重新输入项目名**，确认按钮才从禁用变为可用——前缀、大小写不同、首尾带空格都必须仍然禁用。
- [ ] 归档后该项目从上方列表消失、进入「已归档项目」折叠组，点「恢复」可原样回到列表；归档前后成员、需求、知识与审查数据一条不少。
- [ ] 少于两个字符且非纯数字时给出提示且不发请求；选满 50 人后无法再选；有行未选角色时提交按钮禁用；服务端逐行报错时对应预览行被标出。
- [ ] 成员以紧凑表格展示，单屏可比较多名成员；显示名、`@username`、平台 ID、角色集合、SCM 绑定状态、远程账号、仓库权限与核验时间均未丢失。
- [ ] 成员表「角色」列的行分隔线与其余各列**在同一水平线上**，不出现只横跨半列、浮在徽章下方的短线（该列的 flex 必须落在单元格内层，加在 `<td>` 上会让 `display: table-cell` 失效）。
- [ ] 成员可按文本（显示名/用户名/平台 ID）与角色筛选，两者可组合；空结果有明确反馈。
- [ ] “我在本项目使用的 SCM 身份”是独立面板而不是藏在某一行里；它只对当前登录成员出现。
- [ ] 同一成员可同时显示开发与评审角色；权限取能力并集。Leader 只能通过明确确认的转移动作更换，转移后仍恰有一个 Leader。
- [ ] 成员只能为自己选择与项目仓库兼容的 SCM 身份并用一次性 Token 核验仓库权限；Leader 不能替别人选身份。
- [ ] 默认项目绑定立即生效；开启严格审批后显示待审批，Leader 可批准/拒绝，批准前不参与“本人 PR”权限。
- [ ] `/projects/:id/settings` 直接重定向到 `/repositories?project=<id>`，不留下空白的旧设置页。
- [ ] 仓库接入页支持注册与修改 GitHub / GitLab，并显示正确的 webhook 路径；刷新后展示的是后端真实返回的安全元数据，而不是本地缓存的表单值。
- [ ] 修改仓库表单里「新的访问令牌」与「新的 Webhook 密钥」两个输入框**落在同一水平线**上——令牌那格多出的两条说明不得把同行的另一格压低；「仍需负责人批准」的勾选框与它的文字**同一行**（方块在左、文字在右），且独占一整行位于凭据字段之后；注册与修改两种形态下网格都不留半格空位。
- [ ] 访问令牌字段下给出该 Provider 的 Token 创建页入口与最小权限（GitHub `repo`／公开仓库 `public_repo`，GitLab `read_api`）；API 基地址改为自建实例后入口跟着变。
- [ ] token 与 webhook secret 始终为只写字段；返回摘要和页面任何位置都不回显凭据。
- [ ] 项目知识页可由 LEADER 上传 `.txt` / `.md`，上传后显示切片数、已嵌入数、向量维度、Embedding Profile 与索引状态；非 LEADER 只读且看得到同样的状态。
- [ ] 项目知识页可一次选择多个文件上传，并逐文件报告成功/失败；一个文件失败不影响其余文件。
- [ ] LEADER 可删除公共知识文档，删除后列表与 Chunk/向量计数同步减少；需求附件来源的文档不给删除入口而是说明去哪解除附件。
- [ ] 成员表可移除非 LEADER 成员并有二次确认；LEADER 那一行没有移除入口，且给出「先转移负责人」的说明。
- [ ] 作废需求的详情页出现「删除该作废需求」；非作废需求没有该入口。删除后回到需求列表且该需求已消失。
- [ ] 页面任何位置都不显示原始向量，也没有手工向量查询调试台。
- [ ] 需求附件与公共项目知识分开呈现；附件只有显式提升后才出现在公共知识列表里。
- [ ] 文档处理失败时显示真实失败原因，不显示为“处理中”或“已就绪”。
- [ ] 需求质量检查不在项目或仓库页面出现；对应操作位于需求详情。

## 3. 工作台

- [ ] 工作台以真实列表 API 组合出项目概况；没有任何虚构的评分、健康度或运行状态。
- [ ] 首次进入 `/workspace`（URL 不带 `project`）自动补上项目列表的第一个并展示上下文；手动切换到别的项目后刷新，停留在手动选择的那个而不是被改回第一个。
- [ ] 一个项目都没有时展示“先建一个项目”引导与跳转按钮，而不是空白页。
- [ ] “需求质量检查 → 知识增强实现建议 → 唯一 Review Engine”的能力链清晰可读，且每一段都链接到真实业务页面。
- [ ] 页面上没有聊天框、通用 Assistant 入口或“自动执行”按钮。
- [ ] 未选择项目、项目为空、以及接口失败三种情况各有明确空/错状态，不显示为零值成功。

## 4. 研发需求

- [ ] 需求列表先展示项目上下文、筛选和记录；LEADER 的长创建表单位于列表后的“新建需求” disclosure。
- [ ] 需求列表每行对 LEADER 给出行内操作，且**不放宽后端门槛**：`DRAFT` 显示「编辑草稿」+「作废」，`READY`/`IN_DEVELOPMENT` 显示「发布新版本」+「作废」，`DONE` 只有一句说明、没有任何写入入口，`CANCELED` 只有「删除」。作废与删除各有二次确认；删除后该行消失，AI 调用审计与 PR 关联记录仍保留。
- [ ] 文本、需求状态、评审活动三个筛选可组合，空结果有明确反馈。
- [ ] 每条需求的人工状态与评审活动位于不同的 `<dt>/<dd>`，没有合成徽章。
- [ ] 需求详情同时展示当前内容、负责人、人工状态、独立评审活动和六项 PR 活动计数。
- [ ] 结构化需求区可导出包含标题、背景、描述与 AC 的 Markdown；需求文档区只允许 LEADER 上传 `.txt/.md`。
- [ ] LEADER、DEVELOPER、REVIEWER 都可选中需求文档、阅读完整原文并按原文件名下载；窄屏无页面级横向滚动。
- [ ] LEADER 可运行质量检查并看到版本、规则集、规则与 AI 输出；该操作不改变需求状态。
- [ ] 质量检查与实现建议无论输出多长都在各自结果区内定高滚动：面板高度稳定、不撑破容器，1440/768/390 三档均无页面级横向滚动；超长无空格串会断行而不是撑宽。
- [ ] LEADER 与已指派 DEVELOPER 可生成一次性实现建议；REVIEWER 和未指派 DEVELOPER 没有生成按钮。
- [ ] 实现建议没有输入框、对话历史或流式会话含义；修改需求正文后旧 AI 结果清除。
- [ ] 草稿编辑、发布新版本、状态流转、指派和不可变版本历史仍可完整操作。

## 5. 代码审查索引

- [ ] `/reviews?project=<id>` 直接展示项目级 Review 列表，不要求先知道内部 PR 记录 id。
- [ ] 列表可按文本、执行状态、Decision、当前有效性筛选；执行状态、Decision 与当前/过期分别成列。
- [ ] 点击“审查 N”进入详情；点击“PR #N”打开可刷新、可链接的 `pullRequest` 历史面板。
- [ ] LEADER、REVIEWER 和该 PR 的映射作者 DEVELOPER 可见“请求审查 / 重试”，其他 DEVELOPER 不可见。
- [ ] 需求评审活动概览保持只读，并显示六种单 PR 计数。
- [ ] 内部 PR 记录 id 输入只位于底部“故障恢复” disclosure。
- [ ] 768/390 下宽表只在 `.table-scroll` 内横向滚动，不撑宽整页。

## 6. 审查证据与人工闭环

- [ ] Review 执行状态、Decision、当前有效性、Finding 状态、跨轮血缘和 AI 置信度均为独立标签；缺失置信度显示“未记录”。
- [ ] 证据工作台展示审查时的 Requirement、AC、PR 身份、召回知识集合、改动文件和 unified diff，而不是只展示 JSON。
- [ ] 点击 Finding 的“在证据中定位”会高亮匹配 AC、切换匹配文件并高亮真实新/旧行号。
- [ ] 知识区域只称为“本 Review 召回的知识证据集”，不声称某一块直接支持某一 Finding。
- [ ] Diff 的增加/删除/上下文/分段样式可辨，长行在局部滚动；未返回 patch 有明确空态。
- [ ] 覆盖清单明确显示截断、已审查文件和未审查文件；缺失 manifest 不显示为“全部覆盖”。
- [ ] `SUPPRESSED` Finding 位于独立折叠组，仍可查看审计并按真实规则重开。
- [ ] 每次 Finding 流转可填写可选备注；审计记录显示成员用户名，成员已不存在时回退数字 id。
- [ ] LEADER/REVIEWER、DEVELOPER 的 Finding 按钮矩阵与后端一致；LEADER 不出现“认领 / 标记已修复”。
- [ ] 终局决定前置条件不满足时列出具体原因；REQUEST_CHANGES 的 head 闸门与过期 Review 警告保持可见。
- [ ] 原始上下文 JSON 只位于页面底部折叠诊断区。

## 7. 浏览器与网络

- [ ] 1440 / 768 / 390、正常 / 减动效共六种组合均无页面级横向溢出。
- [ ] Console 无新 error；Network 无意外重试或被静默吞掉的 4xx/5xx。
- [ ] 写请求仍由统一请求边界携带 `X-XSRF-TOKEN`，凭据使用 same-origin cookie。
- [ ] 用真实 LEADER / DEVELOPER / REVIEWER 串行走一遍需求 → PR → Review → Finding → Decision → 需求完成闭环。
