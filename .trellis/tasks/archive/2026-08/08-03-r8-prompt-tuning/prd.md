# 提示词调优：分层模板+两段复核+动态few-shot

> 前置：r7（评测地基）+ r4（prompt 管理规范）。全部改动受 spec 中 prompt 规范约束：宁精勿多、漏报 recall-first、版本化+评测门禁、退役机制、禁承诺"零漏报"。微调线（CodeBERT/QLoRA）已裁决不做，口径："评估过，成本收益与标注数据量不支持，选择提示词工程+评测闭环"。

## Goal

在不改模型的前提下把审查质量的上限打出来：分层模板、类型化清单、两段式复核、动态 few-shot 全部落地，且每一步改进都有评测集数字背书；漏报率相对 r7 基线只降不升。

## Requirements

### R1 分层模板重构

- 现有 prompt 拆为三层：系统层（审查员角色 + JSON 输出契约 + 审查纪律：只报改动引入的问题、每问题必须给行号证据）／项目层（知识库上下文 + 技术栈声明）／任务层（diff + 分片上下文）。
- 各层独立版本号，组装逻辑单元测试覆盖（层缺失/超长截断的行为确定）。

### R2 按文件类型定制审查清单

- Java：事务边界、空指针、越权、资源泄漏；SQL/迁移：注入、不可变迁移纪律；yml/配置：密钥明文、默认值漂移；Vue/JS：XSS、契约字段漂移。
- 每清单条目 ≤10（r4 spec 定稿数为准），每条可验证、有对应评测用例背书；无背书条目不准入（宁精勿多的执行形态）。

### R3 两段式审查

- 第一段初审：recall-first，宁多报。
- 第二段复核：对初审 findings 逐条验证"证据行号存在？确属改动引入？严重度恰当？"，删站不住的、降级夸大的。
- 复核段禁止发现新问题（职责单一）；两段各自记录 ai_call_log，成本可见。

### R4 动态 few-shot

- 从人工反馈库选例：同文件类型 + 被确认的真问题 2 条（正例）+ 被标误报的 1 条（负例），拼入项目层。
- 无反馈数据时优雅降级为静态精选例（不报错、不留空段）。
- 选例逻辑纯后端实现（SQL + 拼接），有单元测试。

### R5 评测闭环（每项改动的合入仪式）

- 顺序执行 R1→R4，**每项独立提交，提交说明附评测对比**：漏报率/误报率相对上一版的变化数字。
- 漏报率上升的改动不得合入，回炉或放弃。
- 全部完成后跑终版全量评测，与 r7 基线对比落档：这组数字（提升幅度）是本任务对外口径的唯一来源。

### R6 漏报闭环机制（长效）

- 建立流程：真实使用中每发现一例漏报 → 脱敏后回灌 r7 评测集为新用例 → 对应清单条目补强或新增（附该案例为准入依据）。流程写入 r4 spec 已定的规范，此处落实首个执行入口（文档 + 操作步骤）。

## Out of Scope

- 模型微调、embedding/检索模式调整、级联路由（已裁决不做）；评测框架改造；前端展示改动。

## Acceptance Criteria

- [ ] 三层模板落地且组装逻辑有单元测试；prompt 相关代码零散字符串拼接清零（全部走模板机制）。
- [ ] 四类文件清单成文，每条有评测用例背书映射表。
- [ ] 两段式上线：ai_call_log 可见两段调用及各自耗时/token；复核段确无新增 finding 的机制保证。
- [ ] 动态 few-shot 有测试覆盖（有数据/无数据两路径）。
- [ ] R1-R4 每项提交附评测对比数字；终版对比 r7 基线：漏报率不升（目标：下降），误报率变化如实记录。
- [ ] 漏报回灌流程成文并演练一次（可用构造案例）。
