# Design：提示词调优

## 模板机制选型

- 三层模板存放为后端资源文件（`resources/prompts/` 每层一个文件 + 版本头注释），组装器单一入口 `PromptAssembler`（现有 `AgentPromptAssembler` 已有打码逻辑，评估扩展 vs 新建，避免两套组装机制并存——**禁止出现第二个拼 prompt 的地方**）。
- 版本号进 ai_call_log 的记录字段（现有表已记 prompt 相关长度，增加模板版本标识的落点评估：复用现有列或新迁移；若需迁移，接当前最大版本号之后）。
- 分片审查（REVIEW_MAX_DIFF_CHARS 打包）与三层模板正交：任务层按分片实例化，系统/项目层跨分片复用——注意分片数 × 两段式 = 调用次数放大，成本记录必须能按任务聚合。

## 两段式的关键设计约束

- 复核段输入 = 初审 findings + 对应 diff 片段，**不含知识库全文**（省 token 且复核职责不需要）；输出 schema 与初审同构但只允许删除/降级/保留操作，禁止新增（后端校验：复核输出的 finding 必须能映射回初审集合，映射不上的丢弃并记日志）。
- 复核段失败（超时/解析失败）时的降级策略：保留初审结果原样输出并标记"未复核"——漏报优先原则下，复核失败不能吞掉初审发现。

## 动态 few-shot 选例规则

- 候选池：该项目下被人工标"确认"的 finding（正例）与"误报"的 finding（负例），同文件类型优先，新近优先。
- 注入预算：few-shot 总量计入 RAG_MAX_CONTEXT_CHARS 同级的字符预算，超预算时按 正例2>负例1 顺序裁剪——不能因塞例子把知识库正文挤掉。
- 例子内容脱敏复用现有 prompt 打码逻辑。

## 评测门禁的执行形态

- 每项改动（R1-R4）完成后在服务器跑 `evaluation/` 全量对比，结果 markdown 落任务目录 `eval-runs/`，提交说明引用文件名。人工比对数字后决定合入——不建自动门禁（原 Phase 7 已裁决不做），仪式靠任务纪律保证。
