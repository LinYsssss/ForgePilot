# Member directory, multi-role, and verified SCM identities

## Goal

让项目负责人能够按姓名、用户名或平台用户 ID 搜索并批量选择已注册员工，为每位成员分配至少一个且可多选的项目角色；让员工本人维护多个已验证 SCM 身份，并为具体项目选择与当前仓库兼容的身份，使“本人 PR”授权稳定、可理解且不可冒用。

## Background and confirmed facts

- 当前 `user_account` 只有稳定 `id`、唯一 `username`、密码和账户状态，没有用于识别人名的 `display_name`。
- 当前 `project_member` 同时保存成员关系、单一 `role` 和单一 `scm_external_user_id/scm_username/scm_identity_verified_at`，每个成员无法拥有角色集合或跨项目复用多个 SCM 身份。
- 当前 Leader 通过精确输入用户名逐个添加成员，并可直接替成员填写 SCM 外部身份；系统没有候选人搜索、批量添加、身份所有权验证或项目绑定确认。
- 当前“本人 PR”按项目成员行上的稳定外部 ID 判断，PR 继续保存不可变作者外部 ID/用户名快照；用户名不参与授权。这一稳定 ID 原则必须保留。
- 当前一个项目只有一个活动仓库，仓库身份为 `provider + normalized instance identity + external repository id`。
- 现有 D004 规定每个项目恰有一个 LEADER；D010 规定身份由 Leader 配置。本任务将保留“恰一 LEADER”，并以新决策替换 D010 的身份所有权与绑定流程。
- 现有 16 表 / 7 migration 是已交付基线；本任务新增的账户 SCM 身份、成员角色和项目身份绑定都是现有模型不能表达的独立业务事实，必须通过新决策与追加 Flyway migration 实现，不修改历史 migration。

## Requirements

### R1 Platform account directory

- `user_account` 增加必填显示名；新注册账户必须填写，既有账户迁移时以当前用户名回填，用户可在账户与安全区域修改自己的显示名。
- 所有成员展示统一包含显示名、`@username` 和稳定平台用户 ID，用户名继续作为登录标识。
- 只有已登录的项目 LEADER 可以搜索候选账户；搜索至少输入 2 个字符，支持显示名、用户名和精确数字 ID，分页且限制返回数量。
- 候选接口只返回平台 ID、用户名、显示名、启用状态及是否已是本项目成员；不返回 SCM 身份详情、邮箱、凭据、其他项目关系或完整全站账户列表。SCM 状态只在加入后的成员列表显示。

### R2 Multiple project roles

- 一个有效项目成员必须至少拥有一个角色，可同时拥有 `LEADER/DEVELOPER/REVIEWER` 中的多个角色。
- 权限按角色能力并集计算；例如同时拥有 `DEVELOPER + REVIEWER` 的成员同时获得两类能力。
- 每个项目恰好一个成员拥有 `LEADER` 角色；LEADER 可以兼任其他角色。
- `LEADER` 不通过批量添加或普通角色编辑授予，只能通过独立、明确确认的负责人转移事务完成；转移不得删除双方其他角色。
- API 与前端从单一 `role/myRole` 迁移为 `roles/myRoles`，所有后端授权仍为最终事实源。

### R3 User-owned multiple SCM identities

- SCM 身份归平台用户本人所有，不归项目或 Leader 所有；一个用户可以绑定多个 GitHub/GitLab及自建实例身份，包括同一 Provider/实例下的多个账号。
- 每个新身份至少保存：用户、Provider、规范化实例、稳定外部用户 ID、外部用户名、用户可理解的标签、用途类型、验证状态/方式、验证与最近同步时间；无法确定 Provider/实例的旧管理员声明只能作为不参与授权的 legacy 例外保留。
- 身份唯一授权键为 `provider + instance_identity + external_user_id`；外部用户名和标签只用于展示。
- 同一个远程 SCM 身份不能绑定给两个平台账户。
- 项目仓库 Token 与成员身份验证凭据严格分离；用于验证成员所有权的临时凭据不得作为成员 Token 长期保存或在响应中回显。
- 首版身份所有权验证使用用户本人提交的一次性个人 Token：后端调用对应 Provider 的当前用户接口取得稳定外部 ID/用户名后立即丢弃 Token；不落库、不写日志、不进入审计或响应。OAuth 明确延期。

### R4 Project-specific SCM binding

- Leader 添加成员时只选择员工和项目角色，不替员工猜测或录入外部 ID。
- 项目成员本人从自己已验证的身份中选择本项目使用的 SCM 身份；系统只接受 Provider 和实例与当前项目仓库匹配的身份。
- 系统验证该身份对当前仓库的可见性/协作者权限，并显示验证结果、访问级别和验证时间。
- 只有一个兼容且具备权限的身份时可以推荐，但仍须成员本人确认；存在多个候选时由成员本人选择。
- 项目默认采用验证成功后自动生效；保留项目级“需要 Leader 审批”策略，严格项目中的绑定先进入待审批状态。
- 一个成员在一个项目最多有一个活动 SCM 绑定。身份更换不得覆盖历史绑定，必须记录发起人、审批人（若适用）、生效和结束时间。
- Leader 可查看成员本人选择的身份标签、用途、外部用户名/ID和仓库访问验证结果，用来理解当前项目身份；Leader 不负责在多个账号之间猜测或代替成员选择。

### R5 Conditional binding policy

- 所有成员必须有平台身份、显示名和至少一个项目角色。
- 项目已接入仓库时，拥有 `DEVELOPER` 角色的成员必须完成兼容 SCM 绑定后，才能使用“本人 PR”类权限。
- 仅 `REVIEWER` 或不参与 PR 作者操作的 `LEADER` 可以保持未绑定；页面必须明确显示“无需绑定 / 等待绑定 / 待审批 / 已生效 / 已失效”。
- PR 作者映射和“本人 PR”授权必须匹配活动项目绑定的 Provider、实例和稳定外部 ID，不得只比用户名。

### R6 Batch member management

- Leader 可搜索并勾选多个候选账户，批量应用共同角色，并可逐行覆盖角色。
- 已是成员的账户禁用重复选择；一次最多提交 50 人。
- 提交前显示姓名、用户名、平台 ID、角色和 SCM 就绪状态预览。
- 后端先验证整批输入，再在一个事务内全部写入；任一成员无效、重复、禁用或角色集合非法时整批不落库，并返回可定位到具体行的错误。
- 批量操作不允许授予或转移 `LEADER`。

### R7 Compatibility and documentation

- 通过追加 migration 将旧单角色迁入角色集合；旧显示名以用户名回填。
- 旧项目级 SCM 字段迁为 `LEGACY_ADMIN_ASSERTED`/待成员确认的身份与绑定，不得伪装成用户已验证。
- 迁移必须保留项目、成员、唯一 Leader、需求指派、Finding assignee、PR 作者快照和当前可追踪关系。
- PRD、ARCHITECTURE、IMPLEMENTATION-PLAN、DECISIONS 与前后端规范必须同步更新；正式评测冻结、语料、holdout 台账和原始输出不得触碰或重跑。
- 不新增顶层包、一级导航、AI runtime、运行时依赖或第二 Review 流程；允许从账户菜单进入一个非一级导航的账户设置页。

## Acceptance Criteria

- [ ] AC1 新注册账户必须填写显示名；旧账户显示名无空值，且用户可修改自己的显示名。
- [ ] AC2 Leader 可按显示名、用户名或精确平台 ID 搜索候选人，但不能通过接口枚举全站账户详情或其他项目关系。
- [ ] AC3 Leader 可在一次事务中批量添加最多 50 名成员；任一输入失败时整批不产生部分成员。
- [ ] AC4 每位项目成员至少有一个角色，并可同时拥有多个角色；后端权限按角色集合判断。
- [ ] AC5 每个项目在创建、角色修改和负责人转移后始终恰有一个 LEADER；负责人可兼任其他角色，转移不丢失其他角色。
- [ ] AC6 用户可维护多个带标签的 GitHub/GitLab身份；同一远程身份无法由两个平台用户认领。
- [ ] AC7 成员身份所有权经过 Provider 验证；验证使用的临时凭据不落库、不回显、不进入日志。
- [ ] AC8 项目成员只能为自己选择 SCM 身份；Leader 不能手填或篡改成员的外部 ID。
- [ ] AC9 项目绑定只接受与仓库 Provider/实例匹配并通过仓库访问检查的身份；多个可用身份由成员本人选择。
- [ ] AC10 默认项目的有效绑定自动生效；严格项目需要 Leader 审批，审批结果和身份更换均可追溯。
- [ ] AC11 `DEVELOPER` 未完成有效绑定时不能使用本人 PR 权限；Reviewer/Leader 的角色权限不依赖 SCM 绑定。
- [ ] AC12 GitHub/GitLab用户名变更不改变既有授权，匹配始终以 Provider、实例和稳定外部 ID 为准。
- [ ] AC13 更换身份不会改写历史 PR 作者快照、Review、Finding 或审计记录。
- [ ] AC14 跨项目猜测候选、身份、绑定和成员 ID 均不可见/不可操作；数据库复合外键拒绝跨用户身份绑定和跨项目写入。
- [ ] AC15 旧数据迁移后项目、成员、角色、唯一 Leader 及现有关联完整，旧管理员声明的 SCM 身份明确显示为待确认。
- [ ] AC16 后端完整验证、前端 lint/typecheck/test/build、空库 Compose 启动、迁移升级路径和结构边界检查全部通过，零 skip。
- [ ] AC17 真实浏览器完成“注册并填写显示名 → Leader 批量添加 → 多角色展示 → 员工验证多个身份 → 项目选择/审批 → PR 作者映射”的人工闭环。
- [ ] AC18 Leader 能看到成员所选身份的标签、用途和仓库验证结果，但无法代选、改写或查看任何个人 Token。

## Out of Scope

- 组织/部门/HR 系统、企业通讯录同步、邮件邀请和审批工作流平台。
- 多仓库项目、多个活动 SCM Connection、代码托管浏览器或本地 clone。
- 服务账号/Bot 伪装成员；自动化账号后续应使用独立模型。
- 长期保存成员个人 PAT、自动代成员创建 PR 或修改代码。
- GitHub/GitLab OAuth App、OAuth 回调和持久个人授权令牌；首版只做一次性 Token 验证。
- 从 GitHub/GitLab批量导入所有协作者作为 ForgePilot 账户。
- 成员移除、离职归档与重新激活；当前版本继续保持既有“只添加、不删除成员”边界。
- 修改或重跑正式评测资产。
