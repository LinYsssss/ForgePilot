# Design：后端分批重构

## 总原则

深模块导向（codebase-design skill 词汇）：接口窄、实现深。拆分不是把一个大类切成十个互相调用的小类（那是把复杂度从类内搬到类间），而是找职责边界——每次拆分后调用方应该更少知道细节，而不是更多。

## 批次设计依据

- **批A 先行**：死代码会污染批B/C 的分析（IDE 引用计数、依赖图都会被死代码干扰），必须先清场。
- **批B 独立于批C**：类内结构（长度、命名）与类间结构（包边界）是两个正交维度，分开做每批 diff 都可读；混做会出现"既移动了文件又改了内容"的不可审查提交。
- **move 与 modify 分离**：git 对"移动+修改"同时发生的文件会丢失追溯，凡涉及类移动，先提交纯移动（git 识别为 rename），再提交内容修改。

## 边界划定方法（批C）

1. 以现有顶层包为候选域：review / agent / scm / sandbox(gateway) / knowledge / auth / infra。
2. `mvn dependency:analyze` + IDE 依赖矩阵画当前引用图，标出反向依赖（infra 引用业务、跨域直接 new）。
3. 每条反向依赖三选一：移动类归位 / 引入接口反转 / 判定为合理保留（写明理由）。不追求教科书式纯净，以"新人能答出'这个类该放哪'"为够用线。

## 特征测试策略

重构点无测试覆盖时：先写"锁现状"的特征测试（输入→当前输出，不判断对错），重构后测试不变即行为不变。特征测试放独立目录并标注，与单元测试区分——它们锁的是现状而非正确性，将来可被正经测试替换。

## 风险清单

- `@Transactional` 自调用：拆类时把事务方法拆到被同类调用的位置会静默失效——拆分涉及事务方法时必须检查调用链（跨任务约束已列，此处是高发点）。
- Spring Bean 扫描：移动类跨包可能脱离 `@ComponentScan` 范围，批C 每次移动后启动冒烟。
- 回滚：每批一个提交序列，revert 范围明确。
