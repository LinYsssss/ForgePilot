## 缺陷与要求

### D1 后端：草稿质量检查把旧结果写回已编辑的草稿（P1）

`RequirementQualityService.check` 在模型调用期间不持有事务，返回后 `store` 按项目 + 修订 ID 无条件 UPDATE。调用在途时，DRAFT 原地编辑会先提交并清空质量列，晚到的旧评估随后又被写回新正文。

- 写回前必须确认修订的正文（标题、背景、描述）与 AC（key、文本、顺序）仍等于本次检查读到的内容；不一致就不写库，并返回 409 和一句可操作的中文提示（需求内容已变化，请重新运行检查）。
- 只改 AC 也必须能识别出来。
- 不能把最长 120 秒的外部调用放进事务或锁内。
- 内容未变时行为保持不变，包括已发布修订：已发布修订不可变，旧修订上的结果照常归属到旧修订。

### D2 前端：保存草稿后显示晚到的旧质量报告（P1）

`runQualityCheck` 直接把响应赋给 `qualityReport`，内容保存/发布、重新加载和卸载都不会作废在途请求。

- 质量请求要像实现建议那样带请求序号：保存/发布、需求内容变化、重新加载、卸载时，在途响应、错误和等待状态一律作废。
- 被作废的旧请求不能清掉新请求的等待状态。

### D3 后端：首次 PR 接收旧仓库的快照（P1，范围窄）

`PullRequestSyncService.apply` 加锁重读了仓库行，但没有比较认证/拉取时所用的稳定身份（provider、instance identity、external id）与当前身份是否相同。若首个 PR 入库前仓库身份被修改，旧仓库的 PR 与 patch 会被归到新身份下。

- 在行锁内比较；身份不同时拒绝这份快照，不写任何行，并与「找不到仓库」返回同一个 401。不重新拉取：旧投递属于旧仓库，用新身份重拉会拿到另一个仓库的同号 PR。
- 只轮换凭据、Webhook Secret 或 api_base 时，稳定身份不变，不能因此误拒。
