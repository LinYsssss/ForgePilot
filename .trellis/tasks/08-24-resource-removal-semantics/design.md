## 0. 必须先解决的三处与既有约束的冲突

方案评审的四条决策里有三条一落到代码就撞上现有约束。它们不是实现细节，先定这三条，后面的设计才成立。

### 0.1 留痕表撞上 ARCHITECTURE §2.1 明令「不建」的 `audit_event`

`ARCHITECTURE.md` §2.1 的**不建**清单里写着：

> 通用 `audit_event`（多态 entity_id 无法被 D006 复合外键约束）

而 PRD 已决策第 4 条要的正是「新增**一张**留痕表承载三类删除的可追溯记录」——一个多态 `resource_id`，字面上就是被禁的形状。这条冲突必须正面处理，不能装作没看见。

**结论：建这张表，但把禁令的适用范围写清楚，并记为 D022。**

禁令的理由是「多态 entity_id 无法被复合外键约束」。而**删除台账的被引对象按定义已经不存在**：知识文档与成员是硬删，行没了；R5 又明令「留痕不得写入被删除对象自身」。所以那条理由在这里不适用——不是「我们偷懒不加外键」，是**没有可加外键的目标**。反过来说，这张表上**能**被约束的两列全都被约束了：`project_id` → `project`（项目隔离，AC13 靠它），`actor_user_id` → `user_account`（操作者仍然存在）。`resource_type` 是**三个值的封闭 CHECK 词表**，不是一个开放的多态注册表。

拆成三张窄表并不能解决外键问题——三张表的资源 id 一样悬空，只是把同一个问题抄了三遍（PRD 决策 4 已判定为重复）。所以「一张 + 封闭词表 + 说明清楚哪一列不可约束及为何」是这里唯一诚实的形状。

业务表 19 → **20**。§2.1 的不建清单要同步补一句例外，否则下一个会话读到的仍是一条绝对禁令。

### 0.2 成员移除要动三个模块的表，而 `project` 不能依赖它们

`ARCHITECTURE.md` §1.3 的依赖方向是单向的：`project` **只能**依赖 `common`。而移除一个成员必须撤销：

| 引用 | 所属模块 | 处理 |
|---|---|---|
| `requirement.assignee_id` | `requirement` | 置 NULL |
| `finding.assignee_id` | `review` | 置 NULL |
| `project_member_scm_binding` | `scm` | 删除 |
| `project_member_role` | `project` | 随实体删除（`@ElementCollection` + `@CollectionTable`，JPA 自动） |
| `pull_request.author_user_id` | `scm` | **数据库自己做**：全库唯一一条 `ON DELETE SET NULL`（D010） |

前三条都在 `project` 依赖不到的模块里，而且 §1.4 第 4 条还禁止跨 feature 注入对方 `*Repository`。

**结论：用既有的进程内事件反转依赖方向。** `project` 定义 `ProjectMemberRemoving`，由 `requirement` / `review` / `scm` 各自 `@EventListener` 撤销自己那部分。这**不是**为本任务发明的机制——`scm` 发布 `PullRequestChanged`、`review` 监听，是 §1.3 已经写明并落地的同一形状，连「类型定义在发布方、由监听方 import」这一点都一样。方向上 `requirement → project`、`review → project`、`scm → project` 全部合法，无环。

`PullRequestChanged` 的 javadoc 里那条禁令在这里同样成立并且更要紧：**必须是同步 `@EventListener`，`@TransactionalEventListener` 是错的工具**——它的默认阶段在提交之后运行，那时 `project_member` 行已经删了，撤销再失败也回滚不了。

顺序是承重的：先发事件让各方撤销，**再**删 `project_member` 行。

**而漏掉一个监听器不会静默通过**：那张表的外键没有 `ON DELETE`，删除会被数据库以 23503 直接拒绝，`ApiExceptionHandler` 转成 409。也就是说**外键本身就是「每一处引用都真的撤销了」的证明**，不需要应用层再自己数一遍。这是选事件而非自建编排的额外好处。

### 0.3 `knowledge` 查不到 `requirement_attachment`，但仍能正确执行决策 8

决策 8 要求「被引为需求附件的文档拒绝删除」。`requirement_attachment` 归 `requirement` 所有，`knowledge` 不得注入 `RequirementAttachmentRepository`（§1.4 第 4 条）。

**结论：按 `knowledge_document.source_type` 判定，不查附件表。** 这不是近似，是等价：`fk_requirement_attachment_document_scope` 引用的是 `knowledge_document(project_id, id, source_requirement_id)`，而 `ck_knowledge_document_scope_matches_type` 强制 `PROJECT_KNOWLEDGE ⟺ source_requirement_id IS NULL`。`requirement_attachment.requirement_id` 是 `NOT NULL`，所以公共知识文档**永远进不了附件表**（V4 注释原话：a public-knowledge document (scope NULL) can never be attached: 23503）。反之附件文档与附件行在 `RequirementAttachmentService` 的同一个事务里成对写入。

于是 `source_type = 'REQUIREMENT_ATTACHMENT'` 恰好就是「可能被附件引用」的集合，而 `source_requirement_id` 直接给出是哪条需求在引用——决策 8 要的「指出是哪些需求在引用」由文档自己那一列提供，一次跨模块查询都不需要。

## 1. 迁移 V10

```
V10__resource_removal.sql
```

两件事，都是追加：

```sql
ALTER TABLE requirement ADD COLUMN deleted_at TIMESTAMPTZ;
ALTER TABLE requirement ADD COLUMN deleted_by BIGINT;
ALTER TABLE requirement ADD CONSTRAINT fk_requirement_deleted_by
    FOREIGN KEY (deleted_by) REFERENCES user_account (id);
ALTER TABLE requirement ADD CONSTRAINT ck_requirement_deleted_shape
    CHECK ((deleted_at IS NULL) = (deleted_by IS NULL));

CREATE TABLE project_deletion_record (
    id            BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    project_id    BIGINT      NOT NULL,
    resource_type VARCHAR(32) NOT NULL,
    resource_id   BIGINT      NOT NULL,
    actor_user_id BIGINT      NOT NULL,
    detail        VARCHAR(500),
    created_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT fk_project_deletion_record_project FOREIGN KEY (project_id) REFERENCES project (id),
    CONSTRAINT fk_project_deletion_record_actor FOREIGN KEY (actor_user_id) REFERENCES user_account (id),
    CONSTRAINT ck_project_deletion_record_resource_type
        CHECK (resource_type IN ('KNOWLEDGE_DOCUMENT', 'PROJECT_MEMBER', 'REQUIREMENT')),
    CONSTRAINT ck_project_deletion_record_resource_id_positive CHECK (resource_id > 0)
);
```

三点说明：

- **`resource_id` 故意没有外键**，且这是本表存在的前提，不是遗漏——见 §0.1。SQL 注释里要写明这一点，否则将来会有人"顺手补上"，而那会让硬删无法留痕。
- **不加 `mode` 列**。它完全由 `resource_type` 决定（文档/成员硬删、需求软删），存下来就是可以自相矛盾的冗余。
- `ck_requirement_deleted_shape` 是 `ADD CONSTRAINT ... CHECK`，会**立即校验既有行**（`database-guidelines.md` 记的 V9 教训）。既有行两列皆 NULL，`(TRUE) = (TRUE)` 通过；但这条路径必须在**非空**库上被证明，见 §5。

## 2. T-005 知识文档删除

### 2.1 端点

```
DELETE /api/projects/{projectId}/knowledge/documents/{documentId}   → 204
```

授权 `LEADER`（与 `POST` 一致）。

### 2.2 语义

一个事务里：

```
1. access.requireRole(projectId, actorId, LEADER)
2. 读 knowledge_document(projectId, documentId)，不存在 → 404
3. source_type = REQUIREMENT_ATTACHMENT → 409，文案指出 source_requirement_id 那条需求
4. 删除该文档的全部 knowledge_chunk（embedding 是 chunk 的列，随之消亡）
5. 删除 knowledge_document
6. 写 project_deletion_record(KNOWLEDGE_DOCUMENT, documentId, actorId, "chunks: N")
```

**级联方式是应用层显式删除，不是数据库 `ON DELETE`**（R1 要求写明）。理由是既有的项目级规则：全库只有 `pull_request.author_user_id` 一条 `ON DELETE`，加第二条会把「删除语义由服务显式表达」这条纪律打开一个口子。而 chunk 是纯派生数据，显式删两行代码就够。

AC4（删除后内容不再出现在任何检索路径）**自动成立**且不需要额外代码：`ChunkSearchRepository.search` 只读 `knowledge_chunk`，chunk 没了，Guidance 与 Review 的附件检索就都召不回它。测试要证明这一条，实现不需要为它写东西。

幂等（AC14）：第二次删除得到 404——对硬删来说这就是明确结果，也与项目既有的「不存在与无权限同答」规则一致。

### 2.3 批量上传：**后端零改动**

R1 的「一次选择多个文件上传、逐个文件报告成功/失败、单个失败不阻断整批」正是 N 次调用现有 `POST /knowledge/documents` 的语义——每次调用自己一个事务，天然逐文件独立、天然逐文件有结果。

所以批量上传是**纯前端**：`<input type="file" multiple>` + 依次调用现有端点 + 渲染逐文件结果表。

新建一个批量端点反而更差：它要么是一个事务（违反决策 7 的「单个失败不该让另外九个回滚」），要么是一个不带事务语义的 `POST`（那它只是把前端的循环搬进服务端，还得自己发明一套逐行结果契约）。而且它会横跨 N 次 embedding 外部调用——决策 7 说的「长事务」正是这个。

## 3. T-006 成员移除

### 3.1 端点

```
DELETE /api/projects/{projectId}/members/{userId}   → 204
```

授权 `LEADER`。

### 3.2 事务内顺序（决策 3，加上事件机制）

```
1. projects.findByIdForUpdate(projectId)        -- 与既有角色/转移路径同一把锁，移除与转移因此串行化
2. access.requireRole(projectId, actorId, LEADER)
3. 读目标 project_member，不存在 → 404
4. 目标持有 LEADER → 409「先完成负责人转移」
5. publishEvent(ProjectMemberRemoving)         -- requirement / review / scm 各自撤销并回填计数
6. members.delete(target)                       -- project_member_role 随 @ElementCollection 一起消失
7. members.flush()                              -- 让外键在本方法内就说话，而不是在提交时
8. 写 project_deletion_record(PROJECT_MEMBER, userId, actorId, 事件回填的摘要)
```

第 4 步用服务端检查而不是交给约束：`UNIQUE(project_id) WHERE role='LEADER'` 保证的是**至多**一个，「至少一个」历来是服务端职责（D013.9 / D020）。删掉唯一 LEADER 不违反任何约束，只会让项目失去负责人。

第 7 步的 `flush()` 是有意的：不 flush，外键违例要到事务提交时才炸，那时已经离开了本方法，错误定位会差很多。

第 8 步在删除之后：留痕不写进被删对象（R5），也不指望一条已经不存在的行。

### 3.3 `ProjectMemberRemoving` 是一个「收集型」事件

```java
public final class ProjectMemberRemoving {   // com.forgepilot.project
    private final long projectId;
    private final long userId;
    private final Map<String, Integer> revoked = new LinkedHashMap<>();

    public void revoked(String reference, int count) { ... }
    public String summary() { ... }   // "requirement assignments: 2; finding assignments: 5; ..."
}
```

不用 `record`：它带一个被监听器写入的可变累加器，用 `record` 会让「看起来不可变、实际被改」这件事更难看清。可变是安全的且要在 javadoc 里说明原因——Spring 的同步发布是单线程、同事务、发布方在所有监听器返回后才继续。

累加计数而不是写一句静态文案：R5 要「连带撤销了什么」，而「requirement assignments: 0」和「requirement assignments: 2」是两件不同的事实。它同时也让「三个监听器都真的跑了」在留痕里可见。

三个监听器各自只碰自己的仓库：

| 模块 | 类 | 动作 |
|---|---|---|
| `requirement` | `ProjectMemberRemovingListener` | `update Requirement set assigneeId = null where projectId = ? and assigneeId = ?` |
| `review` | `ProjectMemberRemovingListener` | 同形状，作用于 `Finding` |
| `scm` | `ProjectMemberRemovingListener` | 删除该 `(projectId, userId)` 的全部 `project_member_scm_binding` |

两条批量 `@Modifying` JPQL 更新绕过持久化上下文；本事务里此后没人再读需求或 Finding，所以没有陈旧实体问题。

### 3.4 什么不被动

- `pull_request.author_external_user_id` / `author_username`——不可变作者快照，两列 `NOT NULL`，移除后完整可读（AC6）。
- `pull_request.author_user_id`——由那条唯一的 `ON DELETE SET NULL` 置空。它是**可重算映射**而非事实本身（D010/D020），映射的成员没了，映射就该消失。决策 2 已经把 R2 的原措辞纠正到这一点。
- `pull_request_requirement_event`、`finding` 血缘、`finding_event`、`ai_call_log`——一行不动。
- 用户自有的 `scm_identity` 与平台账号——身份归用户本人，不是项目财产（AC9）。只有项目作用域的绑定随成员关系消失。

## 4. T-007 作废需求软删

### 4.1 端点

```
DELETE /api/projects/{projectId}/requirements/{requirementId}   → 204
```

授权 `LEADER`。

### 4.2 语义

```
1. access.requireRole(projectId, actorId, LEADER)
2. 读 requirement（含已删的），不存在 → 404
3. deleted_at 已非空 → 404（已经从产品面消失了，答案与不存在一致）
4. status <> CANCELED → 409「只有作废需求可以删除」
5. deleted_at = now(), deleted_by = actorId
6. 写 project_deletion_record(REQUIREMENT, requirementId, actorId, "status: CANCELED")
```

前置条件**只要求状态为 `CANCELED`**（决策 6）：软删之下所有既有引用继续有效，不存在悬空风险，再要求「无 PR 关联且无 Finding」只会平白挡住正常使用。

### 4.3 软删的作用面必须逐处枚举

软删是本任务唯一有扩散风险的改动。所有需要过滤的读取点，全表如下：

| 位置 | 处理 |
|---|---|
| `RequirementRepository.findByProjectIdOrderByIdAsc` | 增加 `AndDeletedAtIsNull` 派生查询，列表用它 |
| `RequirementService.require(...)` | 改用 `findByProjectIdAndIdAndDeletedAtIsNull`——**这是唯一的取值口**，因此详情、编辑、发版、状态流转、指派一次全部拒绝已删需求，正是想要的语义 |
| `RequirementDirectory.existsInProject` | 同样过滤：已删需求不该再接受**新的** PR 关联；既有 `pull_request.requirement_id` 是事实，保持不动 |
| `ReviewActivityRepository.requirementIds` | SQL 加 `and deleted_at is null`——已删需求不该出现在活动概览里 |
| `ReviewActivityRepository` 的 `left join requirement` | **不加过滤**（实施时修正）。那次连接只是取 `current_revision_id` 来匹配当前有效 Review；过滤掉会让修订变成 NULL，从而改写「哪个 Review 当前有效」的判定。PR 自身的活动状态是 PR 的事实，与它的需求是否还在产品面无关。`ofRequirement` 的入口已由 `existsInProject` 挡住（`ReviewActivityService:82`），不需要在 SQL 里再挡一次 |
| `RequirementAttachmentService`（`requirements.findByProjectIdAndId`） | 改用过滤版：不能给已删需求上传或读取附件 |
| `ImplementationGuidanceService` / `RequirementQualityService` | 改用过滤版：不对已删需求跑 AI |
| 删除本身 | 保留未过滤的 `findByProjectIdAndId`，只有这里用它（要能判定「已经删了」） |

`ai_call_log.requirement_id` 与 `pull_request_requirement_event` 的外键因为行还在而继续有效——这正是选软删的全部理由（AC11）。

## 5. 测试

只写承重的。每条都写明锁的是哪个不变量。

| 测试 | 锁住的不变量 | 为什么非它不可 |
|---|---|---|
| `V10MigrationTest` | `ck_requirement_deleted_shape` 在**非空** `requirement` 表上的升级路径 | `ADD CONSTRAINT CHECK` 立即校验既有行；`FoundationDatabaseTest` 跑空库，看不见这类失败（V9 的教训，`database-guidelines.md` 明确要求这个形态） |
| `FoundationDatabaseTest` 更新 | 十条迁移 + **二十**张具名表 | 既有测试刻意按名字比对，多一张计划外的表必须失败 |
| 成员移除全链路 | 三个模块的引用全部撤销、快照与审计完好、作者映射置空 | 本任务最重的一条：跨三模块事件编排，任何一个监听器缺失或顺序错都在这里炸 |
| 唯一 LEADER 不可移除 | 「至少一个 LEADER」是服务端职责 | 没有任何约束表达它；删掉就是项目失去负责人 |
| `resource_type` 词表 ↔ Java enum 逐值贯通 | CHECK 词表与应用词表不得分叉 | `database-guidelines.md` 已把这条写成红线（`finding.category` 的教训）：走到 CHECK 的越界值中止的是整批插入 |
| 知识文档删除 | chunk 随文档消亡；附件文档被拒 | 悬空 chunk 会让该项目所有 TopK 查询语义受损；决策 8 的拒绝是可预期行为而非数据库报错 |
| 已删文档不再被召回 | AC4 | 检索侧无代码改动，正确性完全依赖 chunk 真的被删——必须有一条直接证明 |
| 需求软删 | 只有 CANCELED 可删；删后从列表与详情消失；`ai_call_log` 未被销毁 | 状态门禁与审计存续是 R3 的全部内容 |
| 三个 DELETE 的跨项目隔离 | AC13 | 沿用 `BatchOneApiTest.anotherProjectsIdsAreInvisibleOverHttp` 的形态，新端点必须同样不可跨项目探测 |

**刻意不写**：三个端点的 getter/序列化、`detail` 字符串的具体措辞、`project_deletion_record` 各列的可空性单测、幂等第二次调用的逐端点重复用例（语义同一条，写一次）、非 LEADER 逐端点 403 矩阵（授权走同一个 `ProjectAccessService`，已有覆盖）。
