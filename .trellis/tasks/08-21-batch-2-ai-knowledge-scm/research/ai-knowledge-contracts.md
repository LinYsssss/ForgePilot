`MATCH SIMPLE` is load-bearing twice:

- `knowledge_document (project_id, source_requirement_id)`: `project_id` is non-null and
  `source_requirement_id` is null for public knowledge, so the whole key is **skipped** for
  public documents. That is the only reason public knowledge can exist. Same mechanism batch 1
  measured for `requirement.current_revision_id` (D013.10; recorded at
  `V3__requirement.sql:54-59`). Do **not** tighten to `MATCH FULL`.
- `requirement_attachment (project_id, document_id, requirement_id)`: all three are `NOT NULL`,
  so the key is **always** fully checked. That is what makes it a real lock — §2.3 warns the
  opposite case is worthless: "可空复合外键使用 PostgreSQL `MATCH SIMPLE`，因此不能用 Finding 的
  nullable Requirement/Revision/AC 外键证明父 Review 存在".

## 2. The attachment rule, precisely

### 2.1 What makes a document an attachment

`ARCHITECTURE.md` §2.3:

> 附件 Document 必须满足 `source_type='REQUIREMENT_ATTACHMENT'` 且 scope 非空，公共知识必须 scope 为空

Attachment ⟺ `source_type = 'REQUIREMENT_ATTACHMENT'` **and** `source_requirement_id IS NOT NULL`.
Public knowledge ⟺ `source_requirement_id IS NULL`. §2.1 says the same as "附件类型与归属必须匹配".
A CHECK biconditional is the direct encoding (§1.5).

### 2.2 Which table is the source of truth

§2.3: "附件的唯一事实源是 `requirement_attachment`，`knowledge_document.source_requirement_id`
只是受约束检索投影。" D005 repeats it: "`requirement_attachment` 是领域关系事实源；
`knowledge_document.source_requirement_id` 是受数据库约束的检索投影。"

For code: the relation row carries the domain fact; the document column exists so a
**single-table** retrieval predicate can hard-filter without joining back. Never let them
diverge, and never let a user edit ownership through the projection.

### 2.3 What the double composite FK is for

| FK on `requirement_attachment` | Proves |
|---|---|
| `(project_id, requirement_id) -> requirement(project_id, id)` | the requirement exists **and** is in this project |
| `(project_id, document_id, requirement_id) -> knowledge_document(project_id, id, source_requirement_id)` | the document exists, is in this project, and its **projection already equals this relation row's requirement** |

The second is the anti-divergence device: with `source_requirement_id` as the third referenced
column, the database refuses any relation row disagreeing with the document. §2.3:

> 关系表通过 `(project_id,document_id,requirement_id) → knowledge_document(project_id,id,source_requirement_id)` 锁定二者相等，并以 `UNIQUE(project_id,document_id)` 保证一个 Document 最多属于一个 Requirement。

D005's rationale for constraint over service check: "两份可独立修改的归属字段会形成双事实源。"
§2.3 also fixes the write shape: "Document 与关系同事务写入" — one transaction, never two requests.

Observation (not a conflict): `UNIQUE(project_id, document_id)` already implies
`UNIQUE(requirement_id, document_id)`, since `document_id` alone is unique. §2.1 lists both;
`INFERENCE`: declare both, because §2.1 names both. Cost is one redundant index.

### 2.4 "Promote to public knowledge copies rather than rewrites"

§2.3: "提升为公共知识时复制为新 Document，不就地改写原附件。"
D005: "跨需求共享必须复制/沉淀为新的 Project Knowledge，原附件关系保留。"
`PRD.md` P3: "需求附件只在所属需求的 AI 场景可见；跨需求共享必须显式提升为项目知识".

Concretely, for the code:

1. Promotion is an **INSERT**, never an `UPDATE`. No code path flips `source_type` or nulls
   `source_requirement_id` on an existing row. Were there one, the relation FK would block it
   (`23503`) — constraint and rule agree, which is the intended design.
2. Afterwards **two** documents share the same `text`: the untouched attachment and a new public
   document (`source_requirement_id IS NULL`).
3. The `requirement_attachment` row survives verbatim ("原附件关系保留").
4. The new document needs its own `knowledge_chunk` rows — chunks are keyed by `document_id` and
   are not shareable. Whether they are re-embedded or vector-copied is unstated (`OPEN-6`); it
   affects cost and test determinism.
5. Testable invariant: promotion leaves the source byte-identical. Assert the original's
   `source_type`, `source_requirement_id`, `text` and `updated_at` unchanged, and that
   `SELECT count(*) FROM requirement_attachment WHERE document_id = :orig` is still 1.

### 2.5 The retrieval predicate, quoted

§2.3, "附件检索必须在 SQL 中同时硬过滤项目与 Requirement：":

```sql
WHERE project_id = :projectId
  AND (source_type <> 'REQUIREMENT_ATTACHMENT'
       OR source_requirement_id = :requirementId)
```

Two notes. (a) It is written against `knowledge_document` columns, but retrieval ranks
`knowledge_chunk` rows, so the real query joins chunk → document and applies this to the
document side (`INFERENCE`). (b) It is *inclusive* of public knowledge, which is what P3 wants:
a requirement's AI scenario sees public knowledge **plus** its own attachments, never another
requirement's. §7.2 fixes 检索 TopK = 8, "project-scoped".

D005 also bounds when an attachment may be recalled at all: "附件复用 KnowledgeDocument 的解析、
切片和向量能力，但只允许所属 Requirement 的 Quality/Guidance/Review 场景召回。"

## 3. AI Gateway contract

### 3.1 What `ai` owns and must not own

§1.2: "| `ai` | OpenAI-compatible chat/embed 协议与调用记录 | 业务 Prompt、Agent 编排、自动决策 |"

§4.1 (唯一技术入口):

```text
AiGateway.chat(prompt, schema, useCase)
AiGateway.embed(texts, embeddingConfig)
```

> `ai` 负责 HTTP、认证、超时、一次有限重试、调用元数据、Token/延迟与错误分类。
> 它**不知道** Requirement/Finding/Review 等业务类型，也不暴露 tool loop。
> 业务 Prompt 归 `requirement` 与 `review` 各自所有；Requirement Quality 与一次性 Implementation Guidance 共享 AI Gateway 但使用不同 schema。不建 Prompt Registry，不建万能 ContextBuilder。

§1.3: `common ← auth, project, ai` — `ai` may depend on **`common` only**. `knowledge` sits at
`common, project, ai ← knowledge`, so `knowledge` calls `ai`, never the reverse. §8 names the
failure mode: "| AiGateway 变成 Agent 工具箱 | 接口只允许 chat/embed，不暴露 tool loop |".

`INFERENCE`: `AiCallLog` can live in `ai` without breaking §1.3. D013.1 variant A already forces
scalar `Long xxxId` writes with read-only `@JoinColumn`s; drop the association objects entirely
and `ai` keeps only opaque `Long reviewId` / `Long requirementId` — no compile dependency on
`review` or `requirement`. Same shape §1.3 already blesses for knowledge: "`knowledge` 永不反查
requirement（只收不透明 scope id）".

Only sanctioned subpackage: `ai.openai` (§1.1; `ArchitectureRulesTest:25` already hardcodes it).

### 3.2 Timeout, the one retry, and where its authorization comes from

§7.2 (运行边界，初值):

> | LLM 单次调用超时 | 120 s | 超时按瞬时失败处理 |
> | LLM 重试次数 | 1 | 仅瞬时错误（429/5xx/网络） |

§7.1, right after the "不引入 … Resilience4j Circuit Breaker" list: "HTTP timeout + 一次有限
retry + Review FAILED + 人工 retry 足够覆盖当前故障事实。"
§4.1: "`ai` 负责 HTTP、认证、超时、**一次有限重试**…".
Phase 4: "统一 chat/embed Gateway、超时、一次 retry、PromptSanitizer、`ai_call_log`."

**This project otherwise avoids retries. Here is where each half actually comes from.**
There is no blanket "no retries" rule in `docs/v2/`. What exists is:

- A **batch-1 boundary check**, not a law: `result.md` §4 records
  `grep -rniE "retry|fallback|@Recover"` → "无". That proves batch 1 shipped none; it does not
  forbid batch 2.
- A **frontend** prohibition that does not reach the backend:
  `.trellis/spec/frontend/quality-guidelines.md:16`, `state-management.md:39`,
  `hook-guidelines.md:44,72`.
- A **specific** anti-retry ruling: D013.8 — "必须在写法上根除而不是靠重试" — about the LEADER
  swap, not about I/O.
- D013.11 / `.trellis/spec/backend/error-handling.md`: a database constraint conflict is never
  caught and continued. Also not about outbound HTTP.

So the authorization is **§4.1 + §7.1 + §7.2 + Phase 4 of the plan**, and it is narrow on three
axes: `ai` only, transient classes only (429 / 5xx / network / timeout), count exactly 1.
A retry in `knowledge` ingestion, around the database, or on a non-429 4xx has no authorization
and should be rejected in review.

**Do not merge this with the other "once".** §3.5 allows "非法 JSON 允许**一次** format-repair；
仍失败则 FAILED" — a `review`-owned Phase 6 behavior on a *successful* response with a malformed
body. Two distinct budgets; conflating them silently permits up to 4 calls.

Failure classification is REFERENCE, per the matrix: "| `AiTransientFailureClassifier` | 在用；
瞬时/永久错误 | REFERENCE | `ai.openai.AiFailurePolicy` | 去两运行时/历史 error code 兼容，
保留决策表 |". The second runtime is banned twice: matrix `ai/langchain4j/*` → DROP
("V2 只选一个简单 OpenAI-compatible client，避免双运行时") and §7.1 "不引入 … 第二 AI runtime".

### 3.3 What `PromptSanitizer` must reject — the honest answer

**No authoritative document says `PromptSanitizer` rejects anything.** Every source describes
transformation, not refusal. These are the only four mentions in `docs/v2/`:

- §4.3 (Prompt 安全, the entire section): "Requirement、文档、PR 标题、代码注释**全部是不可信数据**，
  不得改变 system/task 指令；发送前做敏感信息脱敏与预算裁剪。"
- Matrix: "| `ai/PromptSanitizer` | 在用；敏感信息脱敏、Unicode 截断 | KEEP | `ai.PromptSanitizer`
  | 纯函数；继续补注入与密钥格式测试 |"
- §8: "| Prompt injection / 伪造证据 | 不可信标记 + source 白名单 + 输出回查 |"
- `IMPLEMENTATION-PLAN.md` 测试纪律: "安全测试必须覆盖 … SSRF 和 Prompt injection."

Derived duties, all sourced, none a rejection:

1. **Redact secrets** before send ("敏感信息脱敏"); the KEEP note asks for more "密钥格式测试" —
   API-key-shaped strings in requirement text, documents or patches must not leave the process.
   Output is a masked string, not an error.
2. **Unicode-safe truncation** to budget ("预算裁剪" + "Unicode 截断") — never split a surrogate
   pair or a multi-byte sequence when cutting to a character budget.
3. **Mark untrusted data** so it cannot pass as instruction ("不可信标记"); §4.3 forbids untrusted
   content from changing system/task instructions.
4. It is a **pure function** ("纯函数"), so it cannot log, touch the database, or throw on I/O.

The three concrete rejections Phase 4 does owe — invalid UTF-8, NUL, oversize — belong to a
**different** class: `KnowledgeUploadValidator`, KEEP'd for exactly that ("大小/类型/UTF-8/NUL/
文件名安全") and named as owner of the 5 MB limit in §7.2. Assigning them to the sanitizer would
put upload policy inside `ai`, which §1.2 forbids. `OPEN-7`: does the sanitizer ever hard-fail?

### 3.4 Exactly which columns `ai_call_log` records

Verbatim §2.1, purpose "评测与故障定位":

> project_id、review_id、requirement_id、requirement_revision_id（三者均可空且使用含 project_id 的复合 FK）、use_case、model、token、latency、status、error

| Column | Nullability | What it is |
|---|---|---|
| `project_id` | NOT NULL | §2.3: every project-scoped table carries it |
| `review_id`, `requirement_id`, `requirement_revision_id` | all nullable | §2.1 says so ("三者均可空"). Nullable because one gateway serves Quality (requirement+revision), Guidance (requirement+revision), Review (review, maybe requirement) and embedding (none of the three) |
| `use_case` | — | the third `chat()` parameter in §4.1; the discriminator across those scenarios |
| `model` | — | the model actually used, for 评测 reproducibility |
| `token` | — | singular in §2.1: `OPEN-4` |
| `latency` | — | unit unstated; ms is the only sane read (`INFERENCE`) |
| `status` | NOT NULL | values unstated: `OPEN-8` |
| `error` | nullable | classified failure text — the "故障定位" half |

Written by `ai` for **both** `chat` and `embed` (§1.2: "chat/embed 协议与**调用记录**"). Never a
page: §6 "AI Logs 均**不做**一级页面". Its consumer is Phase 8 evaluation (`PRD.md` §4
"可复现评测：… Token、耗时"; Phase 8 "报告 … Token、耗时").

`INFERENCE` forced by "故障定位": the row must be written on **failure** too, and outside the
caller's transaction — otherwise a rolled-back Review erases the evidence of why it failed. The
matrix REFERENCEs that pattern while warning against `REQUIRES_NEW` abuse. `OPEN-10`.

## 4. Testability without credentials — the load-bearing section

**The hard constraint, verbatim** (`IMPLEMENTATION-PLAN.md`, "下一步：批次 2", last paragraph):

> **批次 2 的硬约束：CI 不得依赖任何 AI/SCM 凭据或仓库秘密。** AI Gateway、Embedding、
> GitHub Webhook 与 PR 快照的测试一律打到进程内或本地的假服务端，不打真实 provider。
> 真实凭据只在人工验证时使用，且不进仓库。

Batch 1 already holds this line (`result.md` §4: "CI 仍不依赖任何 AI/SCM 凭据或仓库秘密").

### 4.1 The seam is `AiGateway` itself

§4.1 defines `ai` as the **唯一技术入口** with exactly two methods. That is already the seam; no
new abstraction is needed and none should be invented (D013 总判据: "优先选零新增表、零新增列、
零新增抽象的可行解"). Make `AiGateway` a Java interface in `ai`, implemented by
`ai.openai.OpenAiCompatibleGateway`. Everything above it (`knowledge` ingestion and retrieval,
`requirement` guidance) depends on the interface and never touches HTTP.

| Tier | Proves | Tool |
|---|---|---|
| Above the gateway | ingestion, chunking, dimension check, attachment scoping, retrieval boundary, guidance shape | a deterministic **fake `AiGateway` bean** — no socket |
| The gateway itself | HTTP shape, auth header, 120 s timeout, exactly-one retry, transient/permanent classification, `ai_call_log` contents | a **real local socket** serving canned responses |

### 4.2 Is an in-process stub HTTP server on the existing classpath? **Yes — two of them.**

Verified against `backend/pom.xml` and `/root/.m2/repository` on this machine. No new dependency
is required.

**(a) `com.sun.net.httpserver.HttpServer` — the JDK's own server. Strongest option.**

```
$ docker run --rm eclipse-temurin:21-jdk java --list-modules | grep -iE "httpserver|java.net.http"
java.net.http@21.0.11
jdk.httpserver@21.0.11
```

`jdk.httpserver` ships in the same image `backend/README.md` already prescribes for builds. Zero
dependency delta, real TCP socket, real HTTP/1.1. It can:

- return `200` with a canned OpenAI-compatible JSON body;
- return `429` / `503` / malformed JSON on demand, driving `AiFailurePolicy`;
- sleep past the configured timeout, proving the timeout actually fires;
- **count requests** — the only way to prove "exactly one retry, transient classes only": a
  permanent `400` must leave the counter at 1;
- assert the `Authorization` header carried the configured dummy key, proving auth wiring
  without any real key existing.

Wire it with `@DynamicPropertySource` setting `ai.base-url = http://127.0.0.1:<port>` — the same
mechanism `PostgresTestBase:33-38` already uses for the container. Bind `127.0.0.1` port `0` so
the OS picks a free port and CI never collides.

**(b) `org.springframework.test.web.client.MockRestServiceServer` — already on the classpath.**

```
$ unzip -l ~/.m2/.../spring-test-7.0.8.jar | grep MockRestServiceServer
   .../test/web/client/MockRestServiceServer.class
   .../MockRestServiceServer$RestClientMockRestServiceServerBuilder.class
   .../MockRestServiceServer$RestTemplateMockRestServiceServerBuilder.class
```

Arrives transitively via `spring-boot-starter-test`. Binds to a `RestClient.Builder` or
`RestTemplate` and intercepts below the HTTP layer — excellent for request **shape** (path,
headers, JSON body) with a readable `ExpectedCount` API for call counts. Weak exactly where it
matters most: no socket means no honest timeout test, and connection failures must be simulated
rather than observed.

**Recommendation** (`INFERENCE`): (a) for timeout / retry-count / classification, (b) for
request-shape assertions where a socket adds nothing. Both are free and complementary.

**What is NOT available, and should not be added.** WireMock and OkHttp MockWebServer are absent
from `backend/pom.xml` and from the local repository:

```
$ find ~/.m2/repository -maxdepth 4 -iname "*wiremock*" -o -maxdepth 4 -iname "*mockwebserver*"
(no output)
```

Either would be a new dependency, and `.trellis/spec/backend/quality-guidelines.md` requires a
concrete failure a new gate would have caught. There is none — the JDK server covers every
listed behavior, and adding one would only cost a fresh CI download.

Supporting facts, all verified: `spring-boot-starter-webmvc` pulls `spring-boot-starter-tomcat`,
so `@SpringBootTest(webEnvironment = RANDOM_PORT)` is available if a real servlet port is ever
wanted; `RestClient` is present in `spring-web` 7.0.8; `@MockitoBean` and `@TestBean`
(`org.springframework.test.context.bean.override.*`) are both in `spring-test` 7.0.8. Batch 1's
HTTP tests use `MockMvc` (`BatchOneApiTest:49`), so the existing style already needs no port.

### 4.3 The bean-replacement seam

`@TestBean` (spring-test 7.0.8, verified) replaces the `AiGateway` bean via a static factory
method — no Mockito DSL, and the fake is ordinary readable Java. `@MockitoBean` is the
alternative when a test wants call verification. Either way the rest of the context is untouched,
so the real PostgreSQL, Flyway, security chain and error contract still run. That matters: the
dimension-mismatch and attachment-scoping tests need the **real** database and only a fake provider.

### 4.4 What a deterministic fake embedding looks like

It must give: same input → same vector (re-index idempotence); different input → different
vector; no network; configurable dimension; and a variant returning the **wrong** dimension.

```java
// dim comes from the configured embedding profile; nothing here is random.
static float[] fake(String text, int dim) {
    long h = 1125899906842597L;                          // fixed seed
    for (int i = 0; i < text.length(); i++) h = 31 * h + text.charAt(i);
    float[] v = new float[dim];
    double norm = 0;
    for (int i = 0; i < dim; i++) {
        h ^= (h << 13); h ^= (h >>> 7); h ^= (h << 17);  // xorshift, deterministic
        v[i] = (float) ((h % 2000) / 1000.0 - 1.0);
        norm += (double) v[i] * v[i];
    }
    float inv = (float) (1.0 / Math.sqrt(norm));         // L2-normalise so cosine behaves
    for (int i = 0; i < dim; i++) v[i] *= inv;
    return v;
}
```

Three variants drive three tests: the normal one; `dim + 1` for the dimension-mismatch assertion
(§5.5); and one that throws or returns a transient failure for `ai_call_log.status = FAILED`.

**The caveat that must not be buried.** A hash-based fake gives determinism but **not semantic
similarity** — "登录接口" and "authentication endpoint" land nowhere near each other. Retrieval
tests written against it can honestly assert **isolation, filtering, TopK size, ordering
stability and dimension handling**, and can assert an exact hit when the query text is
byte-identical to a chunk (distance 0, deterministic rank 1). They cannot assert retrieval
*quality*. Quality belongs to the Phase 6 development set and the Phase 8 holdout with a real
provider, which is where `IMPLEMENTATION-PLAN.md` already puts it. A Phase 4 test claiming
semantic recall against a hash fake would be exactly the false green
`.trellis/spec/backend/database-guidelines.md` bans elsewhere.

If a test genuinely needs controlled neighbourhood structure, the honest trick is to let the
fixture text carry its own coordinates (a leading marker the fake parses into a fixed vector)
rather than pretending the hash is a language model.

### 4.5 The one thing this does not solve

A stub proves the gateway against a contract *we* wrote; it cannot prove the real provider honors
the same contract. Close that gap the way batch 1 closed the nginx hop: one manual run with a
real key, recorded in `result.md`, key never committed. Saying so in `result.md` is the
difference between an honest report and an overclaimed one.

## 5. Phase 4 exit criteria as testable assertions

Verbatim (`IMPLEMENTATION-PLAN.md`, Phase 4):

> 退出：项目隔离、非法 UTF-8/NUL/超限/维度不匹配显式失败，附件关系和检索边界通过测试。

Layer names follow batch 1's actual suites: `DatabaseConstraintTest` writes through
`JdbcTemplate` **below** application code and asserts the SQLState; `*ApiTest` uses `MockMvc`
over the real filter chain; both extend `PostgresTestBase`.

### 5.1 项目隔离

| Assertion | Layer |
|---|---|
| `knowledge_chunk` whose `(project_id, document_id)` names another project's document → `23503`. | DB |
| `requirement_attachment` whose `(project_id, requirement_id)` names another project's requirement → `23503`. | DB |
| `knowledge_document` with a `source_requirement_id` from another project → `23503`. | DB |
| `ai_call_log` with a `requirement_id` from another project → `23503`. | DB |
| Project A's member requesting project B's document id gets **404**, byte-identical to a nonexistent id — non-member and missing must be indistinguishable (`.trellis/spec/backend/error-handling.md`; precedent `BatchOneApiTest.anotherProjectsIdsAreInvisibleOverHttp`). | HTTP |
| Every knowledge repository read method takes `projectId` (§2.3: "Repository 读路径仍必须接受 `projectId`，禁止裸 id 查询后再补权限判断"). Enforce by review or a grep check in `quality-guidelines.md`. | static |

### 5.2 非法 UTF-8 显式失败

- Assert: bytes that are not valid UTF-8 (a lone `0xFF`, or a truncated 3-byte sequence such as
  `E4 B8`) return **422** with the single `ApiError` body, and
  `SELECT count(*) FROM knowledge_document` is unchanged.
- Layer: `KnowledgeUploadValidator` unit test (KEEP'd as an isolated, highly testable class) plus
  one HTTP test for the status code and error body.
- **The trap that makes this test worth writing:** `new String(bytes, UTF_8)` does *not* fail — it
  silently substitutes U+FFFD, so a validator built on it would pass a "no exception" test while
  corrupting the document. Decode with `CharsetDecoder` + `CodingErrorAction.REPORT`, and also
  assert no U+FFFD reached storage.

### 5.3 NUL 显式失败

- Assert: content containing code point U+0000 returns **422**, no row written.
- Second assertion at the DB layer: writing a string containing that code point into
  `knowledge_document.text` through `JdbcTemplate` fails with SQLState `22021`
  (`invalid byte sequence for encoding "UTF8": 0x00`). This documents *why* the validator exists —
  PostgreSQL `text` cannot hold NUL at all — and matches batch 1's rule that every migration
  ships an "assert the constraint really rejects" test (`result.md` §10.5).
- Layer: validator unit + `DatabaseConstraintTest`.

### 5.4 超限 显式失败

- Source, verbatim §7.2: "| 单文件上传上限 | 5 MB | `KnowledgeUploadValidator` |".
- Assert both sides of the boundary: 5 MB + 1 byte rejected, 5 MB exactly accepted.
- **Layering trap:** if `spring.servlet.multipart.max-file-size` is set at or below the same
  limit, Spring raises `MaxUploadSizeExceededException` in the filter chain and the validator
  never runs — and that must still produce the one `ApiError` body, not a Spring default page
  (`error-handling.md` lists that as a mistake). Test the **body**, not just the status, and
  decide deliberately which of the two produces the rejection.
- Also: the JVM envelope is frozen at `-Xmx384m` (`quality-guidelines.md`), so a 5 MB upload must
  not be buffered several times over.

### 5.5 维度不匹配 显式失败

- Source: D001 "应用写入时显式校验维度"; §5 "应用层写入时校验向量维度与当前 Profile 一致，不一致显式失败."
- Assert 1: with the `dim + 1` fake, ingestion fails explicitly — the document ends `FAILED`,
  **zero** `knowledge_chunk` rows are written, and the failure is visible to an admin (§6
  "管理员只需看到文档状态与失败原因" — where disagreement C bites, since no column can hold the reason).
- Assert 2 (the honest one): prove the **database does not** protect you. Insert a wrong-dimension
  vector directly via `JdbcTemplate` and assert it **succeeds**, because `embedding` is a
  typmod-less `vector` (D001). That single test is what justifies the application-layer check
  existing; without it a reader assumes the column guards them.
- Assert 3: `knowledge_chunk.dimension` equals the vector's actual length for every written row,
  so the audit column cannot drift from the data.
- Layer: service test with a fake gateway + `DatabaseConstraintTest`.

### 5.6 附件关系与检索边界

- **The single most important row in the batch-2 constraint suite**: a `requirement_attachment`
  whose `requirement_id` differs from the document's `source_requirement_id` → `23503`. That is
  what makes "投影不会漂移" a fact rather than a hope; §2.3 already lists it among the fixed
  integration tests ("固定集成测试包含：… 附件关系与投影不一致").
- A second `requirement_attachment` for the same `document_id` → `23505`.
- `source_type = 'REQUIREMENT_ATTACHMENT'` with a null scope → `23514`; public `source_type` with
  a non-null scope → `23514`.
- Retrieval boundary (the P3/D005 test): in one project seed requirement R with attachment Da,
  requirement R' with attachment Db, and public document Dp. Search scoped to R returns Da and Dp
  and **never** Db; assert the mirror for R'.
- Promotion: promoting Da yields a new public document while Da and its relation row are
  unchanged (§2.4).
- Cross-project guessing, from §2.3's fixed list ("A 项目用户猜 B 项目 requirement/document/… id")
  → 404 at HTTP.

### 5.7 Two Phase 4 items whose exit criteria are silent

- **HNSW index.** D001 / §5 require Phase 4 to add the expression index by separate migration, and
  "检索 SQL 须用一致的 cast 表达式". Testable: `EXPLAIN` on the retrieval query shows an index scan,
  not a seq scan. It fails silently if index expression and query expression differ by so much as
  a cast — which is why the doc calls it out. Blocked on `OPEN-11` and `OPEN-12`.
- **一次性 Requirement Implementation Guidance.** Listed in Phase 4 and `PRD.md` §4, but it appears
  in **none** of the 16 tables — no column anywhere holds its output. `INFERENCE`: it is
  response-only, never persisted; only `ai_call_log` records that the call happened. Consistent
  with "不保存对话" (`PRD.md` §4) and §6's ban on an Assistant page, but a page reload then costs
  another AI call. `OPEN-13`.
